## D1. 향수 간 유사도를 어떻게 정의할 것인가

**문제** — 향 지도는 "가까이 배치할 데이터적 이유"가 필요하다. 유사도를 새로 설계해야 하는가?

**검토한 방법**
1. 기존 EDA 04~06의 Base Similarity 재사용
2. description 텍스트 임베딩
3. `reminds_me_of` 그래프 자체를 거리로 사용

**결정** — (1) 재사용. `sim = 0.5·cosine(accord strength, L2) + 0.5·IDF 가중 Jaccard(note 합집합)`

**근거**
- EDA 04~09가 이미 `reminds_me_of`를 정답으로 삼아 향수-향수 유사도를 측정 완료했다. 향 지도가 새로 푸는 문제는 유사도가 아니라 **2D 투영**이다.
- (3)은 정답을 입력으로 쓰는 것이라 평가가 불가능해진다. 게다가 top1000 중 신뢰 간선 보유 노드가 451개뿐이라 나머지는 배치할 수 없다.
- (2)는 description 품질이 미검증이고 별도 검증 절차가 필요해 2주 안에 무리다.

**결과** — `verify_similarity.py`로 EDA 04의 Development 700 평가를 재현했다. **소수점 4자리까지 일치**했다.

| 모델 | recall@10 | ndcg@10 | EDA 04 기록 |
|---|---|---|---|
| Accord Cosine | 0.1868 | 0.1688 | 0.1688 (차이 0.0000) |
| Note Jaccard | 0.2545 | 0.2345 | 0.2345 (차이 0.0000) |
| Accord + Note | 0.2900 | 0.2668 | 0.2668 (차이 0.0000) |
| **Accord + IDF Note** (채택) | **0.3010** | **0.2709** | 04에 없음 (05에서 채택) |

query 수(12,150 / 3,835), vocab(92 / 2,523), nnz(1,000,570 / 1,091,811) 전부 일치.

**Trade-off** — accord는 향수당 8개 상한이 있어 표현력에 천장이 있다. note는 표층 문자열 기반이라 의미적 유사성(예: 서로 다른 이름의 같은 원료)을 못 잡는다.

## D2. 2D 배치 방법 — MDS에서 UMAP으로 뒤집음

**문제** — 1000×1000 거리행렬을 2D로 어떻게 떨어뜨릴 것인가.

**검토한 방법** — Metric MDS / UMAP / t-SNE / PCA

**최초 판단** — MDS. 이유는 (a) 목적함수가 "거리 보존" 자체라 제품 주장과 일치, (b) `sklearn` 기설치로 의존성 추가 불필요, (c) stress가 해석 가능.

**뒤집은 계기** — 의존성 논거가 약하다는 지적을 받고 실제 거리행렬을 측정했다.

| 측정 항목 | 값 |
|---|---|
| pairwise 거리 평균 / 표준편차 | 0.824 / 0.107 |
| 1번째 최근접 이웃 평균 거리 | 0.466 |
| 20번째 최근접 이웃 평균 거리 | 0.596 |
| 중앙값 파트너 거리 | 0.837 |
| 국소 신호 구간(1~20위)에 드는 pair 비율 | **2.77%** |
| 그 pair가 차지하는 제곱거리 합(MDS 목적함수 질량) | **1.24%** |

→ MDS는 최적화 노력의 **98.8%를 정보 없는 pair**에 쓴다. 고차원 희소 데이터의 거리 집중 현상이다.

성분을 분리하면 실패 방식까지 예측됐다.

| 성분 | 거리 평균 | 표준편차 | d<0.8 비율 |
|---|---|---|---|
| accord cosine | 0.694 | 0.195 | 65.6% |
| IDF note Jaccard | 0.954 | 0.048 | **1.1%** |

note는 거의 전부 "멀다"에 포화. 그런데 EDA 측정상 **더 강한 신호가 note**(ndcg 0.2345 vs 0.1688). MDS는 퍼짐이 큰 accord에 지배되고 note 구조를 버릴 것으로 예측했다.

**결정** — UMAP (`metric='precomputed'`, `n_neighbors=10`, `min_dist=0.1`, `random_state=42`)

**추가 근거** — CLAUDE.md가 "계열 내부 관계 우선, 전 계열 통합 좌표계는 필수 아님"이라고 명시한다. 전역 좌표 일관성이 MDS의 유일한 강점인데 그게 요구사항이 아니었다.

**결과** — 출처 `results/layout_comparison.csv`

| layout | trust@10 | trust@20 | knn_overlap@10 | reminds_pct |
|---|---|---|---|---|
| random | 0.4980 | 0.5044 | 0.0086 | 0.5058 |
| pca | 0.7523 | 0.7541 | 0.0810 | 0.2019 |
| mds | 0.7674 | 0.7684 | 0.0835 | 0.2452 |
| **umap nn=10 md=0.1** | **0.9387** | **0.9186** | **0.3888** | 0.1766 |
| umap nn=10 md=0.3 | 0.9094 | 0.8941 | 0.3354 | 0.1662 |
| umap nn=15 md=0.1 | 0.9340 | 0.9192 | 0.3686 | 0.1570 |
| umap nn=15 md=0.3 | 0.9014 | 0.8907 | 0.3174 | 0.1601 |
| umap nn=30 md=0.1 | 0.9320 | 0.9198 | 0.3405 | 0.1519 |
| umap nn=30 md=0.3 | 0.9031 | 0.8940 | 0.3051 | 0.1485 |

- **예측이 맞았다.** MDS는 kNN overlap 0.0835로 PCA(0.0810)를 겨우 넘고, `reminds_pct`는 오히려 PCA보다 **나쁘다**(0.2452 vs 0.2019). UMAP은 kNN overlap에서 MDS의 **4.7배**.
- `n_neighbors` 3개 값에서 지표가 일관됐다(trust@10 0.90~0.94). 단일 설정의 우연이 아니다.
- random·PCA 대비 세 지표 모두 우위.

**갱신 전 값 (보존)** — 옛 대상 집합에서의 측정. 결론은 동일했다.

| layout | trust@10 | trust@20 | knn_overlap@10 | reminds_pct |
|---|---|---|---|---|
| random | 0.5020 | 0.5045 | 0.0064 | 0.5132 |
| pca | 0.7650 | 0.7663 | 0.0812 | 0.1964 |
| mds | 0.7747 | 0.7767 | 0.0934 | 0.2422 |
| **umap nn=10 md=0.1** | **0.9411** | **0.9208** | **0.3874** | 0.1738 |
| umap nn=10 md=0.3 | 0.9122 | 0.8987 | 0.3468 | 0.1711 |
| umap nn=15 md=0.1 | 0.9369 | 0.9232 | 0.3731 | 0.1804 |
| umap nn=15 md=0.3 | 0.9109 | 0.8965 | 0.3285 | 0.1658 |
| umap nn=30 md=0.1 | 0.9274 | 0.9179 | 0.3403 | 0.1658 |
| umap nn=30 md=0.3 | 0.9016 | 0.8950 | 0.2959 | 0.1606 |

**Trade-off** — "지도상 거리 = 유사도"라고 말할 수 없게 된다. UMAP 좌표는 거리 척도가 아니다. 대신 정확한 답은 고차원 기준 `neighbors` 배열이 담당하도록 설계했고, JSON에 `distance_is_metric: false`를 명시했다. 다만 위 측정대로 MDS로도 이 데이터에선 낮은 stress를 얻을 수 없으므로 실질 손실은 없다.

> **갱신**: 대상 선정 규칙이 `dominant accord 1단계 할당`에서 `usable_pool의 group 결측 제외(7,815 -> 7,302) + 4대 그룹 정원 -> 그룹 내 accord 2단계 할당`으로 바뀐 뒤의 값이다. 대상 1,000개가 달라져 모든 하위 수치가 이동했다. 이 변경은 커밋 경계에서 일어나지 않았다 — MAP 전체가 단일 커밋 `5a9b0c8`로 들어왔고 그 커밋의 `results/*.csv`는 이미 현재 값이었다. 즉 변경은 `5a9b0c8` 이전 미커밋 작업 중에 일어났고 문서 본문만 옛 실행 결과로 남아 있었다. 재현: 옛 규칙을 현재 데이터로 다시 돌려 옛 수치가 그대로 나오는 것을 확인했다(브랜드 219 / 신뢰 간선 896 / A안 943). **결정은 변하지 않음** — UMAP이 random·PCA·MDS를 세 지표 모두에서 이기는 구조가 그대로다.
>
> 단, 위 "뒤집은 계기"의 거리행렬 진단 표(평균 0.824 / accord σ 0.195 / note σ 0.048 등)는 옛 대상 집합에서 측정한 값이고 현재 집합으로는 다시 재지 않았다. 방법 선택의 근거로만 쓰였고 산출물 수치가 아니라 그대로 둔다.

## D3. 지도에 올릴 향수 선정

**문제** — 어떤 향수를 지도에 올릴 것인가. 기획 초안은 "대표 향수 약 200개".

**검토한 방법** — 인기순 top-N / accord 계열별 할당

**결정** — 화면 200개 + 좌표 1000개, 계열(dominant accord)별 **제곱근 비례 할당**(하한 5 / 상한 60), 후보 풀 `people >= 500`. 화면 200개도 같은 규칙.

**근거 1 — 200개로는 검증이 불가능하다** (규모별 집합 내부 정답 간선 측정)

| 집합 | 내부 간선 | 신뢰 간선 | 신뢰 간선 보유 노드 |
|---|---|---|---|
| 인기 top200 | 203 | 94 | **70 / 200** |
| 인기 top1000 | 2,425 | 943 | 483 / 1000 |
| 인기 top2000 | 7,393 | 2,611 | 1,145 / 2000 |

**근거 2 — 인기순은 편향돼 있다** — 출처 `results/selection_comparison.csv`

| 지표 | A. 인기순 top1000 | B. 그룹→accord 할당 | 변화 |
|---|---|---|---|
| dominant accord 커버리지 | 42종 | **58종** | **+38.1%** |
| 브랜드 수 | 182 | **223** | +22.5% |
| 상위 10개 브랜드 점유율 | 29.6% | **25.3%** | −4.3%p |
| vote_count 최소 / 중앙값 | 3,309 / 5,579 | 501 / 5,266 | — |
| 집합내 reminds 간선 | 2,387 | 2,255 | **−5.5%** |
| **신뢰 간선** | **915** | **872** | **−4.7%** |
| 신뢰 간선 보유 노드 | 508 | 467 | −8.1% |

두 행 모두 같은 후보 풀(`usable_pool`, group 결측 제외)에서 뽑은 값이라 A와 B가 같은 조건에서 비교된다. 근거 1의 규모별 표는 group 필터 이전 기준이라 여기의 A행과 직접 비교되지 않는다.

**결과** — 계열 커버리지 +38%와 브랜드 다양성을 **신뢰 간선 4.7% 손실**로 얻었다. 절대량(신뢰 간선 872개)이 검증에 충분하다.

**Trade-off** — 최소 투표수가 3,309 → 501로 내려간다. "사용자가 아는 향수" 전제가 약간 약해진다. 후보 풀을 `people>=200`까지 넓히면 계열이 66종으로 늘지만 신뢰 간선이 883으로 더 줄고 최소 투표수가 203까지 떨어져 채택하지 않았다.

**갱신 전 값 (보존)** — accord 커버리지 43 → 58종(+35%), 브랜드 179 → 219, 상위10 점유율 29.2% → 25.5%, 간선 2,425 → 2,367(−2.4%), 신뢰 간선 943 → 896(−5.0%), 최소 투표수 3,403 → 510.

> **갱신**: 대상 선정 규칙이 `dominant accord 1단계 할당`에서 `usable_pool의 group 결측 제외(7,815 -> 7,302) + 4대 그룹 정원 -> 그룹 내 accord 2단계 할당`으로 바뀐 뒤의 값이다. 대상 1,000개가 달라져 모든 하위 수치가 이동했다. 이 변경은 커밋 경계에서 일어나지 않았다 — MAP 전체가 단일 커밋 `5a9b0c8`로 들어왔고 그 커밋의 `results/*.csv`는 이미 현재 값이었다. 즉 변경은 `5a9b0c8` 이전 미커밋 작업 중에 일어났고 문서 본문만 옛 실행 결과로 남아 있었다. 재현: 옛 규칙을 현재 데이터로 다시 돌려 옛 수치가 그대로 나오는 것을 확인했다(브랜드 219 / 신뢰 간선 896 / A안 943). **결정은 변하지 않음** — 계열 커버리지를 얻고 신뢰 간선을 5% 안팎 잃는 교환비가 그대로다.

## D4. 클러스터 개수와 라벨

**문제** — 프론트가 "향 계열 영역"을 그리려면 라벨이 필요하다. 몇 개로, 어떤 형태로?

**검토한 방법** — k = 8 / 12 / 16을 모두 실행해 accord 구성표를 비교. 갱신 시점에는 **채택 좌표 위에서 각 k가 실제로 영역을 이루는지**도 측정했다(`region_cohesion`, 신뢰 간선의 클러스터 횡단 비율).

**결정** — **k=12**, 라벨은 **상위 accord 3개**만 내보냄

**근거** — 출처 `build_map.py --experiment-b` 실행의 Step 3 출력 + 채택 좌표(`output/scent_map_v1.json`) 기준 응집도 측정

재현: `python review_k.py` — 아래 표의 k별 응집도·클러스터 횡단 비율과 k=16의 accord 구성을 그대로 출력한다.

| k | 최대 클러스터 | 응집도 (무작위 대비) | 신뢰 간선의 클러스터 횡단 | 응집도 0.35 미만 라벨 |
|---|---|---|---|---|
| 8 | 426 (42.6%) | 0.791 (3.0배) | 275/872 (31.5%) | 1개 |
| **12** | **281 (28.1%)** | **0.762 (4.4배)** | **306/872 (35.1%)** | **3개** |
| 16 | 248 (24.8%) | 0.726 (4.9배) | 333/872 (38.2%) | 5개 |

- **k=8 배제** — 한 영역이 지도의 42.6%다. "이 영역이 무슨 향인가"에 답이 안 된다. k=12가 그 426을 `aromatic·woody·citrus`(281)와 `warm spicy·woody·amber`(145)로 분리한다.
- **k=16 배제** — k=16이 얻는 것은 실질 영역 2개다(`leather·woody·animalic` n=28 응집도 0.575, `lavender·aromatic·vanilla` n=33 응집도 0.545). 대신 **경계를 그릴 수 없는 라벨이 3개에서 5개로 늘고**(`sweet·powdery·green` n=4 응집도 0.05, `oud` n=7 응집도 0.2 추가), 신뢰 간선의 클러스터 횡단이 35.1% → 38.2%로 늘어난다. 실험 B(D9)에서 이 횡단 비율이 영역 라벨의 실질 비용임을 확인했고, 실험 B 기각으로 영역을 경계 오버레이로 그리게 된 이상 그릴 수 없는 라벨이 5개인 것은 직접적인 손해다. 최대 클러스터 28.1% → 24.8%의 개선은 "무슨 향인가"에 답이 되는 구간에서는 둘 다 같은 답(`aromatic·woody·citrus`)을 준다.
- 다만 **leather를 독립 영역으로 두는 것이 기획상 가치가 크다면 k=16도 방어 가능한 선택이다.** 위 표가 그 교환비다.

라벨을 한국어 이름 대신 accord 구성으로 둔 이유는 CLAUDE.md의 "근거 없는 scent inference 금지"다. `["woody","warm spicy","amber"]`는 데이터에서 직접 나온 사실이라 검증 가능하고, 사용자에게 보일 한국어 이름은 기획이 나중에 붙일 수 있다.

**결과** — 클러스터가 2D에서 실제로 영역을 이룬다.

- 2D 최근접 10개 중 같은 클러스터 비율 **0.762** vs 무작위 기대값 **0.175** (4.4배)
- 큰 클러스터들의 응집도: aromatic·woody·citrus(281) 0.832 / powdery·woody·musky(128) 0.811 / white floral·floral·citrus(121) 0.769 / sweet·vanilla·fruity(200) 0.760 / warm spicy·woody·amber(145) 0.742

**Trade-off** — n≤3짜리 클러스터가 2개 생기고, 응집도 0.35 미만이 3개다(c2 `mineral·woody` n=6 0.083, c9 `marine` n=2 0.0, c11 `metallic` n=1 0.0). average linkage의 특성이다. UI에서는 무시하거나 인접 클러스터에 병합하는 처리가 필요하다 — 실험 B(D9)에서 실제로 `n<4`를 병합해 12개를 10개로 줄였다.

**갱신 전 값 (보존)** — 최대 클러스터 k=8 411(41%) / k=12 230(23%) / k=16 230(23%), 응집도 0.748(무작위 0.171), 저응집 클러스터 c7 0.100 · c10 0.000 · c11 0.164. 당시 k=16 배제 근거였던 "최대 클러스터가 k=12와 동일(230)"과 "2~3개짜리 클러스터 증가"는 **현재 데이터에서 재현되지 않는다** — k=16의 최대는 24.8%로 k=12보다 작고, n≤3 클러스터는 두 k 모두 2개다. 그래서 위 근거를 측정으로 교체했다.

> **갱신**: 대상 선정 규칙이 `dominant accord 1단계 할당`에서 `usable_pool의 group 결측 제외(7,815 -> 7,302) + 4대 그룹 정원 -> 그룹 내 accord 2단계 할당`으로 바뀐 뒤의 값이다. 대상 1,000개가 달라져 모든 하위 수치가 이동했다. 이 변경은 커밋 경계에서 일어나지 않았다 — MAP 전체가 단일 커밋 `5a9b0c8`로 들어왔고 그 커밋의 `results/*.csv`는 이미 현재 값이었다. 즉 변경은 `5a9b0c8` 이전 미커밋 작업 중에 일어났고 문서 본문만 옛 실행 결과로 남아 있었다. 재현: 옛 규칙을 현재 데이터로 다시 돌려 옛 수치가 그대로 나오는 것을 확인했다(브랜드 219 / 신뢰 간선 896 / A안 943). **결정은 변하지 않음(k=12 유지)** — 다만 위와 같이 **근거는 교체됐다.**

> **주의 — 꽉 차는 축이 x에서 y로 바뀌었다.** 갱신 전에는 x폭 1.0 / y폭 0.7242였고 지금은 x폭 0.8476 / y폭 1.0이다. 어느 축이 1.0을 채우는지는 대상 집합과 UMAP 실행에 따라 **바뀔 수 있는 값**이다. **프론트는 이 문서의 숫자가 아니라 `output/scent_map_v1.json`의 좌표 범위를 직접 읽어 여백을 계산해야 한다.** 문서 값을 하드코딩하면 재생성 때마다 지도가 찌그러진다.

**Trade-off** — 프론트가 캔버스에 채울 때 여백 처리를 해야 한다.

**갱신 전 값 (보존)** — x폭 1.0000 / y폭 0.7242.

> **갱신**: D2~D4와 같은 원인이다 — 대상 선정 규칙이 `dominant accord 1단계 할당`에서 `usable_pool의 group 결측 제외(7,815 -> 7,302) + 4대 그룹 정원 -> 그룹 내 accord 2단계 할당`으로 바뀌면서 대상 1,000개가 달라졌다. 커밋 경계가 아니라 `5a9b0c8` 이전 미커밋 작업 중의 변경이라 커밋으로 특정되지 않는다. **결론은 유지됨** — x·y 동일 배율 정규화 방침과 "한쪽 축만 1.0을 채운다"는 성질 모두 그대로다. 바뀐 것은 어느 축이 채우는지뿐이다.

## D9. 클러스터 라벨을 넣은 반지도 UMAP (실험 B) — 기각

**문제** — 현재 좌표는 이웃 보존이 좋지만(trust@10 0.9387) 2D에서 클러스터가 섬처럼 갈라지지 않는다. 프론트는 탑뷰에서 읽히는 영역 경계와 "사용자 취향 원이 어느 영역인가"가 필요하다. k=12 클러스터의 2D 응집도는 0.764(무작위 0.175)로 영역은 존재하지만 경계가 맞닿아 있다.

**검토한 방법**
1. A안 — 좌표는 그대로 두고 영역 경계를 오버레이로 그린다
2. B안 — 클러스터 라벨을 UMAP target으로 주어 좌표 단계에서 섬을 가른다 (이 실험)
3. C안 — 4계열 라벨로 재배치. `scent_family_decision.html`에서 이미 기각(4계열은 설명문 라벨이고 향 구성과 다른 축. 닮았다 투표 쌍의 50.1%가 계열 간)

**결정** — **B 기각. A안 유지.** 좌표는 `umap_nn10_md0.1` 그대로 두고, 영역 표현은 오버레이로 푼다.

**합격 기준은 실행 전에 확정했고 결과를 보고 수정하지 않았다.** `build_map.py`의 `PASS_TRUST10=0.90` / `PASS_OVERLAP10=0.30` / `PASS_CROSS_MARGIN=0.05` 상수가 그 기록이다. 근거는 D2 스윕에서 채택 가능하다고 본 UMAP 설정들의 실측 범위(trust@10 0.90~0.94, knn_overlap 최저 0.305)다.

### 실험 조건

- 재현: `python build_map.py --experiment-b` → `results/supervised_umap_comparison.csv`
- 고정: 거리행렬 D(Base Similarity), 대상 1,000개, `n_neighbors=10`, `min_dist=0.1`, `random_state=42`, `metric='precomputed'`

- 선행 확인: umap-learn 0.5.12에서 `metric='precomputed'` + `y` 조합이 동작함을 1회 실행으로 확인(성공). 실패 시 원 feature로 우회하지 않기로 했다 — 우회하면 D2 좌표와 비교가 불가능해진다.

**라벨 병합** — `n < 4`인 클러스터를 병합해 12개 → **10개**. precomputed 거리에는 중심(centroid)이 없으므로 **"그 클러스터 구성원까지의 평균 거리"**를 가까움의 기준으로 썼다. 클러스터를 만든 average linkage와 같은 기준이라 일관되고 결정적이다.

**baseline 재현** — 재생성한 baseline이 `results/layout_comparison.csv`의 `umap_nn10_md0.1`과 trust@10 / knn_overlap@10 / reminds_pct 모두 **소수점 4자리까지 일치**(차이 0.0000). 입력이 달라지지 않았음을 확인하고 실험을 진행했다.

**Trade-off** — B를 포기하면서 잃는 것은 좌표 단계에서 공짜로 얻을 수 있었던 영역 분리(sil2d 0.84)다. A안은 경계 다각형 계산이라는 추가 작업을 프론트/후속 작업에 넘긴다. 대신 지키는 것은 향 지도의 원래 주장이다 — 지도상 근접이 "닮았다"와 어긋나지 않는다는 것. 현재 좌표에서도 영역은 이미 존재하고(응집도 0.764, 무작위의 4.4배), 부족한 것은 경계의 시각적 명료함이지 영역 자체가 아니다.

> `output/scent_map_v1.json`은 변경하지 않았다. `scent_map_v2.json`은 만들지 않았다.

> **D2~D6 갱신 완료.** 세 항목 모두 현재 값으로 갱신했고 옛 수치는 각 항목의 "갱신 전 값 (보존)"에 남겼다. 드리프트의 원인은 D8(note 파싱)이 아니라 **대상 선정 규칙 변경**이었다 — 각 항목의 갱신 주석 참조. D4는 k=12 결정을 유지하되 k=16 배제 근거를 측정으로 교체했다.

## D10. 정답 데이터(`reminds_me_of`)의 신뢰성 점검

**문제** — D4/D9에서 신뢰 간선의 **35.1%가 영역을 넘는다**는 값이 반복해서 비용으로 등장했다. 이 값이 지도·라벨의 문제인지, 아니면 정답지 자체의 약점에서 나온 것인지 분리되지 않았다. 의심한 약점은 두 가지다 — 투표한 사람이 너무 적은 것, 그리고 같은 브랜드 쌍이 정답을 쉽게 만들어 주는 것.

**검토한 방법** — 간선 채택 기준을 바꿔가며 횡단 비율이 흔들리는지 본다. 좌표·라벨·거리행렬은 전부 고정하고 **간선 집합만** 바꾸는 단일 변수 점검이다. 라벨은 D9의 병합 라벨(10개), 좌표는 `umap_nn10_md0.1`을 같은 방식으로 재생성해 썼다.

재현: `python check_edges.py` → `results/edge_robustness.csv`, `results/human_check_pairs.csv`

**결과** — 출처 `results/edge_robustness.csv`

| 기준 | 간선 | 같은 브랜드 | 영역 횡단 | 횡단 비율 | reminds_pct | 총 표 중앙값 |

**투표 수 분포** — 기준 A 872쌍의 총 표 수

**해석**

1. **"투표한 사람이 적어서"는 주된 설명이 아니다.** 기준 A 872쌍의 총 표 중앙값이 506이고 95.4%가 20표 이상이다. 최소 3표인 얇은 꼬리는 있지만 소수다.
2. **기준을 조이면 횡단 비율은 실제로 내려간다** (35.1% → 23.9% → 23.6% → 16.4%). 35.1% 중 일부는 약한 간선에서 온 것이 맞다.

`reminds_pct`가 횡단 비율과 같은 방향으로 움직인다(0.1042~0.2039). 두 지표가 서로를 보강한다.

**사람 점검용 표** — `results/human_check_pairs.csv`. 기준 A 간선 중 두 향수 모두 `vote_count` 상위 30%(기준값 7,487표)인 쌍에서 같은 영역 10쌍·다른 영역 10쌍을 총 표 수 내림차순으로 뽑았다. 방향이 반대인 중복 쌍은 사람에게 두 번 묻지 않도록 제거했다. `team_agree_1~3`은 팀원이 채울 빈 칸이고 **여기서 판정하지 않았다.**

추출 과정에서 확인만 해 둘 것 — 다른 영역(N)으로 분류된 P20이 `Narciso Rodriguez for Her Eau de Parfum` ↔ `Narciso Rodriguez For Her`로 같은 브랜드의 같은 계열 제품이다. 반대로 같은 영역(Y)의 P06은 `Baccarat Rouge 540 Extrait` ↔ `Baccarat Rouge 540`이다. 이런 쌍이 라벨 경계 문제인지 클러스터링 문제인지는 팀 점검 결과로 판단한다.

**남는 한계**

- **Negative label이 없다.** `찬성률 ≤ 0.2 & 총표 ≥ 20`인 pair가 0건이라(PLAN §1.5) "안 닮았다"는 검증할 수 없다. 위 표는 전부 positive-only 지표이며, 횡단 간선이 "틀린 배치"라는 뜻은 아니다.
- **투표자 편향.** 대상 1,000개가 이미 `people >= 500` 풀에서 뽑혔고, 사람 점검 컷은 7,487표다. 저투표 구간의 정답 성질은 이 점검으로 알 수 없다.
- **1,000표 이상은 근사값이다** (SCHEMA 명시 — 페이지가 축약 표기). 총 표 75% 지점이 1,023이므로 상위 사분위는 근사 구간에 걸친다. 기준 D처럼 총 표 수에 의존하는 기준은 상단에서 정밀도가 떨어진다.
- 방향 있는 관계를 중복 제거 없이 셌다. 같은 쌍이 양방향으로 기록되면 두 번 계산된다.
- 기준 B와 C가 거의 같다(389 vs 386). 찬성 5표 이상이면서 찬성률 0.7 이상인 쌍은 대개 이미 10표를 넘는다. 두 기준은 사실상 같은 것을 재고 있다.

> **검증** — 기준 A가 간선 872 / 횡단 306 / 35.1%를 정확히 재현했고 `prepare()`가 만든 간선 수와도 일치했다. 기준 A의 같은 브랜드 비율은 **34.8%**(0.3475)로 측정됐다.

> **참조값 36%의 출처** — `scent_family_decision.html`의 "좌표 자체는 검증됐나" 절("정답 쌍의 36%가 같은 브랜드였습니다"). 현재 값과 1.2%p 차이이며 **D2~D6과 같은 선정 로직 드리프트로 추정된다.** 근거는 같은 문단의 다른 수치도 함께 어긋난다는 점이다 — "16%의 쌍은 여전히 멀리 떨어져"가 현재 18.5%다. 반면 그 절의 지표 표(0.498 / 0.752 / 0.939, 0.506 / 0.202 / 0.177)는 현재 `results/layout_comparison.csv`와 일치한다. 표는 갱신됐고 본문 문장만 옛 실행 값으로 남은 것으로 보인다. 36%에 해당하는 모집단은 찾지 못했다(전체 in-set 간선 18.6% / 신뢰 간선 34.8% / 방향 중복 제거 34.4% / 2D 거리 0.35 초과 실패 사례 20.5%).

## D11. 국내 200개 지도의 레이아웃 모집단 — 확장 기각

**문제** — 국내 지도는 200개 점으로 배치돼 있다. 여기서 밀도 지형(높이맵)을 만들면 지형이 200개의 우연한 배치를 그릴 위험이 있고, 200개 안에는 사람이 "닮았다"고 투표한 신뢰 간선이 **40개뿐**이어서(보유 향수 44/200 = 22%) 배치가 맞는지 판정할 근거가 얇다. 글로벌 1,000개에서는 872간선 / 467노드(46.7%)였다.

**검토한 방법**

1. **A안** — 국내 200개만으로 배치 (현재 방식)
2. **B안** — 국내 200개 ∪ 글로벌 대상 1,000개(= **1,140개**)로 배치하고 200개만 `display`

교집합은 60개뿐이다. **국내 200개 중 140개는 글로벌 1,000개에 없다** — 국내 인기와 글로벌 인기가 상당히 다르다.

바꾼 것은 배치 모집단 하나다. 유사도 정의, UMAP 파라미터(`nn=10`, `min_dist=0.1`), 표시 대상 200개는 양쪽 동일. 지표는 전부 **표시 200개 기준**으로 재서 같은 조건으로 비교했고, 시드 5개(42,1,2,3,4)를 돌려 한 번의 우연이 아닌지 확인했다.

재현: `python src/map/compare_korea_map_population.py` → `results/korea_population_comparison.csv`

**결정** — **A안 유지. 확장 기각.**

**근거** — 시드 5개 평균. B안이 모든 배치 지표에서 열세다.

| 지표 | A (200) | B (1,140) | 판정 |
|---|---|---|---|
| trust@10 (표시 200 기준) | **0.9173** ±0.0046 | 0.8975 ±0.0022 | A |
| kNN overlap@10 | **0.4864** ±0.0060 | 0.4076 ±0.0038 | A (상대 +19%) |
| 정답 간선 2D 거리 백분위 (내부 40간선, 낮을수록 좋음) | **0.1869** | 0.2376 | A |
| **시드 간 밀도 격자 상관 (최저)** | **0.9374** | 0.7661 | A |
| 육지 덩어리 개수 범위 | 1~2 | 1~1 | — |

B안이 얻는 것은 **검증 커버리지 하나**다. 200개에 인접한 신뢰 간선이 40 → **276개**, 간선을 하나라도 가진 표시 향수가 44 → **100/200(50%)** 로 늘고, 그 276간선의 거리 백분위도 0.1959로 무작위(0.5)보다 훨씬 좋다.

그런데 그 이득이 배치 품질 손실을 정당화하지 못한다.

- **핵심은 시드 안정성이 뒤집힌 것이다.** 점을 5.7배 늘리면 지형이 더 안정될 것으로 예상했으나 **반대였다**(격자 상관 최저 0.9374 → 0.7661). 사전에 정한 합격선 0.9를 B안은 만족하지 못한다. 점이 많아지면 UMAP의 전역 배치가 시드마다 더 크게 흔들리고, Procrustes(회전·반사)로는 그 차이를 흡수할 수 없다. **지형을 두껍게 하려고 늘린 점이 지형을 덜 재현 가능하게 만들었다.**
- 표시 200개의 이웃 보존도 함께 나빠졌다. 940개의 다른 점이 200개 사이를 밀어낸다.

**결과** — A안(`umap_nn10_md0.1`, seed 42) 유지. 이 좌표는 `output/korea_scent_map_v1.json` 및 `korea_scent_map_v2.json` 의 좌표와 같다. 검증: 재실행한 A안 seed 42가 `results/korea_layout_comparison.csv` 의 기록값을 **소수점 6자리까지 재현**했다(trust@10 0.919423 / overlap@10 0.491000).

**Trade-off** — 표시 향수의 **절반 이상(156/200)이 정답 간선을 갖지 못한 상태로 남는다.** 이 향수들의 배치가 맞는지는 이 데이터로 판정할 수 없다. 확장으로 그 절반을 100/200까지 줄일 수 있었지만 배치 품질과 지형 재현성을 대가로 내야 했다.

그리고 **200개 점의 지형은 임계값 하위 55%에서 육지 덩어리가 1~2개다.** 글로벌 1,000개 지도에서 보이던 "대륙 4~5개"는 200개에서는 나타나지 않는다. 바다·항해 컨셉에서 섬을 여러 개 보여주려면 밀도 임계값을 올려야 하며, 그때 무엇이 드러나는지는 별도 측정 대상이다(밀도장 스윕).

> 확장안을 다시 꺼낼 조건: 국내 map-ready 향수가 크게 늘어 국내 데이터만으로 모집단을 키울 수 있게 될 때. 글로벌 향수를 섞는 방식은 이번 측정으로 기각됐다. 덤으로 UX 문제도 있었다 — 지형이 1,140개에서 나오면 국내에서 살 수 없는 향수가 만든 산이 화면에 남는다.

## D12. 국내 200개 지도의 밀도 지형 파라미터와 영역 라벨

**문제** — 프론트에 "밀도·높낮이"로 표현할 지형을 넘겨야 한다. 방법(KDE vs 히스토그램 블러), 대역폭, 바다 임계, 영역 개수, 라벨 규칙을 정해야 하는데 "보기 좋은 값"으로 고르면 근거가 없다.

**검토한 방법** — 재현: `python src/map/sweep_korea_terrain.py` → `results/korea_terrain_comparison.csv`

방법 2종 × 대역폭 5종(scott ×0.35/0.5/0.7/1.0/2.0) × 임계 8종(하위 40~80 백분위) = 80행. 영역 개수는 k=2~12를 돌려 silhouette·최대 비중·격자 우세 영역 수를 함께 봤다.

**결정**

| 항목 | 값 |
|---|---|
| 방법 | Gaussian KDE |
| 대역폭 | **scott × 0.5** |
| sea_level | 밀도 하위 **60 백분위** (uint8 **97**/255) |
| 격자 | 128 × 136 (bounds 종횡비에 맞춤, 최외곽 점 바깥 0.05 여백) |
| 영역 개수 | **k = 4** (Agglomerative average, precomputed) |
| 라벨 | 클러스터 내 coverage ≥ 0.30 인 accord 중 **(클러스터 보유율 ÷ 코퍼스 보유율) 상위 3개** |

**근거 1 — 방법 의존성은 없다.** KDE와 히스토그램+블러의 격자 상관이 같은 대역폭(×1.0)에서 **0.9841**이다. 지형은 방법이 만들어낸 것이 아니다. 대역폭이 실제 조절 변수다(×0.5는 scott과 0.9054, ×0.35는 0.7982).

4. 대역폭을 바꾸려면 격자를 재생성해야 한다. `sea_level` 만 재생성 없이 조절 가능하다.

## D13. 사람이 검토한 Brand Mapping 을 파이프라인에 반영

**문제** — 사람이 검토·확정한 브랜드 대응표 32건이 **측정만 되고 파이프라인에는 반영되지 않은 상태**였다. `BRAND_ALIASES` 에 키엘·센녹·다슈·테누이·알보우·에이딕트가 0/6, `brand_mapping_reviewed.csv` 참조 0건. 즉 `korea_map_identities.csv` 와 TOP200 은 브랜드 매핑 없이 만들어진 것이었다.

반영을 막는 구조적 문제가 있었다. `commercial_identity_id` 는 `latin_key(canonical_brand)` 를 해시 키의 첫 필드로 쓴다. `latin_key("키엘")` = `""` 이지만 `latin_key("Kiehl's")` = `"kiehls"` 라서 **브랜드를 고치면 ID 가 바뀌고 Gold Set 조인이 깨진다.**

2. **경로 B — ID 를 바꾸고 재매핑표로 흡수** (채택)

## D14. 재현 게이트를 동결 스냅샷에 재앵커링

**문제.** 평가 스크립트 5개(`matcher_baseline` `method1`~`method3` `brand_mapping`)는 모두 "기록된 수치를 다시 만들어내는가" 를 확인하는 재현 게이트를 갖고 있다. 그런데 그 게이트의 입력이 **파이프라인이 매번 덮어쓰는 산출물**이었다.

- `korea_commercial_identity_members.csv`
- `korea_candidate_families.csv`

D13 으로 파이프라인이 브랜드 매핑을 반영하게 됐으므로, 이 파일들을 갱신하는 순간 "변경 전" 이라는 개념이 사라진다. 게이트가 깨지고, 그때 할 수 있는 유일한 대응이 **기대 숫자를 실측값으로 고쳐 맞추는 것**이 된다. 그러면 안전장치가 아니라 장식이 된다.

**검토한 방법.**

| 안 | 내용 | 기각 이유 |
|---|---|---|
| A | 기대 숫자를 새 값으로 갱신 | 게이트의 목적이 소멸한다. 회귀와 정상 변화를 구분할 수 없다 |

| **C (채택)** | 반영 직전 상태를 별도 디렉터리에 동결하고 게이트를 그쪽에 고정 | 원래 경로가 자유로워지고, 게이트는 변하지 않는 기준을 갖는다 |

COMMERCIAL_PATH = SNAPSHOT_DIR / korea_commercial_identities.csv        069a30ca...

## D15. LLM 이름 표현(Method 3)을 파이프라인 채널로 추가

**문제.** Method 3 DEV 실험은 LLM 이 국내 상품명에서 복원한 라틴 이름이 retrieval 을 가장 크게 올린다고 측정했는데(R@5 0.59 → 0.79), **파이프라인은 그 표현을 전혀 쓰지 않았다.** `match_score()` 는 자체 `romanize()` 규칙 기반 음역만 썼다. 매칭률을 올릴 가장 큰 지렛대가 실험 밖에 있었다.

**검토한 방법.**

| 안 | 내용 | 판단 |

| A | `romanize` 채널을 LLM 표현으로 **교체** | 기각. 표현이 없는 identity 607건이 전부 깨진다 |

## D16. 자동 확정의 상한 측정 — 10단계 설계 전 (10a)

**문제.** 이전 Verification 설계 시도는 적대적 검토에서 기각됐다. 이유는 숫자였다 — 자동 확정 상한이 당시 Top-1 보다 낮았고, 그걸 **구현을 끝낸 뒤에** 알았다. 그래서 이번에는 규칙을 만들기 전에 증거 차원이 정답과 오확정을 실제로 갈라내는지 먼저 쟀다.

`src/matching/evaluate_confirmation_dev.py`. 9c 상태(auto 41 / correct 33 / false 8)를 재현하는 게이트를 통과한 뒤에만 분석한다. Gold Set 과 기존 산출물을 수정하지 않고 파일도 쓰지 않는다.

### 결정적 사실 — 자동 확정은 retrieval 1위와 동치다

| | 정답 후보 순위 |
|---|---|
| **정답 확정 33건** | **전부 1위** (33/33) |
| 오확정 D047 · D078 | 2위 |
| 오확정 D022 | 8위 |
| 오확정 D059 | 15위 |
| 오확정 D028 | 18위 |
| 오확정 D016 · D030 | 22위 |
| 오확정 D074 | 후보 풀 밖 (Gold 라벨 낡음) |

**따라서 자동 확정의 상한은 정확히 R@1 이다.** 현재 R@1 = 0.6393 → 39/61. 실제 정답 확정은 33/61. **격차 6건이 회수 가능분**이다(정답이 1위인데 확정되지 않은 건).

그리고 **오확정 7건 중 5건은 정답이 8~22위다. 어떤 확정 규칙으로도 정답을 만들 수 없다 — 거절만 가능하다.** 이 5건은 confirmation 문제가 아니라 **retrieval 문제**다. 사용자가 앞서 정한 "확정 못하면 지도에서 제외" 정책과 정확히 맞는다.

### 증거 차원별 분리력 (오확정 기준선 19.5%)

| 차원 | 정답 33 | 오확정 8 | 오확정 비율 | 판정 |
|---|---:|---:|---:|---|
| `phonetic_only` (모음 제거 키만으로 이김) | 4 | 4 | **50.0%** | **갈라냄** |
| `query_len <= 6` | 3 | 3 | **50.0%** | **갈라냄** |
| 기본명 변형 >= 5개 | 6 | 5 | 45.5% | 약함 |
| `score < 1.0` | 3 | 2 | 40.0% | 약함 |
| 질의 토큰 누락 >= 1 | 6 | 4 | 40.0% | 약함 |
| 농도 명시 형제 있음 | 5 | 3 | 37.5% | 약함 |
| `margin < 0.25` | 16 | 6 | 27.3% | 약함 |
| 후보가 농도 무기록 | 19 | 6 | 24.0% | 약함 |
| `name_exact` | 27 | 4 | 12.9% | **역방향** |
| `llm_exact` | 27 | 3 | 10.0% | **역방향** |
| 질의 = 기본명 그대로 | 27 | 4 | 12.9% | **역방향** |
| 2위가 질의 토큰을 더 잘 덮음 | 0 | 0 | — | **한 번도 발동 안 함** |

**기각한 가설 3개를 기록한다.**

1. **"이름 완전일치가 위험하다"는 틀렸다.** `name_exact`·`llm_exact`·`질의=기본명` 은 모두 **역방향**이다 — 완전일치한 확정이 오히려 더 정확하다(오확정 비율 10~13% vs 기준선 19.5%). 완전일치를 의심하는 규칙은 만들면 안 된다.
2. **"2위가 질의 토큰을 더 잘 덮으면 의심"은 한 번도 발동하지 않았다.** 상위 5개 안에서는 그런 후보가 없다. 정답이 8~22위에 있으니 당연하다.
3. **margin 임계값은 못 쓴다.** `margin < 0.25` 는 정답 16건 / 오확정 6건에 걸린다. 6건을 걸러내려고 16건을 버리는 교환은 성립하지 않는다.

### 기준 단계별 건수와 정확도의 교환비

| 단계 | 확정 | 정답 | 오확정 | precision | 정답 손실 |
|---|---:|---:|---:|---:|---:|
| 현재 (규칙 없음) | 41 | 33 | 8 | 0.8049 | 0 |
| **A** — 음성키 단독 확정을 취소 | 33 | 29 | 4 | 0.8788 | 4 |
| D — 기본명 변형 5개 이상이면 취소 | 30 | 27 | 3 | 0.9000 | 6 |
| **E** — A + D | **25** | **23** | **2** | **0.9200** | **10** |
| F — A + 변형 3개 이상 | 23 | 21 | 2 | 0.9130 | 12 |
| (참고) 농도 명시 형제까지 넣으면 | 27 | 24 | 3 | 0.8889 | 9 |

F 는 E 보다 precision 이 **낮다.** 즉 차원을 더 쌓는 것이 계속 이득이 되지 않는다. **E 가 정점이다.**

### 이 표를 200개 목표로 환산하면

현재 전체 파이프라인은 MATCH 304 / map_ready 279 다. DEV 의 확정 비율을 외삽하면(**외삽이다. DEV 61건 표본이고 실측이 아니다**):

| 단계 | 확정 비율 | 예상 MATCH | 예상 map_ready | 200개 달성 |
|---|---:|---:|---:|---|
| 현재 | 41/41 | 304 | 279 | 가능 (오확정 ~20%) |
| **A** | 33/41 = 80.5% | ~245 | **~225** | **가능** |
| **E** | 25/41 = 61.0% | ~185 | **~170** | **미달** |

**A 는 200 을 지키고 E 는 못 지킨다.** E 를 쓰려면 사람 검토 큐(사용자 결정: 50건 이하)가 실제로 필요해진다 — 가정이 아니라 필수 경로가 된다.

### 결정 보류 — 300건 생성 후 재측정

**아직 단계를 고르지 않았다.** LLM 이름 표현 300건이 들어오면 R@1 이 올라가고, 자동 확정 상한이 R@1 과 동치이므로 이 표 전체가 바뀐다. **최종 매칭 상태에서 골라야 한다.** 지금 고르면 중간 상태에 맞춘 기준이 된다.

## D21. 향 지도 고도화 실험 — 거리 정의는 소진됐다 (프로덕션 미변경)

**문제.** "향 지도를 고도화하자" 는 요구에 대해 무엇을 바꿀 수 있는지 실제로 재봤다. 지도의 실체는 거리 행렬이고, 좌표·군집·지형은 모두 그 아래에서 파생된다. 그래서 거리 정의부터 봤다.

**전제 정리.** 군집 방식(linkage)을 바꿔도 **좌표는 1픽셀도 움직이지 않는다.** 점 위치, 이웃 관계, trust@10, 정답 간선 거리가 전부 그대로다. 바뀌는 것은 점에 붙는 라벨과 배경 색면뿐이다. 즉 군집 변경은 고도화가 아니라 **재라벨링**이다.

**평가 집합.** 지도의 200개 안에는 정답 간선이 44쌍뿐이라 그것으로 가중치를 고르면 과적합한다. 대신 EDA 04 가 쓴 집합을 그대로 썼다 — 전체 코퍼스 131,930개에서 `reminds_me_of` 로 만든 정답 쌍, **Development 700 질의**. `verify_similarity.py` 의 함수를 import 해 절차를 재구현하지 않았다. **Holdout 300 은 두 실험 모두 건드리지 않았다.**

### 보류 — 군집 연결 방식 (`complete` linkage)

같은 맥락에서 군집도 쟀다. `average` 는 특이한 소수를 먼저 떼어내 k 를 어떻게 조절해도 "거대한 덩어리 + 4~5개짜리 조각" 구조가 남는다 — k=2 에서 이미 196:4 이고, 4·5·15개 군집이 k=10 까지 그대로 남는다.

| | 최고 조합 | silhouette | 크기 | 최소 군집 |
|---|---|---:|---|---:|
| `average` | k=7 (규칙 통과 중) | .0761 | `[70,61,27,18,15,5,4]` | 4 |
| `complete` | k=8 | **.0801** | `[51,31,30,26,19,19,14,10]` | **10** |

`complete` + k=8 이 지표가 더 좋고 4개짜리 조각이 사라진다. **그런데 적용하지 않았다.**

이유는 두 가지다. ① 이건 재라벨링이라 지도의 정확도를 개선하지 않는다. ② silhouette 0.0801 도 절대적으로는 낮아, `complete` 는 **분배를 고르게 만들 뿐 없던 경계를 만들지 않는다**(D9 에서 반지도 UMAP 이 기각된 것과 같은 원인). 영역 표현 방식이 확정된 뒤에 함께 결정하는 것이 맞다.

`CLUSTER_LINKAGE` 를 상수로 꺼내 두었다(값은 `average` 그대로). 값만 갈아끼우면 재현된다.

**Trade-off.**

1. **두 실험 모두 음의 결과다.** 하지만 "바꿀 수 있는데 안 했다" 와 "재보니 바꿀 게 없었다" 는 다르고, 후자를 근거로 남긴다. 다음에 같은 질문이 나오면 이 표를 보면 된다.
2. **Development 700 에서 골랐다.** 0.5:0.5 는 원래 EDA 가 이 집합에서 고른 값이라 이번 스윕이 그것을 재확인한 셈이고, 새로운 과적합을 추가하지는 않았다. Holdout 300 은 최종 확인용으로 남아 있다.
3. **정답 데이터 자체의 한계는 그대로다.** D10 에 기록된 `reminds_me_of` 신뢰성 점검 결과(참조값 36%의 출처와 드리프트 추정)가 이 실험들의 상한도 규정한다.

## D22. 영역 표현 방식과 향 계열 체계 확정 — C8b · Set B 9계열 (프로덕션 미변경)

**문제** — 사용자가 향 지도를 탐색할 때 "여기가 어느 향 계열 구역인가"를 읽을 수 없다. D9 이 클러스터 라벨을 UMAP target 으로 넣어 좌표 단계에서 섬을 가르려 했고 기각됐는데, 그때 남은 반론이 **"k=12 는 유사도에서 나온 라벨이라 왜곡이 컸다. 향 계열 라벨로 하면 다를 것"** 이었다. 계열 정의 자체도 확정된 적이 없다 — Phase 0 의 9계열은 `status: PROVISIONAL` 이었고, 확인된 것은 "Fragrantica 4대 그룹보다 잘 뭉친다" 뿐이었다.

이 문제에는 **동시에 만족시키기 어려운 두 요구**가 있다.

- 요구 ① 영역 이해 — 같은 계열이 뭉쳐야 "여기가 우디 구역" 이 읽힌다
- 요구 ② 유사 향수 보존 — 사람이 "닮았다"고 투표한 쌍은 가까워야 한다 (UMAP 을 쓴 원래 이유)

**두 요구가 충돌하는 크기를 먼저 쟀다.** Global 1,000 안의 신뢰 간선 872쌍 중 **412쌍(47.2%)이 계열을 넘는다.** 계열별로 뭉치게 만들면 그 412쌍이 갈라진다.

**검토한 방법** — 계열 정의 3종과 영역 표현 13조건을 **같은 좌표(UMAP seed 42)·같은 게이트**에서 비교했다. 좌표를 바꾸는 방식도 `experiments/` 안에만 만들고 `output/` 은 읽기만 했다.

- 계열 정의 — Set A(Fragrantica 설명문 계열 → 휠 4대 그룹) / Set B(사람 검토 accord 매핑 `reviewed-1` 9계열) / Set C(유사도 거리에서 계층 군집으로 자동 발견)
- 영역 표현 — C1 사후 오버레이 · C2 계열 supervised UMAP(가중 0.2/0.35/0.5/0.7) · C3 명확한 향수만 라벨(0.35/0.5) · C4 해역 고정 + 국소 UMAP · C5 휠 앵커(RadViz) · C6 앵커 + 셀 내 국소 · C7 전이 지대 렌더 · C8a 인식 축 혼합 · C8b 계열 + 인식 축 혼합

**합격 기준은 실행 전에 확정했고 결과를 보고 바꾸지 않았다.**

- **Gate A** — 계열 횡단 신뢰 쌍의 2D 근접도 ≤ baseline + 0.05 = **0.3115** (Global 1,000 · 412쌍). 마진 0.05 는 D9 의 `PASS_CROSS_MARGIN` 을 그대로 쓴 것이다
- **Gate B** — trustworthiness@10 ≥ 0.90 (Global 1,000). D9 의 `PASS_TRUST10` 과 같다

**결정** — 4가지.

1. **C8b 를 메인 Territory 후보로 선택한다.** 향해는 단순 유사 향수 검색이 아니라 향 계열을 탐색하는 지도이므로, 사람 유사성만 극대화하는 C8a 보다 영역 가독성과 사람 판단을 동시에 개선한 C8b 가 서비스 목적에 맞다.
2. **C1 은 baseline·복구용으로 보존한다.** 앞으로 적극적으로 최적화하지 않지만, C8b 의 개선 효과를 비교하고 문제가 생겼을 때 돌아갈 기준선으로 남긴다.
3. **Set B 9계열을 이후 Phase 의 기준 계열 체계로 확정한다.** Fruity 8개 문제는 계열 삭제가 아니라 Phase 4 의 균형·표현 문제로 다루고, `powdery`(보유율 47.7%)는 Family 삭제가 아니라 기여도 분석 대상으로 남긴다.
4. **C3 semi w=0.35 하나만 안전 대안으로 유지한다.** C8b 보다 영역 개선은 작지만 기존 이웃 관계를 거의 보존하므로, C8b 의 local overlap 손실이 후속 실험에서도 해결되지 않으면 이쪽을 쓴다.

| 정답 간선 근접도 (Korea) | 0.1760 | 0.1470 | 개선 |
| trust@10 (Global) | 0.9387 | 0.9191 | **−0.0196** |
| **kNN overlap@10 (Global)** | 0.3888 | 0.3146 | **−0.0742** |

C2·C4·C6 는 영역을 크게 얻고 사람 판단을 크게 잃었다. **C8b 만 둘을 동시에 개선한다.** 이유로 추정되는 것은 섞는 축(계열 프로파일)이 **같은 accord 데이터에서 나온 매끄러운 연속값**이라는 점이다 — accord 8개를 9계열로 집약한 값이므로 원래 거리와 방향이 대체로 일치하고 잡음만 줄인다. 반면 supervised UMAP 의 계열 라벨은 이산값이라 원래 거리와 충돌한다. (추정이다. 인과를 분리해 재지 않았다.)

### 근거 ④ 강제 분리는 "경계" 를 없앤다 — C3 semi 를 남긴 이유

향해가 선언한 사용자 가치 중 하나가 **취향 확장** — 경계가 새로운 계열로 넘어가는 다리가 되는 것이다. 그래서 계열 점수 margin < 0.10 인 **경계 향수 92개(46.0%)** 가 실제로 두 영역 사이에 있는지 쟀다. 각 향수에서 자기 계열 중심까지의 거리와 2위 계열 중심까지의 거리 비이고, 0.5 에 가까우면 두 영역 정중앙이다.

| 방식 | 경계 향수의 중심거리비 | 명확한 향수의 중심거리비 | 차이 |
|---|---:|---:|---:|
| C1 | 0.4555 | 0.3454 | 0.110 |
| **C8b** | 0.4336 | 0.2786 | **0.155** |
| C2 supervised w=0.35 | **0.0999** | **0.0776** | **0.022** |

**C2 에서는 경계 향수도 자기 계열 중심에 딱 붙는다.** 경계 향수와 명확한 향수의 구분이 0.022 로 사라진다 — 강제 분리는 "두 계열 사이" 라는 개념 자체를 없애고 취향 확장의 다리를 끊는다. C8b 는 반대로 차이가 0.155 로 C1(0.110)보다 커서 경계 향수가 더 확실히 경계에 놓인다.

**C7 전이 지대의 면적도 쟀다** (Korea 200, 격자 1·2위 계열 밀도 차이 기준): 0.05 미만 29.5% · 0.10 미만 42.0% · 0.20 미만 58.4%. 향수의 46.0% 가 경계 향수라는 사실과 일관된다 — 향수 하나가 accord 8개를 동시에 가지므로 계열이 애매한 것이 정상이다. 42% 는 절반 미만이지만 작지 않고, **"경계가 예외가 아니라 다수" 라는 사실을 UI 가 정직하게 표현해야 한다**는 근거로 남긴다.

**C3 semi w=0.35 를 대안으로 남긴 이유는 overlap 이다.** Global overlap@10 0.3887 로 C1(0.3888) 대비 손실이 0.0001 이고, 그러면서 Global ratio 를 4.187 → 4.808 로 올린다. C8b 의 영역 개선의 약 2/3 를 **이웃 보존 손실 없이** 얻는다. Gate A 비용은 +0.0152 로 작다.

**결과** — Phase 3 종료 게이트 통과(exit=0, 5개 방법 소수 4자리 재현 일치, 보호 산출물 8개 SHA-256 불변, method2 산문 소실 0줄). `output/` 6개 · `results/` 13개 해시 불변. 시드 5개에서 13개 방식 전부 구조 붕괴 없음(팀 결정 — 안정성은 기록 축이지 Hard Gate 가 아니다). 산출물은 `experiments/phase3a/` · `experiments/phase3b/` · `experiments/phase3/summary.html`.

**Trade-off**

1. **C8b 는 kNN overlap@10 을 0.3888 → 0.3146 으로 잃는다.** 이것이 팀 결정 ④ 가 C3 semi 를 남긴 이유이고, 후속 실험(D23)이 답할 질문이다. 게이트 안이라 합격이지만 손실은 손실이다.
2. **C8b 는 아직 한 점에서만 쟀다** (계열 0.35 · 인식 0.15). 그 점이 최적인지 확인하지 않았다.
3. **Global 지표는 seed 42 한 번만 쟀다.** 시드 5개는 Korea 200 가독성에만 적용했다. Gate A Δ 의 0.01~0.03 수준 차이를 순위 근거로 쓰기에는 부족하고, **D23 이 이것을 다시 쟀다 — 결과가 일부 달라졌다.**
4. **인식 축은 사용자 투표에 의존한다.** Korea 200 에서 계절·성별 투표가 20표 이상인 향수만 유효값을 갖고, 나머지는 중앙값으로 채웠다. 투표가 적은 신상 향수가 늘면 이 축의 신뢰도가 떨어진다.
5. **좌표를 바꾸는 결정이므로 하위 산출물(지형·영역 라벨·프론트 좌표)이 모두 영향을 받는다.** 팀 결정 ② 에 따라 지금 재생성하지 않고, TriMap-dist 재검증과 가중 스윕으로 사용자 가치가 실제로 개선되는지 먼저 확인한다.
6. **Set B 의 미해결 쟁점 2개를 그대로 안고 간다** — `powdery` 보유율 47.7%(배경에 가까운 특성을 계열로 쓴다)와 Fruity 가 Korea 200 에서 8개뿐인 것. 둘 다 Phase 4 로 넘겼다.
7. **Holdout 300 과 `gold_set_test.csv` 는 이 단계에서도 열지 않았다.**

## D23. C8b 혼합 가중 스윕과 TriMap 재검증 — 두 축은 서로 다른 일을 한다 (프로덕션 미변경)

**문제** — D22 가 C8b 를 선택했지만 두 가지가 확인되지 않은 상태였다.

1. C8b 는 **(계열 0.35 · 인식 0.15) 한 점**에서만 쟀다. 그 점이 최적인지 모른다.
2. D22 의 Global 지표는 **seed 42 한 번**이었다. Gate A Δ 의 0.01~0.03 수준 차이를 순위 근거로 쓸 수 없다.

그리고 팀 결정 ④ 가 C3 semi w=0.35 를 남긴 조건이 **"C8b 의 local overlap 손실이 후속 실험에서도 해결되지 않을 경우"** 였다. 이 실험이 그 조건을 판정한다. 팀 결정 ② 는 TriMap-dist 로 같은 후보를 다시 만들어 사용자 가치가 실제로 개선되는 경우에만 전체 파이프라인을 재생성하라고 했다.

**검토한 방법**

혼합 거리를 두 성분으로 분리해 격자로 쟀다.

```
D_blend = (1 - wf - wp)·D + wf·Df + wp·Dp

  D  = Base Similarity 거리 (0.5·accord cosine + 0.5·note IDF Jaccard)   — D1
  Df = 계열 프로파일 코사인 거리 (Set B 9계열 Family Score)                — D22 결정 ③
  Dp = 사용자 투표 인식 축 거리 (계절 따뜻함 · 성별 남성향)                 — Phase 0
```

- 격자 **24점** — `wf ∈ {0, 0.10, 0.20, 0.35, 0.50, 0.65} × wp ∈ {0, 0.075, 0.15, 0.30}`. Korea 200 은 시드 5개, Global 1,000 은 seed 42
- 격자에 기준점 3개가 들어 있다 — `(0,0)` baseline · `(0,0.15)` C8a · `(0.35,0.15)` C8b
- **투영 재검증** — 실행 전에 고정한 4지점 `(0,0) (0,0.15) (0.20,0.15) (0.35,0.15)` 에서 UMAP 과 TriMap-dist 를 같은 혼합 거리로 비교
- **시드 재확인** — 스윕을 보고 고른 최종 후보 9개를 Global 1,000 · 시드 5개에서 다시 재고, 게이트를 **시드마다 따로 적용**해 통과 개수를 셌다 (`experiments/README.md` 의 게이트 시드 규칙)

게이트 기준선(Gate A ≤ 0.3115 · Gate B ≥ 0.90)은 D22 에서 확정한 값을 그대로 썼다. **기준점 재현 확인 11건이 모두 소수 4자리로 일치한 뒤에만** 결과를 냈다 (C8a 4건 · C8b 4건 · Korea `(0,0)` = 출하 좌표 3건).

`src/map/experiment_phase3c_blend_sweep.py` · `experiment_phase3c_seed_check.py` → `experiments/phase3c/`

## D24. 후보 구조 확정과 최종 challenger 검증 — C8b 유지 (프로덕션 미변경)

**문제** — D23 이 혼합 가중 곡선을 밝힌 뒤 두 가지가 남았다. ① 후보 구조(메인·대안·baseline)를 확정하는 것, ② D23 이 발견한 `Family 0.50 + Perception 0.075` 가 실제로 C8b 보다 나은지 검증하는 것.

②가 검증이 필요한 이유는 **Gate A 여유**다. seed 42 에서 이 조합은 C8b 보다 Korea 영역 응집도가 높았지만(4.162 vs 3.913) 계열 횡단 근접도가 0.2884 로 합격선 0.3115 에 훨씬 가까웠다(C8b 0.2273). 한 번의 측정으로 "안정적으로 지킨다"고 말할 수 없었다.

**검토한 방법** — 후보 4개를 **시드 5개**에서 같은 조건으로 비교했다. **추가 가중치 탐색은 하지 않았다**(팀 결정).

| 후보 | 구성 | 역할 |
|---|---|---|
| C1 | Base 1.00 | baseline |
| Family 0.20 | Base 0.80 + Family 0.20 | 안전 대안 |
| **C8b** | Base 0.50 + Family 0.35 + Perception 0.15 | **메인** |
| Challenger | Base 0.425 + Family 0.50 + Perception 0.075 | 최종 challenger |

비교 지표는 팀이 지정한 8개다 — Gate A · Gate B · Korea normalized cohesion ratio · 자기 계열 영역 위 비율 · 영역 fragmentation · boundary perfume 유지 정도 · kNN overlap@10 · cross-family proximity. 여기에 Phase 3b 가 확정한 고정 시험지(설명 가능성)와 방향성을 **기록 축**으로 함께 냈다. 판정에는 쓰지 않았지만 빼면 회귀를 놓친다.

Gate A 여유가 좁은 후보를 가리기 위해 **메인·challenger 만 시드 15개**로 확장했다.

게이트 기준선(0.3115 / 0.90)은 Phase 3 확정값을 그대로 썼고, 판정은 `experiments/README.md` 게이트 시드 규칙을 적용했다 — **전무 DROP · 일부 통과 REVIEW · 전부 통과이고 최악값 여유가 0.01 이상일 때만 PASS.**

`src/map/experiment_phase3d_challenger.py` → `experiments/phase3d/`

**결정** — 5가지.

1. **안전 대안을 `C3 semi w=0.35` → `Family 0.20 단독`으로 교체한다.** 구성이 `Base 0.80 + Family 0.20` 뿐이라 설명하기 쉽고, 이웃 관계를 거의 훼손하지 않으면서 영역 가독성을 개선한다. `C3 semi w=0.35` 는 실험 기록만 남기고 이후 후보에서 제외한다.
2. **메인은 C8b 를 유지한다.** `Family 0.20` 으로 교체하지 않는다. 향해의 향 지도는 최근접 이웃의 정확한 복원보다 계열 영역을 읽고 탐색 방향을 정하는 경험을 우선한다.
3. **C8b 의 Perception 0.15 를 유지한다.** `Perception 0.30` 계열은 trustworthiness 를 지나치게 떨어뜨려 종료한다.
4. **Challenger 를 메인으로 승격하지 않는다.** Gate A 가 **REVIEW** 이고, 팀 우선순위 ②(경계 향수 탐색 경로)와 영역 fragmentation 에서 C8b 에 진다.
5. **최종 판단 원칙** — 향 지도는 "원래 이웃을 정확히 복원하는 지도"가 아니라 "향 계열을 공간적으로 이해하고 탐색하는 지도"다. 우선순위는 ① Territory 가독성 → ② 경계 향수의 탐색 경로 → ③ Gate A·B 안정성 → ④ overlap 손실이 작은 쪽. **영역을 우선하되 보호 지표를 통과하는 범위 안에서만 허용한다.**

5. **C8b 의 약점은 머스크·파우더리다** — 퍼짐 1.001 로 18개(9%)가 지도 전체에 흩어진다. 원인은 확인하지 못했다(가설 2개 기각). `powdery` 보유율 47.7% 쟁점과 함께 Phase 4 에서 다뤄야 한다.

## D25. Phase 4 대표 향수 구성 균형 — Hard Gate 로는 D1·D2 탈락 (프로덕션 미변경)

**문제** — 향 지도의 계열 분포가 심하게 편중돼 있다. 플로럴 61개(30.5%) · 프루티 8개(4%)이고, 프루티는 지도에서 사실상 보이지 않는다. 계열별 향수 수를 고르게 만들면 작은 계열도 탐색 가능한 Territory 가 되는가.

**Phase 3 과 성질이 다르다.** Phase 3 은 같은 200개의 위치를 바꿨고 정답 데이터(신뢰 간선 44쌍)가 불변이었다. Phase 4 는 **어떤 200개인가**를 바꾸므로 정답 데이터가 함께 바뀐다. 그리고 **Gate A·B 는 Global 1,000 에서 재는데 Phase 4 는 Global 을 건드리지 않아 게이트로 걸러지지 않는다.** 그래서 Korea 200 재선정에 맞는 보호 기준을 실행 전에 새로 확정했다.

**검토한 방법** — 좌표 방식을 **C8b 로 고정**하고(D24) 구성 3안만 비교했다. 좌표와 구성을 동시에 바꾸면 개선의 원인을 판단할 수 없다.

| 안 | 구성 | 계열 분포 (최대/최소) | 교체 |
|---|---|---|---:|
| **D0** | 현재 출하 200개 | 61 / 8 | — |
| **D1 cap30** | 계열 상한 30, 나머지는 국내 순위 | 30 / 9 | 31개 |
| **D2 최대균형** | 후보 풀 안 물채우기 배분 | 25 / 14 | 37개 |

고정한 것 — 200개 유지 · 후보 풀 286개(매칭 파이프라인 재실행 없음) · Set B 9계열(Phase 4 중 수정 금지) · 계열 내 선정 순서는 `selection_rank`(국내 인기) · 시드 5개.

**계열 내 선정을 국내 순위로 고정한 이유** — 계열이 뭉치도록 구성원을 고르면 선정을 결과 지표로 최적화하는 순환이 된다. 국내 순위는 외부 근거다.

**완전 균등은 데이터가 허용하지 않는다** — 후보 풀 286개 안에서 프루티 14개 · 아쿠아틱 15개가 상한이다. 9계열을 정확히 균등하게 하려면 지도가 126개가 된다.

**Hard Gate 는 실행 전에 확정했고 결과를 보고 바꾸지 않았다.**

| 게이트 | 기준 |
|---|---|
| **P4-A** | 국내 TOP50 유지 = 50/50 |
| **P4-B** | accord coverage ≥ 60 (D0 baseline) |
| **P4-C** | Territory 보유 계열 수 ≥ D0 **AND** 관측 응집도(raw) ≥ D0 |

Territory 보유 판정도 실행 전 확정 — 면적 ≥ 3% **AND** 최대 연속 덩어리 ≥ 60% **AND** 자기 영역 위 ≥ 0.50, 시드 5개 중 3개 이상.

Review Guardrail(자동 탈락 아님) — 신뢰 간선 ≥ 38 · 계열 횡단 ≥ 20.

`src/map/experiment_phase4_balance.py` → `experiments/phase4/`

**결정** — 3가지.

1. **Hard Gate 판정은 D1·D2 탈락, D0 유지다.** P4-C 두 조건 모두 실패했다.
2. **머스크·파우더리 문제는 개수와 무관함이 확인됐다.** 팀 §9 의 두 갈래 중 후자 — Phase 4 의 균형 문제와 분리해 **계열 정의 재검토를 별도 후속 작업**으로 넘긴다. Phase 4 중 Set B 는 수정하지 않았다.
3. **최종 구성 선택은 팀 결정으로 남긴다.** 게이트는 D0 를 가리키는데 팀 §12 우선순위 ②(작은 계열이 분명한 영역을 형성하는가)는 D2 만 달성한다. **게이트와 우선순위가 충돌하는 지점이므로 자동으로 고르지 않는다.**

### 근거 ① 지표 함정을 실행 전에 잡았고, 그것이 결론을 뒤집었다

`normalized cohesion ratio` 의 분모는 무작위 기대 `Σp_f²` 이고, **Phase 4 는 계열 분포를 조작 변수로 삼는 실험이라 분모가 오염된다.**

| 안 | 관측 응집도 (raw) | 무작위 기대 Σp² | 분모 D0 대비 | ratio |
|---|---:|---:|---:|---:|
| D0 | **0.6222 ± 0.0065** | 0.1587 | 1.000 | 3.921 ± 0.041 |
| D1 cap30 | 0.6121 ± 0.0105 | 0.1212 | 0.764 | 5.052 ± 0.086 |
| D2 최대균형 | 0.6135 ± 0.0095 | 0.1150 | 0.725 | 5.335 ± 0.083 |

**실행 전 계산** — 관측 응집도가 D0 와 똑같더라도 D2 의 ratio 는 3.921 → 5.411 로 오른다.

**실측** — D2 는 ratio 가 **+1.414 (유의, 5/5 시드)** 올랐는데 관측 응집도는 **−0.0087** 로 내려갔다. **ratio 상승분은 전부 분모에서 나왔다.**

**ratio 로 게이트를 걸었다면 D1·D2 모두 "큰 개선" 으로 통과했을 것이다.** 그래서 P4-C 를 관측값으로 바꿨다.

**같은 정규화가 계열 개수 비교(7/8/9)에서는 필수였다** — 거기서는 계열 *개수*가 변수여서 교정이었고, 여기서는 계열 *분포*가 변수여서 버그가 된다. **같은 공식이 무엇을 조작하느냐에 따라 역할이 반대가 된다.**

### 근거 ② 균형을 맞추면 Territory 보유 계열 수가 줄어든다

**앰버가 두 안 모두를 탈락시킨 원인이다.** 개수는 14 → 22 → 25 로 늘고 면적도 7.7% → 11.4% → 11.7% 로 늘지만 **최대 덩어리가 99% → 53% → 48% 로 쪼개진다.** 앰버 향수의 **95.2% 가 자기 영역 위에 있다** — 향수가 흩어진 것이 아니라 **영역이 두 조각 이상으로 갈라진** 것이다. 국내 상위 14개가 우연히 응집적이었고 후보 풀의 나머지 앰버(국내 208~282위, Tenui·TUMI·Chwi 등 11개)는 향 특성이 흩어져 있다.

### 근거 ③ 팀 §9 머스크 진단 — 개수가 원인이 아니다

| 개수 | 면적 | 최대 덩어리 | 퍼짐 | 판정 |
|---|---:|---:|---:|---|
| 18개 (D0) | 10.3% | **55%** | 1.010 | 없음 |
| 22개 (D1) | 15.0% | **83%** | 0.836 | **보유** |
| 25개 (D2) | 17.4% | **53%** | 1.093 | 없음 |

**단조롭지 않다.** 22개에서 좋아지고 25개에서 다시 나빠진다. 퍼짐도 1.010 → 0.836 → 1.093 으로 되돌아온다. **개수가 원인이라면 늘릴수록 좋아져야 한다.**

팀 §9 에 따라 Phase 4 에서 Set B taxonomy 를 수정하지 않았고, `powdery` 보유율 47.7% 와 "powdery 가 Family 보다 cross-family modifier 에 가까운지" 는 **별도 후속 작업**으로 넘긴다.

**아쿠아틱도 개수로는 해결되지 않는다.** 12 → 15개로 늘려도 면적은 6.3% → 6.8% 로 거의 그대로고 덩어리는 85% → 73% 로 나빠진다. 선정 단계에서 이미 예측됐다 — fractional 합이 6.9(D0) / 7.4(D2)로 **9계열 중 성분 총량이 가장 작다.**

### 근거 ④ argmax 와 fractional 의 결론이 갈린다 (팀 §8)

| 계열 | D0 argmax | D0 fractional | 차이 |
|---|---:|---:|---:|
| 플로럴 | **61** | **39.3** | −21.7 |
| 프루티 | **8** | **14.9** | **+6.9** |
| 아쿠아틱 | **12** | **6.9** | **−5.1** |
| 앰버 | 14 | 20.7 | +6.7 |
| 머스크 | 18 | 24.1 | +6.1 |

- **플로럴 편중은 argmax 의 산물이다** — 30.5% vs fractional 19.6%
- **프루티는 개수가 부족한 게 아니다** — argmax 8개인데 fractional 14.9. 성분을 가진 향수는 이미 있는데 1위를 못 잡는다
- **아쿠아틱은 과대표집돼 있다** — argmax 12개인데 fractional 6.9

**편중 지표도 두 기준에서 다르다.** argmax CV 는 D0 0.654 → D1 0.301 → D2 0.187 로 크게 벌어지는데, **fractional CV 는 0.366 → 0.305 → 0.279 로 D1·D2 가 거의 같다.** 팀 §8 이 정한 대로 기록한다 — **D2 의 추가 균형은 대부분 argmax 라벨 규칙에서 나온다.**

**Trade-off**

1. **프루티 판정은 임계값에 민감하다.** 면적 임계 3% 에서 D0 는 2.7% 로 간신히 미달, D2 는 3.7% 로 간신히 통과다. 임계가 2.5% 면 D0 도 통과해 D2 의 이득이 사라지고, 4% 면 D2 도 탈락한다. **임계값에 무관한 사실은 면적 +37% · 덩어리 +13%p 이고 방향은 실재한다.** 임계값은 실행 전에 확정했으나 근거가 "9계열 균등의 1/4" 이라는 논리적 기준이고 실측에서 유도한 값이 아니다.
2. **Gate P4-C 가 총합이라 상쇄가 일어난다.** 프루티 획득(+1)과 앰버 상실(−1)이 서로 지운다. "작은 계열의 획득" 에 가중을 두는 판정이면 결론이 달라질 수 있다. 이것을 팀 결정으로 남긴다.
3. **D2 는 Review Guardrail 두 값 모두 경계선이다** — 신뢰 간선 38(기준 38) · 계열 횡단 21(기준 20). Korea 200 의 정답 밀도가 낮아 자동 탈락 기준으로 쓰지 않았지만, 이보다 더 줄이면 Korea 쪽 검증이 사실상 불가능해진다.
4. **아쿠아틱은 후보 풀 안에서 해결되지 않는다.** fractional 성분 총량이 최소이고 개수를 늘리면 덩어리가 나빠진다. "아쿠아틱을 독립 Territory 로 만들지 않는다" 도 선택지로 남긴다.
5. **앰버만 상한을 건 D2 변형이 가능하다.** D2 의 유일한 Territory 손실이 앰버이므로 앰버를 14~18개로 제한하면 게이트를 통과할 수 있다. 다만 그것은 **결과를 보고 만든 안**이므로 채택하려면 게이트를 다시 확정하고 별도로 검증해야 한다.
6. **국내 인기 손실은 팀이 §12 에서 감수하기로 한 범위 안이다.** D2 에서 빠지는 37개는 전부 플로럴이고 국내 순위 최상위 61위 · 중앙 145위다. TOP50 은 하나도 빠지지 않는다. 들어오는 37개는 201~282위(중앙 235위)로 지도의 18.5% 가 국내 인기 200위 밖 향수가 된다.
7. **좌표 방식을 C8b 하나로 고정했다.** 안전 대안(Family 0.20)에서도 같은 결론인지 확인하지 않았다. 팀 §0 에 따른 것이고, 구성이 확정되면 재확인이 필요할 수 있다.

## D26. Phase 4 종결 — D0 유지, Fruity 는 구성이 아니라 표현 문제로 재정의

**문제** — D25 가 세 구성(D0 / D1 cap30 / D2 최대균형)을 비교해 Hard Gate 로는 D1·D2 가 모두 탈락한다는 결과를 냈다. 그런데 팀 §12 우선순위 ②(작은 계열이 분명한 영역을 형성하는가)는 D2 만 달성했다. 게이트와 우선순위가 충돌하는 지점을 팀이 판단해야 했다.

**결정** — 5가지.

1. **대표 향수 200개 구성은 D0 를 유지한다.** D2 는 Fruity 영역을 개선했지만 Amber Territory 상실 · 전체 Territory 감소(7.4 → 6.8) · 영역 조각 증가(16.4 → 25.0) 등 전체 지도 품질의 비용이 더 컸고 사전 Hard Gate 도 통과하지 못했다.
2. **D2 의 Amber 제한 변형은 바로 채택하지 않는다.** 먼저 결정 ⑤ 를 확인하고, 해결되지 않을 때만 Amber 를 기존 수준으로 고정한 targeted balance 실험을 별도로 진행한다.
3. **Aquatic 은 현재의 작은 독립 Territory 를 유지한다.** 데이터를 억지로 늘려 영역을 키우지 않는다. D0 에서 이미 Territory 가 존재하고(5/5 시드) 향수를 12 → 15개로 늘려도 덩어리가 85% → 73% 로 나빠졌다.
4. **Musk/Powdery 정의는 별도 후속 작업에서 재검토한다.** 계열을 삭제하지 않고, 보유율 47.7% 인 `powdery` 를 Family 결정 신호가 아니라 **modifier** 로 다루는 방식을 우선 검증한다.
5. **Fruity 문제는 향수 수가 아니라 Family 표현 방식의 문제로 우선 다룬다.** argmax 로는 8개지만 fractional 로는 14.9개분의 Fruity 신호가 이미 지도에 있으므로, Family Score 전체를 쓰는 **soft / multi-family Territory** 를 먼저 실험한다.

**근거** — D25 의 실측이다.

| | D0 | D1 cap30 | D2 최대균형 |
|---|---:|---:|---:|
| Territory 보유 계열 수 | **7.4 ± 0.5** | 6.2 ± 1.0 | 6.8 ± 0.8 |
| 영역 조각 수 | **16.4 ± 2.7** | 19.0 ± 1.4 | 25.0 ± 2.6 |
| 관측 응집도 | **0.6222** | 0.6121 | 0.6135 |
| 프루티 | 1/5 (면적 2.7%) | 0/5 (1.3%) | **5/5 (3.7%)** |
| 앰버·스파이시 | **5/5 (덩어리 99%)** | 1/5 (53%) | **0/5 (48%)** |
| 아쿠아틱 | **5/5 (덩어리 85%)** | 3/5 (75%) | 3/5 (73%) |
| Hard Gate | 기준 | **탈락** | **탈락** |

**결정 ⑤ 의 근거** — argmax 와 fractional 의 괴리다.

| 계열 | argmax | fractional | 해석 |
|---|---:|---:|---|
| 프루티 | **8** | **14.9** | 신호는 이미 있는데 1위를 못 잡는다 |
| 플로럴 | **61** | **39.3** | 편중이 argmax 라벨의 산물이다 |
| 아쿠아틱 | 12 | 6.9 | 반대로 과대표집돼 있다 |

Fruity 를 개수로 풀려면 후보 풀 상한 14개까지 끌어와야 하고 그 대가가 D2 의 전체 손실이었다. **표현 방식으로 풀면 구성을 바꾸지 않고도 같은 신호에 접근할 수 있다** — 이것이 ⑤ 의 가설이다.

**결과** — 프로덕션 미변경. Phase 4 산출물은 `experiments/phase4/` 에 있고 D0 가 현재 출하 구성 그대로이므로 `output/` 재생성이 필요 없다.

**Trade-off**

1. **D2 가 해결한 Fruity 문제는 아직 해결되지 않은 채로 남는다.** D0 에서 프루티는 면적 2.7% 로 판정 1/5 이다. 결정 ⑤ 가 실패하면 결정 ② 의 targeted balance 로 돌아와야 한다.
2. **결정 ⑤ 의 순진한 구현은 실패가 예측된다** — 아래 D27 참조. Family Score 전체를 그대로 쓰면 프루티 신호의 퍼짐이 0.147 → 0.653 으로 4.4배 나빠진다. 실험은 "soft 를 쓸까" 가 아니라 **"얼마나 soft 하게 할까"** 의 스윕이 되어야 한다.
3. **결정 ③ 은 아쿠아틱의 작은 면적(6.3%)을 받아들이는 것이다.** 사용자가 아쿠아틱 구역을 찾기 어렵다는 문제는 남는다. UI 표현(라벨·줌)으로 보완할지는 Phase 5 의 문제다.
4. **결정 ④ 를 미루는 동안 머스크는 Territory 없이 남는다.** D0 에서 머스크는 18개인데 덩어리 55% 로 판정 1/5 이다. 지도의 9% 가 구역 없는 상태로 출하된다.
5. **Phase 4 의 게이트와 우선순위 충돌은 게이트 설계의 한계를 드러냈다.** Territory 보유 계열 수를 총합으로 세면 작은 계열의 획득과 큰 계열의 상실이 상쇄된다. 이후 Phase 에서 같은 판정을 쓸 때는 **어느 계열을 얻고 잃었는지 함께 봐야 한다.**

## D27. soft / multi-family Territory — T1 이 9계열 전부를 만든다 (프로덕션 미변경)

**문제** — D26 결정 ⑤ 가 지정한 검증이다. D0 에서 프루티는 argmax 8개라 Territory 가 없는데(면적 2.7%, 판정 1/5) fractional 로는 14.9개분의 프루티 신호가 이미 지도에 있다. **향수 구성을 바꾸지 않고 Family Score 를 더 쓰는 것만으로** 프루티 Territory 를 만들 수 있는가.

**실행 전 실측으로 순진한 구현의 실패를 예측했다** — Family Score 를 전부 그대로 쓰면 프루티 신호의 퍼짐이 `0.147 → 0.653` 으로 4.4배 나빠진다. 신호가 지도에 흩어져 있기 때문이다. 그래서 "soft 를 쓸까" 가 아니라 **"얼마나 soft 하게 할까"** 를 스윕했다.

**검토한 방법** — 향수 200개(D0)와 좌표(C8b)를 고정하고 **Territory 계산 시 계열 기여 방식만** 8단계로 바꿨다. argmax 계열은 어떤 조건에서도 유지되므로 `T0w ⊆ T1 ⊆ T2 ⊆ T3 ⊆ T6` 로 hard → soft 가 단조 구간이다.

| 조건 | 기여 방식 | 평균 active Family | 총 신호량 |
|---|---|---:|---:|
| T0 | argmax 만 · 가중 없음 (Phase 4 방식 · 대조군) | 1.00 | 200.0 |
| **T0w** | argmax 만 · **원래 강도 가중** (통제 조건) | 1.00 | **80.2** |
| **T1** | 비중 ≥ 0.30 + argmax | 1.14 | 89.7 |
| T2 | 비중 ≥ 0.20 + argmax | 2.01 | 131.1 |
| T3 | 비중 ≥ 0.15 + argmax | 2.69 | 155.0 |
| T4 | 상위 2계열 | 2.00 | 128.1 |
| T5 | 상위 3계열 | 3.00 | 160.1 |
| T6 | 전 계열 (결정 ⑤ 문자 그대로) | 5.08 | 200.0 |

**팀 결정 반영** — ① threshold 이후 **재정규화하지 않고 원래 강도를 유지**한다. 임계는 향수 안 비중에 건다. ② 자기 영역 위는 **weighted coverage** 로 잰다.

```
coverage[f] = Σ_i W[i,f]·1{향수 i 가 선 칸을 f 가 차지} / Σ_i W[i,f]
```

W 가 one-hot 이면 Phase 4 의 `on_own` 과 **정확히 일치**한다 (9계열 전부 실측 확인). 따라서 판정 임계 0.50 을 재보정하지 않았다.

**T0w 는 내가 추가한 통제 조건이다.** argmax 만 쓰되 원래 강도로 가중한다 — 다계열을 전혀 쓰지 않는다. T0 → T1 의 개선에서 **'가중' 효과와 '다계열' 효과를 분리**하기 위한 것이다. 이것이 없으면 개선의 원인을 판단할 수 없다.

Hard Gate 는 실행 전에 확정했다 — **P5-A** Territory 보유 계열 수 ≥ T0(7.4) · **P5-B** 프루티 Territory 보유(시드 3/5 이상) · **P5-C** 향수당 평균 active Family ≤ 2.0(UX 제약).

`src/map/experiment_phase5_soft_territory.py` → `experiments/phase5/`

**결정** — 3가지.

1. **T1(비중 ≥ 0.30 + argmax)을 Territory 계산 방식으로 채택할 것을 제안한다.** 9계열 전부가 Territory 를 갖고(9.0 ± 0.0) 프루티 5/5 이며 영역 조각도 22.0 → 19.4 로 줄어든다. **향수를 하나도 바꾸지 않았다.**
2. **D26 결정 ② (Amber 제한 targeted balance)는 발동하지 않는다.** 조건부 실험이었고 결정 ⑤ 가 성공했다.
3. **D26 결정 ④ (powdery modifier)는 유지하되 시급성을 낮춘다.** 강도 가중만으로 머스크 Territory 가 생겼지만 taxonomy 문제 자체가 사라진 것은 아니다.

### 근거 ② 개선의 75% 는 다계열이 아니라 '강도 가중' 에서 나온다

| 구간 | 추가된 것 | Territory 변화 | 평균 active |
|---|---|---:|---:|

**T0w 는 향수당 계열이 여전히 1개다.** 바뀐 것은 **계열 소속이 흐릿한 향수의 영향력을 줄인 것**뿐이다(총 신호량 200 → 80.2). Family Score 는 향수마다 합이 정확히 1.0 이므로(실측 확인) '원래 강도' 는 곧 1위 계열의 비중이다 — Gucci Bloom 은 플로럴 0.82 로 0.82 만큼, Tenui `Bare` 는 머스크 0.22 로 0.22 만큼 기여한다. 그것만으로 프루티가 1/5 → 4/5 가 되고 머스크 Territory 가 생긴다.

**즉 D0 의 Territory 문제는 "한 향수가 한 계열만 갖는 것" 보다 "계열 소속이 약한 향수가 강한 향수와 똑같은 무게로 영역을 그린 것" 이 더 컸다.** T0w 를 통제 조건으로 넣지 않았다면 이 사실을 몰랐을 것이다.

2. **채택하면 프론트 스키마가 바뀐다.** T1 은 향수마다 1~3개 계열과 가중치가 필요한데 현재 `output/korea_scent_map_v2.json` 은 계열 1개다. 좌표는 그대로다.

4. **weighted coverage 임계 0.50 은 Phase 4 에서 그대로 가져왔다.** T0 에서 두 정의가 정확히 일치함을 확인했으므로 재보정하지 않았지만, soft 조건에서 0.50 이 적절한 바인지는 별도 근거가 없다.
5. **이 실험은 Territory 계산만 바꿨다.** 좌표 · 향수 구성 · 계열 정의는 전부 그대로다. 지도에서 점의 위치는 1픽셀도 움직이지 않는다.
6. **D25 가 프루티를 D2(구성 변경)로 풀려 했던 것과 비교하면 비용이 훨씬 작다** — D2 는 향수 37개를 교체하고 앰버 Territory 를 잃었다. T1 은 교체 0개에 Territory 를 2개 더 얻는다.

## D28. soft Territory 임계 미세 조정 — 0.24 가 0.30 보다 낫다 (프로덕션 미변경)

**문제** — D27 이 채택을 제안한 T1(임계 0.30)은 **격자의 한 점**이었다. Phase 5 는 0.30 과 0.20 두 점만 봤는데 그 사이에서 결과가 크게 갈렸다(구역 9.0 → 6.4계열). **0.22 ~ 0.28 은 한 번도 보지 않았고**, 0.30 이 최적이라는 근거도 없었다.

**검토한 방법** — **임계값 하나만** 바꿔 0.22 / 0.24 / 0.26 / 0.28 을 추가하고 기존 T0 · T0w · 0.30 · 0.20 과 함께 8조건을 같은 조건에서 비교했다. 향수 200개(D0) · 좌표 C8b · 계열 체계 Set B · 시드 5개는 Phase 5 와 동일하고, 계산 함수도 `experiment_phase5_soft_territory` 를 그대로 import 했다.

게이트와 판정 규칙은 Phase 5 확정값을 그대로 썼다 — P5-A 구역 보유 계열 수 ≥ T0(7.4) · P5-B 프루티 구역 보유 · P5-C 평균 active Family ≤ 2.0 · Territory 판정(면적 ≥ 3% · 최대 덩어리 ≥ 60% · weighted coverage ≥ 0.50, 시드 3/5).

`src/map/experiment_phase5b_threshold.py` → `experiments/phase5b/`

**결정** — 2가지.

1. **채택 임계를 0.30 → 0.24 로 바꿀 것을 제안한다.** 구역 보유 계열 수는 9.0 ± 0.0 으로 같은데 프루티 면적이 4.1% → 5.6%, 프루티 덩어리가 81% → 100%, 영역 조각 수가 19.4 → 15.2 로 모두 개선되고 **판정 여유가 훨씬 크다.**
2. **인식 축 결측 처리는 별도 실험하지 않는다.** 실측으로 문제가 없음을 확인했다(아래 근거 ③).

### 근거 ② 0.30 의 프루티는 판정선에 0.01%p 차이로 붙어 있었다

45개 시드×계열 조합의 **최악값**을 보면 결론이 뒤집힌다.

| 임계 | 면적 최저 (선 3.0%) | 덩어리 최저 (선 60%) | coverage 최저 (선 0.50) | 최악 상대 여유 |
|---|---:|---:|---:|---:|
| **0.30 (T1)** | **3.010%** (여유 +0.000) | 66% | 0.628 | **0.3%** |
| **0.24** | 3.910% (여유 +0.009) | 73% | 0.544 | **30.3%** |
| 0.22 | 3.340% | 71% | **0.483** (미달) | 실패 |

**0.30 의 가장 아슬아슬한 지점은 시드 3 의 프루티로 면적 3.01% — 판정선 3.00% 에 0.01%p 차이다.** 즉 **Phase 5 가 낸 "9계열 전부 구역" 이라는 결론은 시드 운에 걸쳐 있었다.** 시드 하나만 달라졌으면 프루티가 탈락했을 것이다.

**0.24 의 가장 아슬아슬한 지점은 아쿠아틱 면적 3.91~3.96% 로 상대 여유가 30% 다.** 프루티는 5.6% · 덩어리 100% 로 여유가 크다.

계열별로 봐도 0.24 가 대부분 개선한다 — 덩어리 비율이 시트러스 99→100% · 아쿠아틱 82→94% · 우디 94→97% · 머스크 81→94% 로 오르고, 구르망만 83→79% 로 소폭 내린다.

### 근거 ③ 인식 축 결측은 지도에 나타나지 않는다

D27 Trade-off 와 이전 기록에서 "아직 재지 않았다" 로 남겨둔 항목이다. 실험을 제안하기 전에 먼저 쟀다.

Korea 200 에서 계절 투표 20표 미만 15개 · 성별 20표 미만 21개 · **둘 다 미만 15개**다. 현재 처리는 중앙값 채움이라 **그 15개는 인식 축 공간에서 거리가 정확히 0** 이다(유효 향수끼리는 중앙 0.386). 그리고 그 15개가 `Daniel's Truth` · `Dashu` · `Sennok` · `RboW` · `Tenui` 같은 **국내 브랜드에 몰려 있다** — Fragrantica 투표가 적기 때문이다.

**그런데 지도에서는 나타나지 않는다.**

| | 결측 15개끼리 | 무작위 쌍 | 차이 |
|---|---:|---:|---:|
| 지도상 2D 거리 백분위 | 0.487 | 0.503 | −0.015 |
| **원본 유사도 거리** | **0.457** | **0.492** | **−0.035** |

인식 축과 무관한 원본 거리에서 이미 −0.035 가까웠는데 지도에서는 −0.015 로 **오히려 덜 가깝다.** 인식 축이 거리의 15% 뿐이라 나머지 85%(원본 0.50 + 계열 0.35)가 효과를 묻는다. **별도 실험을 하지 않는다.**

**결과** — 재현 확인 **12/12 PASS**. Phase 5 와 겹치는 4조건(T0 · T0w · 0.30 · 0.20)의 구역 계열 수 · 프루티 면적 · 평균 coverage 가 전부 일치했다. `output/` 6개 · `results/` 13개 SHA-256 불변. Phase 0 재현 스냅샷 PASS. Holdout 300 과 `gold_set_test.csv` 는 열지 않았다.

**Trade-off**

1. **0.24 는 coverage 를 내준다.** 평균 weighted coverage 0.808 → 0.678, 계열 최저 0.731 → 0.588(구르망). 판정선 0.50 까지 여유는 남지만 0.30 보다 좁다. 이는 다계열 배정의 필연적 결과다 — 두 계열에 기여하는 향수는 한쪽 땅 위에만 설 수 있다.
2. **다계열 향수가 27개 → 95개로 늘어난다.** 평균 계열 수 1.14 → 1.51. P5-C(≤2.0)는 통과하지만 프론트가 처리할 데이터가 늘어난다.
3. **0.24 도 격자의 한 점이다.** 0.23 · 0.25 는 재지 않았다. 다만 0.22 가 3/45 실패, 0.26 이 1/45 실패이므로 **0.24 주변이 안정 구간의 중앙**으로 보인다.
4. **선택 규칙을 스크립트가 잘못 뽑았다.** `best_by_fruity_area` 가 프루티 면적을 구역 수보다 우선해 0.22 를 골랐는데, 0.22 는 구역 8.4 ± 0.8 이고 45개 중 3개 조합이 실패한다. **P5-A(구역 수)가 1순위 지표이므로 0.24 가 맞다.** 산출물의 그 필드는 참고용이며 판정에 쓰지 않는다.
5. **여전히 T1 계열(다계열)과 T0w(1계열) 사이의 결정은 남는다.** 0.24 를 쓰면 프론트가 향수당 계열 1~3개와 가중치를 받아야 한다. T0w 는 8.6계열이지만 스키마를 바꾸지 않는다.
6. **Phase 5 의 결론을 이 실험이 보강했다.** "T1 이 9계열을 만든다" 는 맞지만 여유가 없었다. 임계 스윕을 하지 않았다면 프루티 구역이 시드에 따라 사라지는 것을 나중에 발견했을 것이다.

## D29. 프론트 전달 스키마 v3 초안 — C8b 좌표 + 9계열 Family (output/ 미변경)

## D30. Phase 6 UX 프로토타입 — 9개 라벨은 태블릿 이상에서 읽힌다 (프로덕션 미변경)

**문제** — Phase 5b 까지 9개 계열이 전부 Territory 를 갖게 됐지만, **그 라벨이 실제 화면에서 읽히는지는 데이터가 답할 수 없다.** 특히 작은 계열(아쿠아틱 4.9% · 프루티 6.2% · 구르망 6.8%)이 화면에서 찾을 수 있을 만큼 넓은지 확인해야 했다.

**검토한 방법** — v3 초안(`experiments/phase6/korea_scent_map_v3.json`)을 그대로 렌더하는 프로토타입을 만들고, 뷰포트 3개(375 모바일 · 768 태블릿 · 1280 데스크톱) × 줌 3단계에서 라벨 배치를 실제로 돌렸다. 라벨 규칙은 **앵커에 놓기 → 가장자리로 나가면 안으로 당기기 → 겹치면 밀어내기**이고, 각 단계에서 몇 개가 걸리는지 화면에 센다.

`src/map/build_phase6_ux_prototype.py` → `experiments/phase6/ux_prototype.html` · `label_report.json`

**결정** — 3가지.

1. **라벨 앵커는 그대로 쓴다.** 9개 전부 자기 계열 땅 위에 있다(9/9). 별도 배치 알고리즘이 필요 없다.
2. **모바일(375px)에는 가장자리 처리가 필요하다.** 3개가 화면 밖으로 나가 안으로 당겨진다. 라벨을 지도 안에 넣는 대신 **범례로 빼거나 줌 인 후 표시**하는 대안을 UI 단계에서 정한다.
3. **영역 크기는 문제가 아니었다.** 걱정했던 작은 계열이 375px 에서도 전부 40×40px 이상이다. 문제는 **면적이 아니라 앵커의 가장자리 근접**이다.

### 근거 ① 뷰포트별 라벨 배치 결과

| 뷰포트 | 지도 크기 | 가장자리로 당겨진 라벨 | 겹쳐서 밀어낸 라벨 | 40×40px 미만 계열 |
|---|---|---:|---:|---:|
| **375px (모바일)** | 375 × 316 | **3개** — 플로럴 · 앰버·스파이시 · 아쿠아틱 | **2개** — 앰버·스파이시 · 아쿠아틱 | 0개 |
| **768px (태블릿)** | 768 × 648 | **0개** | **0개** | 0개 |
| **1280px (데스크톱)** | 1280 × 1080 | **0개** | **0개** | 0개 |

**768px 이상에서는 9개 라벨이 전부 겹치지도 잘리지도 않는다.** 모바일에서만 3개가 걸린다.

### 근거 ② 원인은 면적이 아니라 앵커 위치다

라벨 앵커 9개는 **전부 자기 계열 땅 위에 있다**(9/9). 그런데 4개가 지도 가장자리에 붙어 있다.

| 계열 | 앵커 | 붙은 쪽 |
|---|---|---|
| 아쿠아틱 | x = 0.011 | 왼쪽 끝 |
| 플로럴 | x = 0.972 | 오른쪽 끝 |
| 우디 | y = 0.054 | 아래쪽 |
| 앰버·스파이시 | y = 0.046 | 아래쪽 |

그리고 **가장 가까운 라벨 쌍이 우디 ↔ 앰버·스파이시로 간격 0.122** 다.

| 지도 폭 | 그 간격 |
|---|---:|
| 375px | **46px** — "앰버·스파이시" 7자가 약 70px 이라 겹친다 |
| 768px | 93px |
| 1280px | 156px |

**작은 계열이 문제일 것이라는 예상은 빗나갔다.** 아쿠아틱(4.9%)은 375px 지도에서도 정사각형 환산 48px 로 라벨이 들어간다. 문제는 그 앵커가 x=0.011 로 화면 왼쪽 끝이라는 것이다.

### 근거 ③ 프로토타입이 다루는 탐색 동작

팀이 §12 에서 정의한 탐색 행동을 실제로 눌러볼 수 있게 했다.

- **"우디 영역을 탐색해봐야겠다"** — 라벨이나 범례를 누르면 그 계열만 남고 기여 향수가 가중치 순으로 나온다
- **"프루티 쪽에는 어떤 향수가 있지?"** — 프루티는 argmax 8개지만 기여 향수는 14개다. 목록에 다른 계열도 함께 표시된다
- **"다른 계열로 이동"** — `경계 향수 보기` 는 2계열 이상인 95개만 남긴다. 다리 역할을 하는 향수가 어디 있는지 보인다
- **줌 3단계** — 멀리(색면+라벨) · 중간(+점) · 가까이(+국내 24위 이내 향수 이름)

**결과** — `output/` 과 `results/` 는 읽지도 쓰지도 않았다(v3 초안만 읽는다). 브라우저에서 렌더와 뷰포트 전환을 확인했다.

**Trade-off**

1. **모바일 대안을 아직 고르지 않았다.** 라벨 3개를 지도 밖 범례로 빼거나, 줌 인했을 때만 표시하거나, 짧은 이름("앰버")을 쓰는 세 가지가 있는데 어느 쪽이 나은지는 사용자 테스트가 필요하다.
2. **밀어내기 규칙은 면적이 큰 계열을 고정한다.** 큰 계열의 라벨 위치가 더 안정적이라는 판단인데, 작은 계열이 항상 밀린다는 뜻이기도 하다. 다른 규칙(항상 아래로, 지도 중심 방향으로)은 시험하지 않았다.
3. **한 시드(42)의 좌표만 봤다.** 시드가 바뀌면 앵커가 이동하므로 가장자리 문제의 정도가 달라진다. 다만 출하는 시드 고정이므로 실사용에는 영향이 없다.
4. **실제 사용자 테스트가 아니다.** 라벨이 물리적으로 겹치는지만 쟀다. "사용자가 계열 이름을 보고 탐색 방향을 정하는가" 는 사람이 써봐야 안다.
5. **`name_ko` 가 긴 계열이 불리하다.** "머스크·파우더리"(8자) · "앰버·스파이시"(7자) · "그린·아로마틱"(7자) 가 짧은 이름보다 겹치기 쉽다. 지도용 축약 이름을 따로 둘지 결정이 필요하다.

## D31. 향 지도 인계 묶음 — DB · BE · FE 3인에게 넘길 산출물 분리 (기존 코드 미변경)

**문제** — 팀이 v3 를 실제 서비스의 향 지도로 쓰기로 정했고, 역할이 나뉘었다. DB 담당자가 테이블을 만들고, BE 가 데이터를 프론트로 내보내고, FE 가 웹에 지도를 그린다. 그런데 **넘길 것이 없었다.**

- 향 지도 JSON 을 설명하는 문서가 하나도 없다. `docs/SCHEMA.md` 는 원본 코퍼스 덤프 문서이고, `docs/FRONTEND_HANDOFF.md` 는 `FRONTEND_MAP_DATA_WORKFLOW.md` §6.5 에 명세만 있고 실행되지 않았다
- 그 §4 의 스키마 초안은 **실제 v3 와 20군데 이상 다르다** (`regions` 배열→객체, `sea_level` 백분위→uint8, `grid_height` 150→108 등)
- v3 는 `dataset_status: "DRAFT"` 로 `experiments/phase6/` 안에 있다
- **팀 ERD 에 이미 향 지도 테이블이 있는데 v3 와 맞지 않는다**

이 저장소는 개인 작업 폴더이고 팀 레포지토리는 따로 있다. 팀원이 이 폴더를 열지 않으므로, 폴더를 정리하는 것이 아니라 **저장소 없이 단독으로 읽히는 인계물**을 만들어야 했다.

**검토한 방법** — 범위를 먼저 확인받았다.

1. **폴더 재편** — 실험 스크립트 33개를 `experiments/` 아래로 옮기고 `src/` 에는 프로덕션만 남긴다. 구조는 깔끔해지지만 import 경로를 전부 고쳐야 하고, 실험 모듈이 사실상 라이브러리로 쓰이는 곳이 있어 재현성이 깨질 위험이 있다.
2. **출하 경로만 분리** — 기존 파일을 이동하지 않고 새 폴더만 추가한다. ← **채택**
3. **문서만 만들기** — 코드·폴더를 전혀 건드리지 않는다.

**결정** — 4가지.

1. **기존 파일은 이동하지 않는다.** `src/delivery/` 와 `delivery/` 만 새로 만든다.
2. **출하 빌드는 v3 를 다시 계산하지 않는다.** 검증을 통과한 JSON 하나만 읽어 형태만 바꾸는 순수 변환으로 둔다.
3. **지도 격자·해안선은 정적 파일로 분리한다.** DB 에 넣지 않는다.
4. **군집 7개(`regions`)는 인계에서 뺀다.** 향 계열 9개만 넘긴다.

그리고 문서에서 **[측정]과 [제안]을 눈에 보이게 구분한다** — 기존 `FRONTEND_MAP_DATA_WORKFLOW.md` 의 표기를 재사용했다. 우리가 넘기는 것은 데이터이고, 어떻게 담고 내보내고 그릴지는 담당자가 정한다.

```
src/delivery/build_delivery.py       v3 -> 산출물 (stdlib 만)
src/delivery/build_handoff_docs.py   담당자별 HTML 3종
src/delivery/verify_delivery.py      산출물 <-> v3 대조 + 보호 파일 SHA-256
delivery/                            밖으로 넘길 묶음
```

### 근거 ① 출하 빌드를 순수 변환으로 둔 이유

`build_korea_scent_map_v3.py` 는 **실험 스크립트 5개를 라이브러리로 import** 한다.

### 근거 ③ v3 실측에서 나온 함정 — 문서 가치의 대부분

| 함정 | 실측 |
|---|---|
| **`weight >= 0.24` 는 거짓 제약** | 임계는 0.24 지만 argmax 는 항상 포함되므로 **최솟값 0.20**. 0.24 로 걸면 적재 실패 |
| **가중치 합이 1.0 아님** | 향수별 0.20 ~ 1.00. 재정규화하지 않았다 |

| **폴리곤 고리가 안 닫힘** | 해안선 4개 중 3개가 열려 있다. 감기·구멍 플래그도 없다 |

| **`neighbors[].id` 는 `fragrantica_id`** | 2,000개 전부 200개 안에서 닫힌다 → NOT NULL FK 안전 |
| **크기** | 디스크 994 KB → compact 487 KB → **gzip 74 KB** |

빼기로 한 것 — 군집 7개(`regions`, compact 77 KB)와 파생 필드 4개(`map_identity_id` = `"fragrantica:"+id` 200/200, `display_priority` = `korea.selection_rank` 200/200, `display` 전부 `true`, `region`), 계열별 `name_ko` 중복.

### 근거 ④ 기존 검증 하나가 아무것도 검증하지 않고 있었다

`build_korea_scent_map_v3.py:393` 의 17번 검증이 항진명제다.

```python
chk("v2 파일 불변", v2b.sha256(V2_PATH) == v2b.sha256(V2_PATH))
```

같은 경로를 두 번 해싱해 비교하므로 **항상 통과하고 v2 변경을 감지할 수 없다.** 기존 파일은 손대지 않고, `verify_delivery.py` 가 기록된 해시 상수(`9dee6b6b...`)와 대조해 이 검증을 실제로 수행하게 했다. **한 줄 수정은 별도 승인 사항으로 남긴다.**

`experiments/phase6/schema_diff.json` 도 손으로 쓴 것이라 불완전하다 — v3 에서 사라진 `layout.metrics.trust_at_20`, `terrain.quantization_note` 와 `reminds_distance_percentile` 의 `null → float` 변화가 빠져 있다. 인계 문서는 이것을 근거로 쓰지 않고 실측값을 썼다.

**결과** — 검증 **31/31 통과**.

| 산출물 | 내용 |
|---|---|
| `delivery/scent_map.json` (474 KB) | 향수 200 + 계열 9 |
| `delivery/scent_map_terrain.json` (227 KB) | 격자 2장 + 해안선 |

검증 내역 — 행 수 6종, 값 왕복(좌표·계열·이웃·accord·폴리곤 전부 v3 와 일치), 좌표 범위, `weight > 0` 과 합 ≤ 1.0001, rank 1 = argmax, 격자 길이 = `grid_width × grid_height`, 참조 정합성(이웃 200개 안에서 닫힘 · 계열 키 9종 · accord 마스터 포함), 제안 DDL 의 타입·길이가 실제 값을 받는지, 빼기로 한 필드가 실제로 빠졌는지, **보호 파일 59개 SHA-256 불변**.

**프론트 문서가 검증을 겸한다** — 인계 파일 2개만으로 문서 안에서 지도를 실제로 그린다. 칠한 땅 **5,519칸** 으로 v3 의 `land_area_share` 0.3992 와 일치하고, 향수 200개와 계열 라벨 9개가 전부 나온다. 즉 "정적 파일만으로 같은 지도가 나오는가" 가 문서를 열면 확인된다.

`output/` · `results/` 는 읽지도 쓰지도 않았다. `src/map/` · `src/common/` diff 0.

**재현 게이트를 실행하지 않았다.** 매칭 파이프라인 입력을 하나도 바꾸지 않고 새 파일만 추가했다. `evaluate_brand_mapping_dev.py` 는 자기 리포트를 덮어쓰므로 실행하면 `evaluation/` 백업이 먼저 필요한데, 불필요한 위험이라 판단했다. 대신 보호 파일 59개 SHA-256 불변 확인으로 대체했다.

**Trade-off**

1. **v3 는 여전히 `DRAFT` 다.** `output/` 으로 옮기는 것은 프론트 확인 후 별도 결정이다. 그래서 인계 묶음의 데이터도 초안에서 나온 것이고, 프로덕션 반영 시 한 번 더 만들어야 한다.
2. **DDL 을 실행해 보지 않았다.** 작업 환경에 Postgres 가 없다. 타입·길이·NULL 제약이 실제 값을 받는지는 파이썬으로 대조했지만 **문법 검증은 하지 못했다.** 문서와 SQL 첫 줄에 명시했다.
3. **v3 재생성 절차를 문서로만 남겼다.** 실행 가능한 단일 스크립트로 묶지 않았다 — 121 MB 원본과 1.5 GB 캐시, EDA 산출물이 전제라 자동화의 이득이 적다고 봤다. 절차가 틀렸는지는 실제로 처음부터 돌려봐야 알 수 있고, 아직 하지 않았다.
4. **`accord → 계열` 매핑이 코드에 있다.** `experiment_phase0_family_mapping.py` 의 파이썬 dict 다. 데이터가 아니라 코드라서 DB 로 옮길 때 출처가 코드 파일이 된다. 지금 고치지 않고 문서에 적었다.
5. **`dataset_status` 리터럴이 3종이다** — 문서는 `PROVISIONAL`, v2 는 `VERIFIED`, v3 는 `DRAFT`. enum 이 선언된 적이 없다. 인계 문서에서 정의를 제안했지만 확정하지 않았다.
6. **`match.basis` 를 그대로 넘겼다.** 73종 비정형 문자열이라 BE 가 필터링에는 쓸 수 없다. 정리하지 않고 미결로 적었다.
7. **문서를 사람에게 읽혀보지 않았다.** 쉽게 읽히도록 썼지만 실제로 담당자가 이걸 보고 일할 수 있는지는 넘겨봐야 안다.
