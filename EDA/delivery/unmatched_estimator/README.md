## 5. 지연 — 병렬로 예산 안에 듭니다 [측정]

| | 문장당 | ①단계 1.5s 포함 | 8s 예산 |
|---|---:|---:|---|
| 순차 | 6.05s | 7.55s | 실사용 2.1% 초과 |
| **병렬(8)** | **1.64s** | **3.14s** | 여유 |
| **캐시 적중** | **0.01s** | 1.51s | GMS 를 안 부릅니다 |

GMS 한도는 **분당 30,000요청**(응답 헤더 `X-Ratelimit-Limit-Requests`)이라 동시 8개는
한도의 1.4% 입니다.

**병렬이 결과를 바꾸지 않는 것을 확인했습니다** — 고정 estimator 로 순차·병렬을 돌려
설문 143건 전부 일치했습니다.

## 6. 캐시 — 이게 없으면 같은 문장에 매번 다른 향수가 나옵니다

**같은 문장 · 같은 설정으로 두 번 부르면 5문장 중 5문장이 달랐습니다** [측정].

| | 캐시 없음 | **캐시 있음** |
|---|---:|---:|
| 두 번 물어 같은 결과 | 0/5 | **5/5** |
| 재시작 뒤 | — | 로그에서 복구해 같은 답 |

**캐시는 미매칭 로그 파일 자체입니다.** 별도 저장소를 만들지 않았고,
`unmatched_log.cached_estimator()` 가 원래 그렇게 설계돼 있었습니다.

**`ai/logs` 볼륨이 그대로 필요합니다.** 없으면 재시작마다 캐시가 비고 답이 달라집니다.

## 7. 무엇이 어떻게 바뀌나 — 코드

| 파일 | 바뀐 것 |
|---|---|
| `llm_stage1.py` | `estimate_accords()` · `make_estimator()` **추가**. 실패하면 `None` (기존 관례) |
| `nlr_engine.py` | `_apply_estimates()` 를 **병렬**로. `ESTIMATE_MAX_WORKERS = 8`. **실패(`None`)와 빈 판정(`[]`)을 구분** |
| `server.py` | 기동 시 `cached_estimator` 를 만들어 연결. `NLR_ESTIMATOR` 스위치 |
| `unmatched_log.py` | **실패를 캐시에 넣지 않는다** · 빈 판정을 캐시로 복구한다 |
| `data/estimator_prompt_v1.txt` | 신규 |

### `llm_accords` 의 세 가지 상태 — DB 테이블도 이걸 지켜야 합니다

```
['woody','green']   LLM 이 accord 를 골랐다
[]  (빈 배열)        LLM 이 "향이 아니다" 라고 판정했다  — 전체 표현의 38%
NULL                아직 묻지 않았다 (추정이 꺼졌거나 호출 실패)
```

**셋을 구분하지 않으면** 네트워크가 한 번 끊긴 표현이 영영 *"향이 아님"* 으로 굳거나,
38% 를 재시작마다 다시 물어봅니다. `NLR_PREDEPLOY_DECISIONS.md` 안건 ③ 후속 참고.

## 8. 확인하지 못한 것

- **실사용 정확도를 잴 수 없습니다.** 설문 143건에 정답 라벨이 없습니다(`spec.md` §8 3번).
  조건을 뽑게 됐다는 것과 그 조건이 맞다는 것은 다릅니다
- **`spec.md` 1장의 예외입니다.** *"매핑은 사전이 하고 LLM 은 구조화만 한다"* 를 어깁니다.
  근거와 한계는 `DECISIONS.md` N15 에 9개 항목으로 적었습니다
- **일관성은 캐시 안에서만 보장됩니다.** 처음 묻는 표현은 그때그때 답이 다릅니다
- **AI 서버를 여러 대로 늘리면 깨집니다.** 대마다 파일 캐시가 다릅니다. 지금은 1대입니다
- **프롬프트가 v1 한 판뿐입니다.** 비교군이 없습니다
- **E3 는 `RELAXED_OR` 를 42 → 74 로 늘립니다.** *"조건을 넓혀 찾았습니다"* 가 더 자주 뜹니다
- **초기에는 캐시가 비어 호출이 몰립니다.** 실사용 39.2% 가 조건 0개입니다
- **서버(`server.py`)를 실제로 띄워 확인하지 않았습니다.** 엔진 함수를 직접 불러 검증했습니다
