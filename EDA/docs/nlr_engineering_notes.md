# 자연어 추천 — 측정 기록과 트러블슈팅

자연어 추천 시스템을 설계하면서 실제로 발견하고 측정한 것들. 설계 결정의 근거이면서, 프로젝트 회고와 포트폴리오의 소재.

기록 형식: **문제 → 어떻게 발견했나 → 측정 → 판단 → trade-off**

| # | 제목 | 한 줄 |
|---|---|---|
| 1 | 의미는 맞는데 검색이 안 되는 매핑 | LLM이 제안한 accord의 코퍼스 지지도가 1개 |
| 2 | 한국어 "머스크"는 영어 musk가 아니다 | 매핑은 맞지만 의도한 향은 결과의 1% |
| 3 | avoid F1 0.000의 실체는 채점기였다 | 모델은 맞혔는데 표기가 달라서 0점 |
| 4 | 잘 만든 향 어휘 사전이 실사용의 12%만 덮는다 | 와인 도메인의 독립 측정치와 일치 |
| 5 | Fragrantica의 향 계열 라벨이 description 안에 있었다 | 컬럼에 없는 필드를 문장에서 복원 |
| 6 | 같은 뜻을 다르게 쓰면 다른 향수가 나온다 | 사전 없이 LLM만으로는 TOP50 겹침 중앙값 0% |
| 7 | 평가셋이 팀원 작성이라 실사용보다 쉽다 | 실사용은 2.4배 길고 조건이 2배 많다 |

## 1. 의미는 맞는데 검색이 안 되는 매핑

### 문제

자연어 표현을 Fragrantica accord로 바꾸는 실험(노트북 23)에서, LLM이 "비 온 뒤의 숲의 냄새"를 `foresty` + `earthy`로 변환했다. 사람이 봐도 타당한 매핑이었다.

### 어떻게 발견했나

변환 결과를 그대로 승인하지 않고, **각 후보 accord를 실제로 검색했을 때 향수가 몇 개 나오는지** 계산했다.

```python
S = df.accords.fillna('').map(lambda s: set(p.split(':')[0] for p in s.split('|') if p))
def and_count(targets): return sum(1 for x in S if set(targets) <= x)
```

### 측정

전체 131,930개 기준.

| accord | 보유 향수 |
|---|---:|
| `foresty` | **1** |
| `wet plaster` | 2 |
| `soapy` | 1,720 |
| `musky` | 41,154 |

파일럿 12건 전체를 검색 결과 크기로 분류한 결과:

| 판정 | 건수 |
|---|---:|
| 쓸만함 | 6 |
| 검색 결과 0~1개 | **3** (전부 `foresty` 때문) |
| 너무 넓음 (33,478개) | 1 |
| LLM이 포기 | 2 |

accord 92개 중 보유 향수가 1,000개 미만인 것이 **36개**, 10개 미만인 것이 **11개**였다.

### 판단

**"의미가 맞는가"만으로 매핑 품질을 판정하면 이 실패를 놓친다.** Domain Lexicon 항목마다 `corpus_support`(해당 accord를 가진 향수 수)를 필수 컬럼으로 두기로 했다.

이 정보는 **LLM이 구조적으로 알 수 없다.** `foresty`가 우리 데이터에 몇 개인지는 세상 지식이 아니라 우리 데이터 안에만 있는 사실이라, 모델을 키우거나 프롬프트를 고쳐서 해결되지 않는다. 렉시콘이 LLM보다 확실히 나은 지점이 바로 여기다.

### Trade-off

- 렉시콘 항목을 추가할 때마다 코퍼스 집계를 다시 돌려야 한다 → 스크립트로 자동화
- 지지도가 낮다고 항목을 지우면 의미적으로 정확한 표현을 잃는다 → 지우지 않고 값만 기록하고, 검색 단계에서 판단

## 2. 한국어 "머스크"는 영어 musk가 아니다

### 문제

`머스크향` → `musky`는 외래어 그대로라 안전해 보이는 매핑이다. 실제로 LLM도 이렇게 변환한다.

### 어떻게 발견했나

한국어 향수 커뮤니티·커머스 문서를 조사하다가, 한국에서 "머스크"가 사실상 **화이트머스크**(세탁·비누 느낌)를 가리킨다는 지적을 발견했다. Fragrantica의 `musky`는 애니멀릭까지 포괄한다.

주장으로 끝내지 않고 코퍼스에서 검증했다.

### 측정

```
musky 보유              41,154  (전체의 31.19%)
  ├ soapy 동반             400  (musky의 1.0%)     ← 한국어 화자가 뜻하는 쪽
  ├ powdery 동반         70.9%
  ├ woody 동반           59.3%
  └ animalic 동반        18.9%                     ← 반대쪽
```

역방향도 확인했다. `soapy` 보유 1,720개 중 `musky`를 같이 가진 것은 400개(23.3%)다.

### 판단

`머스크향 → musky`는 **틀린 매핑이 아니라 무효한 매핑**이다. 코퍼스의 31%를 반환하면서 의도한 의미는 그중 1%다. 변별력이 거의 없다.

렉시콘에 `caution` 컬럼을 두고 이런 내용을 명시적으로 적기로 했다.

```
머스크 → musky   caution: "단독 사용 금지. 코퍼스 31%, 의도한 화이트머스크는 그중 1.0%"
                 대안: soapy + musky + fresh 조합
```

부수적으로, "외래어는 1:1이라 쉽다"는 가정이 틀렸다는 것도 확인했다. **외래어 층도 항목마다 감사가 필요하다.**

### Trade-off

- `soapy`(1,720개)를 필수 조건으로 걸면 결과가 매우 좁아진다 → 필수/보조를 구분하고 좁으면 완화
- 한국어 사용자의 의도를 우선하면 애니멀릭 머스크를 원한 소수 사용자를 놓친다 → 문맥 조건으로 분기

## 3. avoid F1 0.000의 실체는 채점기였다

### 문제

Stage 1 평가에서 `avoid`(회피 조건) 항목의 F1이 **정확히 0.000**이었다. 36건 전부 틀렸다는 뜻이다.

처음에는 "LLM이 부정 표현의 범위를 이해하지 못한다"고 해석했고, 모델이나 프롬프트를 개선하는 방향을 검토했다.

### 어떻게 발견했나

**정확히 0.000이라는 게 이상했다.** 부분 점수가 조금이라도 나와야 자연스러운데 완전한 0이었다. 36건 전부를 눈으로 열어봤다.

### 측정

| 정답(gold) | 모델 출력(pred) | 채점 |
|---|---|---|
| 머스크 | musk | 0점 |
| 우디 | woody | 0점 |
| 파우더리 | powdery | 0점 |
| 시트러스 | citrus | 0점 |
| 바닐라 | Vanilla | 0점 |
| 복숭아, 체리 | Peach, Cherry | 0점 |
| 인위적인 | 인위적인 향 | 0점 |

**모델은 맞혔다.** "머스크는 빼줘"를 읽고 `musk`를 정확히 뽑았다. 정답이 한국어 원문 조각이고 채점이 문자열 완전 일치라서 0점이었다.

36건 중 **진짜로 못 뽑은 건 11건**, 나머지 **25건은 맞혔는데 표기가 달라서 0점**이었다.

`additional_requirements`도 같은 문제였다. 정답이 원문에서 글자 그대로 잘라낸 조각이어야 하는데 모델은 조금 길게 자르거나 다듬어 쓴다.

| 질문 | 정답 | 모델 출력 |
|---|---|---|
| 시트러스 계열의 깔끔한 향의 향수가 있어? | `깔끔한` | `깔끔한 향` |
| 비가 온 뒤의 숲같은 향을 찾고 있어 | `비가 온 뒤`, `숲` | `비가 온 뒤의 숲같은 향` |

모델 출력을 하나도 바꾸지 않고(API 재호출 0회) 채점기만 고쳐서 다시 계산했다.

처음에는 즉석 정규화로 avoid 0.507 / additional 0.569를 얻었다. 그 뒤 노트북 25에서
규칙을 층으로 나눠 사전 등록하고 정식으로 재채점했고, QA 60건으로 gold 오류까지 분리했다.
**아래가 확정 수치다.**

| 단계 | avoid | additional | 대상 |
|---|---:|---:|---:|
| ① 원래 채점 | **0.000** | 0.124 | 36 / 170 |
| ② 채점 규칙 수정 (노트북 25) | **0.493** | **0.337** | 36 / 170 |
| ③ ② + gold 오류 13건 보정 가정 | **0.653** | — | 23 |

③은 진단용 가정 계산이고 평가 데이터는 수정하지 않았다.

층별 기여 (avoid, LLM) — `L0 0.000 → L2 별칭 0.319 → L3 접미사 0.435 → L4 포함 0.493`.
`L1 구두점`은 이 데이터에서 기여가 정확히 0이었고 그대로 보고했다.

그리고 ③ 이후 남은 FN 9건 중 **8건이 번역·의역**이고 예측이 빈 것은 1건뿐이다.

```
36건 중
  13건  정답 라벨이 잘못됨        ← QA로 발견
  22건  맞혔는데 표기가 달라 0점   ← 채점기 문제
   1건  진짜로 못함
```

### 판단

**자가 틀어져 있었다.** 이 상태에서 모델을 개선하면 "정답의 자르기 습관을 흉내내도록" 튜닝하게 되고, 그건 추천 품질과 무관하다.

작업 순서를 바꿨다.

1. 채점 기준을 팀이 정한다 (한국어↔영어를 같다고 볼 것인가, 부분 일치를 어디까지 인정할 것인가)
2. 이미 준비돼 있던 Golden Set QA 60건을 판정한다 (`16_golden_set_quality_audit_candidates.csv`, 당시 0/60)
3. 저장된 LLM 응답(`15_llm_stage1_checkpoint.csv`)으로 재채점 → 진짜 baseline 확보
4. 그 다음에 개선 방향을 정한다

그리고 채점기를 고치는 데 필요한 것이 `머스크=musk`, `우디=woody` 같은 20~30줄짜리 표라는 점을 확인했다. **이건 Domain Lexicon의 가장 싼 조각이다.** 렉시콘 작업과 평가 정상화가 경쟁 관계가 아니라 같은 부품을 공유한다.

### Trade-off

- 부분 일치를 관대하게 허용하면 실제보다 좋게 나온다 → `MAX_EXCESS_TOKENS = 1`을 사전 등록하고 고정했다.
  0/1/2/3/무제한을 전부 계산했는데 무제한은 Extended Rule의 과포획 span까지 득점시켜 채택하지 않았다
- 규칙 오지정은 0건이다. QA에서 "예측이 실제로 틀렸다"고 판정한 건에 규칙이 점수를 준 사례가 없다
- 평가 데이터 자체는 수정하지 않았다 (메모리에서만 재계산)
- 남은 8건의 번역·의역을 잡으려면 별칭표를 키워야 하는데, 그건 **내가 내린 판정에 맞춰 내가 만든
  규칙을 조정하는 것**이 된다. 파라미터를 판정 전에 사전 등록한 이유가 이것이라 고치지 않았다

## 4. 잘 만든 향 어휘 사전이 실사용의 12%만 덮는다

### 문제

팀이 Michael Edwards의 14개 향 계열 기준으로 한국어 묘사 어휘 문서(2,813줄)를 만들었다. 이걸 Domain Lexicon의 기반으로 쓸 계획이었다.

### 어떻게 발견했나

문서를 그대로 신뢰하지 않고, **실제 사용자 쿼리 200개에서 뽑은 표현 346개와 대조**했다(노트북 24). 그리고 다른 도메인에 같은 측정이 있는지 찾아봤다.

### 측정

**우리 데이터:**

```
MATCHED     43  (12.4%)   문서에 명시된 표현과 일치
RELATED    105  (30.3%)   부분 문자열 또는 활용형
NOT_FOUND  198  (57.2%)   근거 없음
```

역할별로 나누면 어디가 비었는지 보인다.

| 표현 종류 | 커버리지 |
|---|---:|
| SENSORY (형용사) | 91.4% |
| DIRECT_SCENT | 77.3% |
| SOURCE (물건 이름) | 58.6% |
| IMAGE | 48.3% |
| **SCENE (장면 비유)** | **36.0%** — 정확 일치 0건 |

**외부 비교:**

Croijmans et al. (2020), *Natural Language Engineering* 26(5). 와인 전문가 리뷰 73,329건에서 실사용 용어 146개를 추출하고 고전 와인 향 사전 3종(244개 용어)과 대조 → **겹치는 것 34개, 13.9%.** 반대로 13명 전원이 쓰는데 어느 사전에도 없는 용어가 89개.

우리 12.4%와 독립적으로 관측된 13.9%가 거의 같다.

### 판단

**12%는 문서의 결함이 아니라 이런 종류 자산의 일반적 성질이다.** 그러므로 "어휘를 더 모으자"는 방향은 효과가 없다.

방향을 바꿨다.

- 문서를 키우는 대신, **실제 사용자 표현에서 출발해 역으로 채운다**
- 초기 목표를 30~50개 항목으로 잡는다 (발표된 감각 사전 대부분이 14~40개)
- 문서가 이미 잘하는 형용사(91.4%)가 아니라, **비어 있는 장면 비유(36.0%)에 집중한다**

### Trade-off

- 항목 수가 적으면 미등록 표현이 늘어난다 → 매칭 실패를 로그로 남기고 주기적으로 후보 검토
- 실제 쿼리에서 항목을 뽑으면 그 쿼리로 평가할 때 leakage가 생긴다 → `source_query_ids`를 기록해 seen/unseen 분리

## 5. Fragrantica의 향 계열 라벨이 description 안에 있었다

### 문제

한국어 묘사 문서는 **Michael Edwards의 14개 향 계열** 기준이고, 검색 데이터는 **Fragrantica accord 92개** 기준이다. 두 축을 잇는 연결이 없었다. `perfumes.csv` 59개 컬럼에 향 계열 필드는 없다.

### 어떻게 발견했나

`description` 컬럼의 실제 값을 눈으로 확인하다가 첫 문장의 패턴을 발견했다.

> "Orange Tonic by Azzaro is a **Floral Green** fragrance for women."

컬럼에는 없지만 문장에는 들어 있었다.

### 측정

대문자로 시작하는 1~4개 토큰만 받는 보수적 정규식으로 추출했다.

```python
pat = re.compile(r'\bis an? ((?:[A-Z][a-z]+ ){0,3}[A-Z][a-z]+) fragrance for (?:women|men)')
```

```
추출 성공     110,163건 = 전체의 83.50%
서로 다른 라벨      35개
기본 용어           16개

Floral 52,306 · Oriental 32,117 · Woody 29,216 · Aromatic 21,324
Fruity 18,965 · Spicy 8,846 · Musk 8,081 · Citrus 6,140 · Vanilla 5,592
Gourmand 5,112 · Chypre 4,571 · Green 3,458 · Aquatic 3,425
Fougere 3,255 · Leather 2,367 · Aldehyde 790
```

미매칭 16.5%는 파싱 실패가 아니라 group 자체가 없는 레코드였다("is a fragrance for women").

### 판단

기본 용어 16개는 Edwards의 14개 계열과 상당히 가깝다 (Chypre↔Mossy Woods, Fougere↔Aromatic Fougère, Oriental↔Amber 계열). **한국어 문서와 Fragrantica 사이의 끊긴 연결을 이을 후보 축**이 될 수 있다.

accord의 심한 편중 문제도 완화한다. 최소 라벨인 Aldehyde도 790건이라, `foresty`의 1건 같은 붕괴가 없다.

### Trade-off와 미확인 사항

- **이것이 Fragrantica의 공식 group 필드인지 문서로 확인하지 못했다.** 추정이다
- 라벨이 없는 16.5%를 어떻게 다룰지 정해야 한다
- 정규식 추출이므로 원본 데이터가 바뀌면 깨질 수 있다
- 채택하려면 위 세 가지를 먼저 정리해야 한다

## 6. 같은 뜻을 다르게 쓰면 다른 향수가 나온다

### 문제

사용자 A는 `달콤한`, 사용자 B는 `달큰한`이라고 쓴다. 같은 말이다.
둘이 다른 accord로 가면 같은 취향에 다른 향수가 추천된다.

이 질문의 답이 사전 규모를 정한다. LLM이 알아서 처리하면 사전은 작아도 되고,
못 하면 변형어 층을 사전이 담아야 한다.

### 어떻게 발견했나

사전 커버리지를 재보니 새 쿼리의 **8.2%**밖에 못 덮었다(표현 346개 중 93%가 1회만 등장).
어간으로 묶어도 15.8%였고, 묶인 12건이 전부 `깨끗하고/깨끗한/깨끗함` 같은 활용형이었다.
`달콤한/달큰한`처럼 **다른 단어**는 하나도 안 묶였다.

그래서 "표현을 나열하는 건 불가능하니 LLM에 맡기고 사전은 교정만 하자"는 가설을 세웠고,
**그 가설을 측정했다.**

### 측정 (노트북 26)

팀 문서 `perfume_14families_korean_descriptors.md` 20-B/19장에서 변형어 21쌍을 가져왔다.

설계에서 중요한 것 두 가지.

- **표준형과 변형형을 서로 다른 요청으로 보냈다.** 같은 요청에 나란히 넣으면 모델이 둘을 보고
  억지로 일관되게 답할 수 있다
- **정답을 사람이 정하지 않았다.** 두 답이 서로 같은지만 봤다

```
accord 집합 완전 일치      2/21 (10%)
1순위 accord 일치          7/21 (33%)
AND 검색 Jaccard 중앙값     0.8%
점수 검색 TOP50 겹침 중앙값   0.0%   ← 21쌍 중 15쌍이 전혀 겹치지 않음
허용 목록 밖 accord 생성     3종 (sharp, dry, rain)
```

```
달콤한 → 138개      달큰한 → 3,745개      교집합 17개
```

### 판단

**LLM 단독으로는 안 된다.** 그런데 유형별로 갈렸고, 여기가 결론이다.

| 유형 | 쌍 | 1순위 일치 | TOP50 겹침 |
|---|---:|---:|---:|
| 외래어 파생 (우디한, 바닐라리한) | 4 | **100%** | 27.0% |
| 철자 변형 (달큰한, 보송한) | 4 | **75%** | 25.0% |
| 방언·의태어 (쓸쿰한, 폭신한) | 5 | 0% | 0.8% |
| 문화적 비유 (절간 냄새, 에프킬라) | 7 | 0% | 0.3% |
| 커뮤니티 은어 (화플) | 1 | 0% | 0.0% |

님이 예로 든 `달콤한/달큰한`은 **LLM이 처리하는 쪽**이었다. 못 하는 건 한국 향수 커뮤니티
고유 어휘였다.

그런데 그 세 유형의 **실사용 빈도를 재보니 결론이 또 뒤집혔다** (→ `DECISIONS.md` N1).
설문 155건에서 은어 0.6%, 비유 0.6%, 방언은 19건 중 18건이 `달달` 하나였다.
반면 사전이 다루지 않던 **향수 전문 용어가 18.1%** 였다.

### Trade-off

- 92개 목록을 프롬프트에 명시했는데도 목록 밖 이름을 만들었다 → JSON Schema enum 강제가 필요하다
- 21쌍은 목적 표집이며 무작위 표본이 아니다. 이 비율을 전체 성능으로 일반화하지 않는다
- 단일 실행이고 모델 하나만 측정했다
- "1순위만 쓰기"가 33%로 나아 보이지만 순서가 불안정하다. `상큼한/상콤한`은 집합이 같은데
  순서가 달라 1순위로는 불일치가 됐다

## 7. 평가셋이 팀원 작성이라 실사용보다 쉽다

### 문제

Stage 1의 모든 숫자(Overall EM 6.0%, avoid F1, scent F1)가 `13_stage1_golden_set_v1_200.xlsx`
200건에서 나왔다. **이게 실사용을 대표하는가?**

### 어떻게 발견했나

Golden Set의 `Audit` 시트를 열어보다 `source_author` 컬럼을 발견했다.

```
김재성 35 · 송가연 26 · 차서영 23 · 김경린 21 · 권영민 21 · 김용석 20 · (미기재) 54
→ 팀원 6명이 작성
```

즉 **golden set은 팀원이 "사용자가 이렇게 물어보겠지" 하고 상상해 쓴 합성 데이터**이고,
`data/survey/processed/survey_nlp_queries_candidates.csv` 155건이 진짜 일반인 응답이다.

### 측정

| | golden 200 (팀원) | survey 155 (실사용자) |
|---|---:|---:|
| 평균 길이 | 30자 | **71자** |
| p90 | 42자 | **145자** |
| 최대 | 58자 | **600자** |
| 한 쿼리의 조건 수 (평균) | 1.3개 | **2.7개** |
| 조건 수 (최대) | 3개 | **20개** |
| 향수 전문 용어 | 5.5% | **18.1%** |

실사용에만 있는 것들.

```
[277자] "너는 최고급 니치 향수 전문 컨설턴트야. ... 각 향수마다 왜 골랐는지 자세히 설명해 줬으면"
        → 역할 부여 + 출력 형식 지정. 악의적 공격이 아니라 평범한 입력이다
[600자] "이 편지는 영국에서 최초로 시작되어..."
        → 행운의 편지. 향과 무관한 입력 처리가 필요하다
```

### 판단

golden set이 잘못됐다는 게 아니다. 라벨이 2명 검수로 붙어 있고 재현 가능한 비교 기준이다.
다만 **"실사용 성능 추정치"로 읽으면 안 된다.**

역할을 나눴다.

```
golden 200 (팀원 작성)  →  개발용 회귀 테스트
                          코드를 고쳤을 때 깨지는지 보는 용도.
                          여기서 나온 숫자를 "실사용 성능"이라고 부르지 않는다

survey 155 (실사용자)    →  외부 holdout
                          아직 라벨링 안 됨. 노트북 22가 12건 사용.
                          남은 143건을 라벨링하면 처음으로 실사용 성능을 잴 수 있다
```

`spec.md` §7.2에 "새 쿼리 60~100개를 수집해 동결"이라고 써뒀는데 **수집할 필요가 없다. 이미 있다.**

### Trade-off

- 실사용 성능은 지금 숫자보다 낮을 가능성이 크다. 조건이 20개인 쿼리에서 5개 필드가 전부
  정확히 맞을 확률은 조건 1개짜리보다 훨씬 낮다
- 설문 155건을 라벨링하려면 비용이 든다. 그리고 라벨링 전에 `avoid` 기준을 확정해야 한다
  (→ errata의 가이드 개정안). 안 그러면 같은 오분류가 반복된다
- 설문에도 한계가 있다. 인구통계 문항이 없어 응답자 구성을 알 수 없다
