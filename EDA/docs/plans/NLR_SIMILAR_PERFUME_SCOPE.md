# 안건 — "비슷한 향수 찾기" 를 누가 맡는가

| | |
|---|---|
| 작성 | 2026-09-17 |
| 작성자 | AI (자연어 추천) |
| 정할 사람 | **향 지도 담당 · 자연어 추천 담당(나) · 백엔드** |
| 무엇을 정하나 | 사용자가 향수 이름을 주고 *"이것과 비슷한 것"* 을 물을 때 **어느 기능이 답하는가** |
| 왜 지금 | 실사용 설문에서 **아직 추천을 못 받는 16건 중 5건**이 이 유형이다 (측정 기록 24번) |

## 0. 한 줄

**지금 두 기능 다 이 질문에 답하지 못합니다.** 자연어 추천은 향 표현만 다루고, 향 지도는
대표 200개만 다룹니다. 사용자는 그 200개 밖의 향수 이름을 말합니다.

---

## 1. 무엇이 막혀 있나 [측정]

실사용 설문 143건 중 추천을 아예 못 받는 것이 16건입니다. 그 16건을 성격으로 나눴습니다
(측정 기록 24번).

```
내가 쓰는 향수와 비슷한 것      5건    ← 이 안건
나/내 이미지와 어울리는 것      4건
향이 아닌 조건                3건    가격 · 성별 · 땀 · 여름
추천 요청이 아님               2건
향 표현인데 사전에 없음         2건
```

**5건이 이렇게 생겼습니다.**

```
"내가 쓰는 향수랑 비슷한 향이 나는 다른 향수가 궁금하다"
"난 평소 클로에 EDP를 좋아하는데 비슷한 향수 추천해줘"
"향수1, 향수2, 향수3 쓰고 있는데 비슷한 느낌의 향수 추천해줘 계절감 고려해서"
"내가 자주 사용하는 모스키노 토이2 EDP ... 조금 더 저렴한 브랜드 중 이 향이랑 가장 비슷한 향"
"랄프로렌 스타일과 어울리는 향수는?"
```

막힌 것 중 가장 큰 덩어리입니다. 전체 143건 기준으로는 3.5% 입니다.

## 2. 왜 자연어 추천이 못 하나

자연어 추천의 설계는 **문장 → 향 표현 → 향 특성(accord) → 향수** 입니다.

```
"빨래 냄새 나는 향수"  ->  "빨래"  ->  soapy  ->  soapy 가 강한 향수 5개
```

그런데 `"클로에 EDP와 비슷한 향"` 에는 **향 표현이 없습니다.** 향수 이름이 있습니다.
①단계 LLM 이 뽑아낸 것도 표현이 아니라 요청 자체였습니다 [측정].

```
"난 평소 클로에 EDP를 좋아하는데 비슷한 향수 추천해줘"
    ①단계가 뽑은 것  ->  "클로에 EDP와 비슷한 향을 원함"
    사전에서 찾을 수 있는 표현이 아니다  ->  조건 0개
```

**사전을 키워도 풀리지 않습니다.** 향 표현이 아니기 때문입니다.

## 3. 왜 향 지도로도 안 되나 — 200개 문제 [측정]

향 지도가 이미 향수 사이의 유사도를 갖고 있습니다.

```
MAP/delivery/for_db/seed/perfume_map_neighbors.csv
  기준 향수      200개
  향수당 이웃     10개
  합계          2,000행
  컬럼          fragrantica_id · neighbor_fragrantica_id · similarity · rank
```

DB 에도 들어가 있습니다 — `perfume_neighbors` 테이블을 확인했습니다 [측정].

**문제는 범위입니다.**

```
지도 위 향수            200개
이웃으로 가리키는 것      199개
그중 지도 밖 향수        0개      <- 200개 바깥을 전혀 가리키지 않는다
```

**200개 안에서만 닫혀 있습니다.** 그런데 자연어 추천이 쓰는 향수는 **129,161개**입니다.

사용자가 말한 `클로에 EDP` · `모스키노 토이2 EDP` 가 그 200개에 들어 있을 가능성은
낮습니다 — 200개는 향 지도용 대표 선정이고 선정 기준이 다릅니다
(`korea_selection_rank` · `korea_selection_basis`).

> **확인했습니다 — 거의 없습니다** [측정 · 6장 1번]. `Moschino Toy 2` 는 후보 5개 중
> 0개, `Ralph Lauren` 은 116개 중 2개(`Polo`·`Polo Blue`)입니다. `Chloe` 는 엔진
> 데이터에 브랜드 자체가 잡히지 않았습니다.

## 4. 재료는 이미 다 있습니다

새 데이터를 만들 필요가 없습니다.

```
DB perfume_accords     1,000,570행    향수 129,161개 × accord 92종의 세기
                                      weight 0 < w <= 1
AI 서버 메모리          129,161 × 92 행렬 (약 162MB)
                                      nlr_engine 이 기동 때 만든다. 검색에 쓰는 것과 같은 것
```

**향수↔향수 유사도는 이 행렬의 두 행을 비교하는 것**입니다. 코사인 유사도든 다른
방식이든 계산 재료가 이미 올라가 있습니다.

향 지도가 200개에 쓴 방식이 무엇인지는 확인하지 못했습니다 [미확인]. `similarity` 값이
`0.5276` · `0.4272` 처럼 0~1 범위라 코사인으로 보이지만 문서에 적혀 있지 않습니다.
**같은 방식을 129,161개로 늘릴 수 있는지가 이 안건의 갈림길입니다.**

## 5. 갈림길 — 셋 중 하나를 정해야 합니다

### ㉠ 향 지도가 범위를 129,161개로 늘린다

향 지도가 이미 유사도 계산 방식을 갖고 있으므로 그 방식을 전체로 확장합니다.
자연어 추천은 향수 이름을 뽑아 향 지도에 넘기기만 합니다.

```
얻는 것    유사도 정의가 한 곳에만 있다. 화면(지도)과 추천이 같은 이웃을 보여준다
잃는 것    200개 × 10 = 2,000행이 129,161개 × 10 = 130만 행이 된다
          DB 적재량과 계산 비용을 향 지도 담당이 다시 판단해야 한다
          향 지도의 원래 목적(대표 200개 탐색)과 범위가 달라진다
```

### ㉡ 자연어 추천이 따로 계산한다

AI 서버가 이미 `129,161 × 92` 행렬을 메모리에 갖고 있으므로 요청이 올 때 계산합니다.
미리 저장하지 않습니다.

```
얻는 것    DB 에 130만 행을 넣지 않는다. 향 지도 범위를 안 건드린다
          AI 서버 안에서만 끝나 인계 조건이 안 바뀐다
잃는 것    **유사도 정의가 두 곳에 생긴다.** 화면의 지도 이웃과 추천의 이웃이 다를 수 있다
          같은 향수를 놓고 "비슷한 것" 이 두 답이 나오면 사용자가 혼란스럽다
          요청마다 계산한다 — 129,161개 중 상위 10개를 뽑는 비용을 재지 않았다 [미확인]
```

### ㉢ 이번 배포에서는 하지 않는다

`NO_CONDITION` 으로 두고 화면에서 유도합니다 — *"향수 이름 대신 원하는 향을
말씀해 주세요"* 같은 방식입니다.

```
얻는 것    범위 결정을 미룬다. AI·향 지도 어느 쪽도 안 바뀐다
잃는 것    막힌 16건 중 5건이 그대로 남는다
          다만 지금도 그 5건은 빈 결과다 — 나빠지는 것은 없다
```

## 6. 정하기 전에 확인할 것 — 1번은 답이 나왔습니다

### 1. 설문 향수는 지도 200개 안에 거의 없습니다 [측정 · 2026-09-17]

설문에 나온 향수를 엔진 데이터에서 찾아 200개 목록과 대조했습니다.

```
Moschino Toy 2     후보 5개 중 지도 안 0개
Chloe              엔진 데이터에 브랜드 자체가 0개

```

**㉠(향 지도가 범위를 늘린다)이 작은 일이 아니라는 뜻입니다.** 사용자가 말하는 향수가
대표 200개 밖이므로 범위 확장이 전제가 됩니다.

### ⚠ 함께 나온 것 — 향수 이름 맞추기가 생각보다 어렵습니다

`Chloe` 로 찾으니 엔진 데이터에 **0개**입니다. 실제 표기가 `Chloé` 처럼 악센트가 붙어
있을 가능성이 큽니다 [추정 — 직접 확인하지 않았습니다].

7장에서 *"향수 이름을 뽑고 DB 와 맞춰야 한다"* 고 적었는데, **맞추기 자체가 별도
문제**라는 신호입니다. 사용자는 `클로에` 라고 쓰고 데이터는 `Chloé` 입니다.

### 2. 향 지도의 `similarity` 계산 방식은 여전히 모릅니다 [미확인]

`MAP/delivery/for_db/README.md` 에 적혀 있지 않습니다. **향 지도 담당이 답해야 합니다.**
㉠은 그 방식을 늘리는 것이고 ㉡은 새로 정의하는 것입니다. 같은 방식이면 두 답이
달라지지 않습니다.

## 7. 이 안건과 별개로 필요한 것

㉠·㉡ 어느 쪽이든 **자연어 추천이 해야 하는 일이 하나 남습니다.**

```
문장에서 향수 이름을 뽑아내기
    "난 평소 클로에 EDP를 좋아하는데"  ->  브랜드 "Chloe" · 향수명 "EDP"?
    "모스키노 토이2 EDP"              ->  브랜드 "Moschino" · 향수명 "Toy 2"
```

지금 ①단계 프롬프트는 **향 표현만 뽑도록** 설계돼 있습니다. 향수 이름을 뽑으려면
프롬프트를 고쳐야 하고, 그러면 ①단계 출력 전체가 바뀝니다 — **측정 기록 17번이
프롬프트 수정의 위험을 이미 쟀습니다.**

> 같은 프롬프트로 다시 부른 것만으로 NDCG 가 `+0.0608` 움직였다.
> 이 세션에서 잰 개선들이 전부 이 폭보다 작다

그리고 뽑은 이름을 DB 의 향수와 맞추는 일이 남습니다. `클로에` → `Chloé`,
`모스키노 토이2` → `Moschino Toy 2` 처럼 **한국어 표기를 영문 향수명과 맞춰야** 합니다.

**한국어 이름은 거의 다 있습니다** [측정] — 향수 129,161개 중 129,160개(100.0%),
브랜드 7,725/7,793(99.1%)입니다. 그리고 AI 서버가 쓸 수 있도록 파일로도 만들었습니다
(아래 10장).

**그래도 맞추기는 남습니다.** 채움률이 높은 것과 사용자가 쓴 말로 찾을 수 있는 것은
다릅니다 — `Chloe` 로 찾으면 0개입니다(6장).

**즉 ㉢을 고르더라도 이 부분은 언젠가 필요합니다.** 범위가 작지 않다는 것을 함께
봐 주십시오.

## 10. 함께 나온 것 — 200개 우선 정렬은 결정만 있고 구현이 없습니다

**이 안건과 주제는 다르지만 접점이 같습니다.** 둘 다 *"향 지도 200개를 자연어 추천이
어떻게 쓰는가"* 입니다. 조사하다 발견해 여기 적습니다.

`ai/docs/nlr_api_contract.md` 50행에 이렇게 적혀 있습니다.

> | 4 | **향 지도 200개를 항상 먼저 보여준다** | 형식은 안 바뀐다. 순서만 바뀐다 (`search_rules.md`) |

「이 계약이 서 있는 결정 넷」의 네 번째입니다. 나머지 셋은 전부 실현됐습니다.

**그런데 구현이 없습니다** [측정].

```
엔진 코드         korea_selection · map_point · is_map · priority   전부 0건
엔진 데이터        perfumes_nlr.csv.gz 에 200개인지 표시하는 칸 없음
search_rules.md   계약이 이 문서를 가리키는데 "200개" 언급 0건
```

**의도적으로 미룬 것입니다.** 커밋 `4efa3bf`(2026-09-14)의 메시지가 이유를 적었습니다.

> 아직 구현하지 않은 필드는 "구현 안 됨" 으로 표시했다. `accordKo`(향 특성 92개의
> 한국어 표기)와 **`onMap`(향지도 200개 여부)**이 그것이다.

다만 `onMap` 이라는 필드명이 **저장소 어디에도 없습니다** — 커밋 메시지에만 있습니다.
`accordKo` 는 계약 문서 299행에 흔적이 남았는데 `onMap` 은 남지 않았습니다.

### ⚠ 정하기 전에 물어야 할 것

**"왜 200개를 먼저 보여주는가" 의 근거가 어디에도 없습니다.** 계약 문서에 결정만 있고
이유가 없습니다. 정렬을 바꾸는 것은 `DECISIONS.md` N9(정렬 규칙)를 다시 여는 일이라
근거 없이 하면 나중에 왜 그랬는지 아무도 모릅니다.

**이 결정을 한 사람이 이유를 말해 주십시오.**

## 11. 만든 것 — 파일 둘 (2026-09-17)

AI 서버는 DB 를 읽지 않으므로(`spec.md` 132~139행 · 아웃바운드 제한) 필요한 데이터를
파일로 만들어 두었습니다. **DB 를 읽는 선택지 대신 이 방법을 골랐습니다.**

```
ai/build_ai_inputs.py           생성 스크립트 (신규)
ai/data/map_perfume_ids.csv        200행      1.4KB    fragrantica_id
ai/data/perfume_names_ko.csv   129,160행  3,451KB    fragrantica_id · name_ko
```

원천은 둘 다 팀 저장소에 있어 DB 가 필요 없습니다.

```

```

**한국어 이름 맞추기는 `load_perfume_catalog.sql` 133~140행과 같은 규칙을 씁니다** —
영문 이름 하나에 번역이 하나로 정해지는 것만 쓰고 겹치면 버립니다. 규칙이 두 곳에
있으면 어긋나므로 스크립트 docstring 에 그 사실을 적었습니다.

### 검증 [측정]

DB 의 `perfumes.name_ko` 와 대조했습니다.

```
DB 행수 129,160 · 내 파일 129,160 · 한쪽에만 있는 것 0개 · 값이 다른 것 3개
```

그 3개는 **DB 가 낡은 것**이었습니다. `perfume_ko.csv` 가 오늘 `develop` pull 로
갱신됐고(`Sep 17 17:01`) DB 는 그 전에 적재됐습니다. 원천을 확인해 제 파일이 최신값을
따르는 것을 봤습니다 — 예: `Eclat d'Arpège` 가 원천·내 파일 `에클라 드 아르페주`,
DB `에클라 다르페주`.

200개 목록은 **200개가 전부 엔진 데이터에 있습니다**(없는 것 0개).

### ⚠ 같은 데이터가 한 곳 더 생겼습니다

`spec.md` §8 19번이 이미 향수 정보가 두 곳에 있는 것을 문제로 적었는데 이 파일들이
한 곳을 더 만듭니다. **원천을 복사하지 않고 스크립트로 다시 만드는 방식**을 쓴 것은
그래서입니다 — 원천이 바뀌면 다시 돌립니다. 다만 **자동으로 따라가지는 않습니다.**

### 아직 엔진이 읽지 않습니다

파일만 만들었고 `nlr_engine` 이 이 파일들을 쓰지 않습니다. 10장의 근거 질문이 풀려야
200개 우선 정렬을 구현할 수 있습니다.
