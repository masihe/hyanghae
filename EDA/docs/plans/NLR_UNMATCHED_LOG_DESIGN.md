## 왜 만드는가

**사전이 덮지 못하는 입력이 많고, 그게 얼마나 되는지 재봤다.**

```
합성 평가셋 600건    134건 (22.3%) 이 향 조건을 하나도 못 뽑음
실사용자 설문 155건   75건 (48.4%) — 실사용은 두 배 나쁘다
```

**지금은 이 실패가 사라진다.** `logger.info` 로 한 줄 찍고 끝이다.

`spec.md` §4.3 이 이미 방향을 적어뒀다.

> `LLM` 등급은 자동으로 미매칭 로그에 쌓이고, 사람 검토를 거쳐 `TEAM` 으로 승격한다.
> **시간이 지날수록 설명 가능한 비율이 올라간다. 처음부터 완벽한 사전이 필요 없다.**

**이 문서는 그 로그를 실제로 만들기 위한 설계다.**

---

## 지킬 원칙 셋 — 이걸 어기면 설계가 무너진다

### ① 사전 경로와 LLM 경로를 등급으로 구분한다

두 경로는 성질이 다르다. 같은 것처럼 다루면 안 된다.

| | 사전 경로 | LLM 경로 |
|---|---|---|
| 일관성 | 같은 뜻 → 항상 같은 결과 | **같은 뜻 → 다른 결과** |
| 근거 | 사람이 쓴 문장이 남아 있음 | 사후 설명 |
| 등급 | `VERIFIED` / `TEAM` | **`LLM`** |

> **측정 근거** — 노트북 26. 사전 없이 LLM 만 쓰면 같은 뜻의 표현 21쌍 중
> **15쌍이 점수 검색 상위 50개에서 하나도 겹치지 않았다** (겹침 중앙값 0%).
> `달콤한 → gourmand,sweet` / `달큰한 → caramel,sweet` / `달달한 → vanilla,sweet`

### ② LLM 이 쓴 "이유"는 근거가 아니라 추정 기록이다

```
사전의 rationale       "팀 문서의 생활 비유에 '햇빛에 바싹 말린 빨래'가 있다"
                       <- 매핑을 정한 이유. 사람이 판단한 뒤 쓴 것

LLM 의 이유            "따뜻한 이미지라 amber 로 추정"
                       <- 매핑한 뒤 붙인 설명. 판단 근거가 아니다
```

**칸을 나누고 이름을 다르게 둔다.** `rationale` 과 `llm_reasoning` 을 섞지 않는다.

`spec.md` §1 — *"사후에 설명을 만들 수는 있지만 그건 매핑한 이유가 아니다."*

### ③ 승격에 빈도만이 아니라 판정이 들어간다

```
3회 쌓임  =  "이 표현이 자주 나온다"      (중요도)
             "LLM 추정이 맞다" 가 아니다  (정확도)
```

승격 경로는 이렇다.

```
로그 N회 누적  →  후보로 올림  →  판정  →  사전 등재
                                 ↑
                    A/B 판정표 또는 ai_summary 배수 대조
```

**이 단계를 빼면 "LLM 이 자주 틀린 것을 사전에 박는" 결과가 된다.**

## 무엇을 기록하는가

`spec.md` §4.4 의 스키마에 판정에 필요한 칸을 더했다.

| 칸 | 예 | 왜 필요한가 |
|---|---|---|
| `raw_text` | `"밤에 쓰기 좋은 섹시한 향 추천해줘"` | 원문. **이게 있어야 문맥을 본다** |
| `structured` | `{"additional_requirements": ["섹시한"]}` | LLM 구조화 결과 |
| `unmatched_expression` | `섹시한` | 사전이 받지 못한 표현 |
| `normalized_key` | `섹시한` | 정규화 후 조회 키 |
| `llm_accords` | `["patchouli", "cinnamon"]` | LLM 추정 결과 |
| `llm_reasoning` | `"관능적 인상은 향신료·목재 계열"` | **추정 기록.** 근거가 아니다 |
| `tier` | `LLM` | 등급 |
| `result_count` | `5` | **추정이 검색까지 성공했는지** |
| `occurrence_count` | `7` | 누적. 중요도이지 정확도가 아니다 |
| `first_seen` / `last_seen` | 날짜 | 추세 |
| `status` | `new` / `reviewed` / `promoted` / `rejected` | 승격 상태 |

### `result_count` 를 꼭 넣는다

LLM 이 accord 를 추정했는데 **검색 결과가 0개**인 경우가 있다. 실제로 겪었다 —
LLM 이 `foresty` 를 골랐는데 그 accord 를 가진 향수가 **전 세계에 1개**였다.

```
result_count > 0   추정이 기능했다.        의미가 맞는지는 별개
result_count = 0   의미상 맞아도 기능 실패.  코퍼스 지지도 문제
```

**두 실패는 원인이 다르므로 구분해서 센다.** 앞엣것은 사전 확장, 뒤엣것은 accord 선택 문제다.

## 결정해야 할 것

구현 전에 정한다. 이 문서에 답을 적는다.

| | 선택지 | 메모 |
|---|---|---|
| **저장 위치** | 파일(JSONL/CSV) · DB 테이블 · 둘 다 | 서비스 인스턴스가 여럿이면 파일은 어긋난다. 지금은 1개 |
| **개인정보** | 원문을 그대로 저장할 것인가 | 사용자가 개인적 기억을 쓸 수 있다. 비회원 입력이라 식별자는 없다 |
| **집계 시점** | 매 요청마다 누적 · 배치로 집계 | `occurrence_count` 를 실시간으로 올릴지 |
| **LLM 추정 호출** | 미매칭 때마다 · 안 함 | 호출 비용과 지연이 붙는다 |
| **승격 문턱** | `spec.md` 는 3회 | 실사용 규모를 모르니 잠정 |

| 사전 자동 갱신 | **측정과 반영을 분리한다.** `DECISIONS.md` N4 의 원칙 |

## 현재 코드 상태

팀 저장소 `ai/nlr_engine.py` 에 자리가 있다.

```python
# recommend() 의 반환에 이미 들어 있는 것
{
  "status": "NO_CONDITION",                    # 조건을 못 뽑은 경우
  "conditions": { "matched_expressions": [], "source": "lexicon_only" },
  "diagnostics": { "unmatched_hint": "...", "candidate_count": 0 }
}
```

`understand()` 가 `evidence` 리스트를 만들고 각 항목에 `tier` 와 `rationale` 이 들어간다.
**LLM 추정 경로는 아직 없다.** `conditions` 인자로 받은 것을 쓸 뿐이다.
