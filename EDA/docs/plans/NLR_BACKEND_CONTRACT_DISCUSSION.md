## ⛔ 2026-09-21 정정 — **이 문서의 틀이 틀렸습니다. 협의할 것이 없어졌습니다**

작성 직후 두 가지를 다시 봤고, **둘 다 백엔드 협의 없이 갈 수 있습니다.**
자세한 것은 개인 저장소 측정 기록 36번에 있습니다.

```
②  미매칭 건은 **버그였다.** 그리고 계약을 안 바꾸고 고칠 수 있었다
    -> 목록에서 빼면 된다. 백엔드는 온 것을 그대로 넣는다
    -> **이미 고쳤다** — S15P21E203-349 (푸시됨)

①  ⑤단계는 **세 번째 길이 있었다.** 조각을 묶어 보내고 조각별로 답을 받으면
    `matched[].from` 을 유지하면서 호출도 1회가 된다
    -> **계약이 안 바뀐다.** 예비 실행에서 서식 6/6 성공
    -> 다만 "묶으면 LLM 이 덜 답한다" 는 것이 보여 설계를 다시 잡는 중이다
```

**아래 본문은 그 전에 쓴 것입니다.** 무엇을 잘못 봤는지가 남아야 해서 지웠다가
다시 쓰지 않고 이 정정만 붙입니다. **백엔드에 보내실 때는 이 상자까지 함께 보내
주시거나, 지금은 보내지 않으셔도 됩니다.**

한 가지는 그대로 유효합니다 — **미매칭 로그가 기준별로 갈린다는 것**입니다.
343 · 349 로 두 번 바뀌므로 집계하는 쪽이 알아야 합니다 (3장).

**둘 다 지금 당장 고쳐야 하는 버그가 아닙니다.** 방향만 정해 주시면 AI 쪽에서
구현하고 MR 을 올립니다.

## ① ⑤단계 LLM 을 표현마다 부를지, 문장마다 부를지

### 지금 어떻게 도나

사용자 문장을 ①단계 LLM 이 조각으로 쪼갭니다.

```
"겨울에 쓸 따뜻하고 값비싸 보이는 향"
   -> "겨울에 쓸" · "따뜻한 느낌" · "값비싸 보이는 느낌"
```

사전이 못 알아들은 조각을 **⑤단계 LLM 에게 하나씩** 물어봅니다. 조각마다 한 번입니다.

그 덕에 **어느 조각에서 나왔는지**를 적을 수 있습니다.

```json
"matched": [
  { "accord": "amber", "from": "따뜻한 느낌", "tier": "LLM" }
]
```

백엔드가 이것을 `phrase` 로 바꿔 화면에 보냅니다.

### 왜 바꾸려 하나 — **LLM 이 이미 문장에 답하고 있습니다** [측정]

⑤단계 프롬프트에 원문을 함께 주면 오탐이 줄고 커버리지가 오릅니다. 그런데 **그 이유가
"조각을 더 잘 이해해서" 가 아니었습니다.**

```
같은 문장 안에서 조각끼리 답이 얼마나 겹치나 (accord 자카드)
  지금(v1)   0.150
  v2        0.473      <- 3배가 넘는다
```

```
원문 "겨울 저녁에 쓸 클래식한 남자 향… 진한 술 향을 중심으로 따뜻하고 값비싸 보이는"
  "값비싸 보이는 느낌"   v1 []   ->   v2 [amber, whiskey, warm spicy]
```

`값비싸 보이는` 에 `whiskey` 가 붙은 것은 **그 조각의 뜻이 아니라 원문에 술이 있어서**
입니다. **문장에 답할 거면 조각마다 물어볼 이유가 없습니다.**

### 얻는 것 — GMS 호출이 1/3 이하로 줍니다 [측정]

| 평가셋 | 지금 (조각마다) | 바꾸면 (문장마다) |
|---|---:|---:|
| 설문 143 | 124회 | **51회** |
| 합성 600 | 193회 | **55회** |

GMS 크레딧에 제한이 있어 이 차이가 작지 않습니다.

### 잃는 것 — `matched[].from` 이 `null` 이 됩니다

문장 하나에 한 번 물었으니 **어느 조각을 가리킬 수가 없습니다.**

```json
"matched": [
  { "accord": "amber", "from": null, "tier": "LLM" }
]
```

### 백엔드는 안 깨집니다 [확인]

`NaturalLanguageRecommendationService.reasonsOf()` 를 읽었습니다.

```java
Map<String, List<String>> labelsByPhrase = new LinkedHashMap<>();
labelsByPhrase.computeIfAbsent(matched.from(), phrase -> new ArrayList<>());
```

`LinkedHashMap` 은 **null 키를 허용**합니다. 예외가 나지 않습니다.
**다만 근거가 한 줄로 합쳐집니다.**

```
지금    [ {phrase:"따뜻한 느낌", evidence:"앰버"},
         {phrase:"겨울에 쓸",   evidence:"우디"} ]

바뀌면  [ {phrase: null, evidence:"앰버 · 우디"} ]
```

### 계약서와 프론트는 이미 `null` 을 다룹니다 [확인]

```
ai/docs/nlr_api_contract.md
  | reasons[].phrase | string | null | 사용자가 쓴 표현. 입력어와 무관한 근거면 null |

frontend/src/features/recommend/api.ts
  { phrase: null, evidence: '가을 어울림 평가 71%' }
```

**그래서 형식 자체는 이미 허용되어 있습니다.** 바뀌는 것은 **`null` 이 나오는 빈도**와
**화면에 보이는 모양**입니다.

### 얼마나 많은 응답이 바뀌나 [측정]

⑤단계는 **사전이 조건을 하나도 못 만들었을 때만** 돕니다. 그 응답만 영향을 받습니다.

| 평가셋 | ⑤단계가 도는 문장 | 비율 |
|---|---:|---:|
| 설문 143 (실사용자 문장) | 51 | **35.7%** |
| 합성 600 | 55 | 9.2% |

⚠ **설문 쪽이 훨씬 높습니다.** 실사용자 문장이 사전에 안 걸리는 표현을 더 많이 씁니다.
화면에서 *"'○○' 때문에 추천"* 이 안 나오는 응답이 **셋 중 하나**가 될 수 있습니다.

### 정해 주셔야 하는 것

```
1  근거 줄이 합쳐지고 phrase 가 null 이 되는 것을 받아들일 수 있나
2  받아들인다면 화면에 무엇을 보여줄지   예: "AI 가 문장 전체를 보고 골랐습니다"
3  아니라면 지금대로 둔다 — 호출 절감을 포기한다
```

**[미정]** — AI 는 어느 쪽이든 구현할 수 있습니다.

### 참고 — 함께 딸린 결정이 하나 더 있는데 **그건 협의가 필요 없습니다**

⑤단계 프롬프트에 원문을 넣는 것(v2 채택) 자체는 **응답 형식을 안 바꿉니다.**
`ai/` 안의 내부 시그니처만 바뀝니다.

```
오탐        -13.0%p (표현 단위) · -13.7%p (파이프라인)
커버리지     +12.7%p · +8.0%p
NDCG       변화 없음 [-0.0071, +0.0067]
```

**이건 AI 쪽에서 판단해 진행할 수 있는 항목입니다.** 위 ①은 그 위에 얹는 별개 결정입니다.

## ② 미매칭 로그에 "이미 풀림" 표시를 넣을지

### 지금 어떻게 도나

AI 는 *"①단계 LLM 이 뽑았는데 사전이 못 받은 표현"* 을 `unmatched[]` 로 내려보냅니다.
백엔드가 `nlr_unmatched_expressions` 에 쌓고, **그 로그를 캐서 사전을 늘립니다.**

### 무엇이 문제인가

**2026-09-20 에 병합된 346 이후로 브리지가 푼 표현도 거기 남습니다.**

```
"무화과 향이 나는 여성스러운향"
   -> 브리지가 fig 로 풀어 accord 조건을 만들었다 (정상 동작)
   -> 그런데 unmatched[] 에도 "사전에 없는 표현" 으로 들어간다
```

| 평가셋 | 미매칭 표현 | 그중 이미 풀린 것 |
|---|---:|---:|
| 설문 143 | 324개 | 9개 (**2.8%**) |
| 합성 600 | 1,368개 | 168개 (**12.3%**) |

**추천 동작에는 영향이 없습니다.** 로그를 읽는 쪽이 **이미 해결된 것을 빈칸으로 봅니다.**
사전을 늘릴 우선순위를 그 로그로 정하면 10% 남짓이 헛짚은 칸입니다.

### 고치려면 — `unmatchReason` 에 값 하나

```
지금   NOT_IN_LEXICON · CONDITION_NOT_MET · NOT_CORE
추가   RESOLVED_BY_BRIDGE        <- 이름은 협의  [미정]
```

### 백엔드는 안 깨집니다 [확인]

```java
// NlrRecommendResponse.java
String unmatchReason,          // 자바 enum 이 아니라 String
```

```sql
-- V23__add_nlr_feedback_tables.sql
unmatch_reason VARCHAR(30) NOT NULL    -- CHECK 제약이 없다
```

**새 값이 와도 역직렬화도 저장도 그대로 됩니다.** 손볼 곳은 둘입니다.

```
집계 쿼리     새 값을 아는 것. "사전에 없는 표현" 을 셀 때 빼야 한다
테스트 픽스처  NlrClientTest · NlrFeedbackIntegrationTest 가 세 값만 쓴다
```

### 정해 주셔야 하는 것

```
1  값을 추가할지, 아니면 집계할 때 걸러 낼지
2  추가한다면 이름을 무엇으로 할지        RESOLVED_BY_BRIDGE / BRIDGED / ...
3  V23 의 주석(셋을 적어 둔 곳)을 고칠지  ⚠ **V23 을 직접 고치면 Flyway 체크섬이
                                     깨집니다.** 320 때 같은 실수를 했고 V24 로
                                     덧붙이는 쪽이 맞았습니다
```

## 3. 언제 하면 좋을까

**둘 다 급하지 않습니다.** 다만 시점에 얽힌 사정이 있습니다.

```
①  지금 해도 되고 나중에 해도 된다. GMS 크레딧을 아끼고 싶을 때가 적기다

②  **로그가 쌓일수록 오염이 는다.** 320 은 2026-09-18 16:41 에 배포됐고
    그때부터 nlr_* 표가 쌓이고 있다. 늦게 고칠수록 되돌아보기 어려워진다
```

### ⚠ 함께 알려 드릴 것 — 미매칭 로그가 두 기준으로 갈립니다

이건 협의 항목이 아니라 **이미 일어난 일**입니다.

```
09-18 16:41   320 배포. nlr_* 표가 쌓이기 시작
09-20         343 병합 (develop). 미매칭 판정 기준이 바뀜
              -> 합성 600 기준으로 249건이 줄어든다
아직          343 이 master 에 없다. **지금까지 쌓인 로그는 전부 옛 기준**
```

**`develop` -> `master` 릴리스 시각이 경계**입니다. 그 시각을 적어 두시면 집계할 때
두 기간을 가를 수 있습니다. 옛 기간은 **미매칭이 실제보다 많이 잡혀 있습니다.**
