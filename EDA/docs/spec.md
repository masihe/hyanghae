## 0. 이 문서의 범위

### 다루는 것

사용자가 한국어 문장으로 원하는 향을 설명하면 향수 3~5개와 각각의 추천 이유를 돌려주는
기능의 구조, 처리 흐름, 정책.

### 다루지 않는 것

- REC-12 개인화 추천, REC-13 신규 사용자 추천 — 별도 문서
- MAP-09 추천 결과 지도 표시 — 인터페이스만 언급
- API 엔드포인트 상세 명세, 프론트엔드 화면 설계
- 향 지도 좌표 생성 (MAP 폴더에서 별도 진행)

## 1. 무엇을 만드는가

사용자는 향수 이름도, `woody` 같은 데이터 용어도 모른 채 자기 말로 원하는 향을 쓴다.

> "여름에 쓸 건데 빨래 냄새 나고 이불 같은 느낌이면 좋겠어. 머스크는 빼줘."

시스템은 이 문장을 데이터가 이해하는 조건으로 바꾸고, 13만 개 중에서 3~5개를 골라,
각 향수가 **어느 조건에 어떻게 맞았는지**를 함께 보여준다.

핵심 난점은 **`빨래`와 `이불`이 Fragrantica 데이터에 없는 말**이라는 것이다.
데이터에 있는 건 `soapy`, `fresh`, `powdery` 같은 92개의 accord와 note 목록뿐이다.

### 왜 LLM에게 매핑을 맡기지 않는가

NLR-07은 *"각 향수가 자신의 입력 조건과 어떤 부분에서 일치하여 추천되었는지 확인할 수 있다"* 를
요구한다. LLM이 `달큰한 → caramel`이라고 했을 때 **왜 caramel인지 물어볼 데가 없다.**
사후에 설명을 만들 수는 있지만 그건 매핑한 이유가 아니다.

그리고 실제로 일관되지 않는다 (노트북 26).

```
달콤한 → gourmand, sweet      같은 뜻인데
달큰한 → caramel,  sweet      매번 다른 답이 나오고
달달한 → vanilla,  sweet      왜 다른지 알 수 없다
```

점수 검색 상위 50개 기준 **21쌍 중 15쌍이 하나도 겹치지 않았다.** 같은 취향을 다르게 표현한
두 사용자가 서로 다른 향수를 추천받는다.

그래서 **매핑은 사전이 하고 LLM은 구조화만 한다.**

## 2. 전체 구조

```
                    ┌──────────────────────────────────────┐
   [Frontend]       │            Spring Boot               │
       │            │                                      │
       └──POST──────▶  ① 입력 검증 · 호출량 제한            │
                    │                                      │
                    │  ②─────HTTP────▶ [Python 추천 서버]   │
                    │      조건 구조화 (LLM 1회)             │
                    │      + 정규화 + 사전 조회 (LLM 없음)    │
                    │  ◀────────────── 조건 + accord + 근거  │
                    │                                      │
                    │  ③ SQL 검색 · 점수 · 조건 완화         │
                    │      │                               │
                    │      ▼                               │
                    │  [PostgreSQL]                        │
                    │                                      │
                    │  ④ 추천 근거 계산 (규칙)               │
                    │                                      │
                    │  ⑤─────HTTP────▶ [Python 추천 서버]   │
                    │      근거 → 자연어 문장 (LLM 1회)       │
                    │  ◀────────────── 추천 이유 텍스트      │
       ┌────응답─────  ⑥ 결과 조립                          │
       ▼            └──────────────────────────────────────┘
   [Frontend]
```

**LLM 호출은 2회다.** ②의 구조화와 ⑤의 문장화뿐이고, 향 변환은 사전 조회로 처리한다.

### 왜 이 구조인가

이 기능이 하는 일은 성격이 둘로 갈린다.

**언어를 다루는 일** — LLM 호출, 한국어 형태소 분석(`우디한` → `우디`), 사전 조회.
형태소 분석은 Python 생태계가 낫다. `kiwipiepy`는 설치가 한 줄이고 불규칙 활용을 처리한다.
Java에는 동급 선택지가 없다.

**데이터를 다루는 일** — 13만 개를 accord로 거르고 점수 매기고 정렬. SQL이 잘하는 일이다.

그래서 둘을 나눈다. 대신 **Python 서버는 데이터베이스에 접근하지 않는다.**
문자열을 받아 조건과 accord 후보를 돌려주는, 거의 순수 함수에 가까운 서버다.

이 제약이 중요한 이유는, 두 서버가 같은 DB 스키마를 알고 있으면 DB 담당자가 컬럼 하나를
바꿀 때 양쪽을 고쳐야 하기 때문이다. Python이 DB를 모르면 그 위험이 사라지고,
입력→출력만 보면 되니 테스트와 실험도 쉬워진다.

**대가** — 서버가 2개가 되고 Spring↔Python 왕복이 2번 생긴다. 왕복 자체는 수십 ms 수준이다.

## 3. 처리 흐름

예시 입력을 끝까지 따라간다.

> **"여름에 쓸 건데 빨래 냄새 나고 이불 같은 느낌이면 좋겠어. 머스크는 빼줘."**

### ① 입력 검증 · 호출량 제한 (Spring)

- 길이 제한 (제안: 1,000자). **설문 실측 최대가 600자**이므로 500자는 부족하다
- 비회원은 세션 기준, 회원은 user_id 기준으로 호출량 제한
- 빈 문자열, 공백만 있는 입력 거절

호출량 제한이 필요한 이유는 비회원을 허용하기 때문이다. 구체적 수치는 팀이 정한다
(제안: 비회원 세션당 5회, 회원 시간당 30회).

### ② 조건 구조화 + 향 변환 (Python)

#### ②-a. 조건 구조화 (LLM 1회)

사람 말을 코드가 쓸 수 있는 형태로 바꾼다.

```json
{
  "scent_preference": [],
  "context":  { "season": ["summer"], "daypart": [], "gender": [] },
  "performance": { "intensity": "", "longevity": "" },
  "avoid": ["머스크"],
  "additional_requirements": ["빨래 냄새", "이불 같은 느낌"]
}
```

**이 단계는 향을 추론하지 않는다.** `빨래`와 `이불`은 원문 그대로 보존된다.

이 규칙이 있는 이유는 두 가지다. 현재 Stage 1 프롬프트(`15_stage1_llm_prompt_v1.txt`)와
200개 Golden Set이 이 정책으로 만들어져 있고, "말한 것"과 "추론한 것"이 섞이면
나중에 추천 이유를 설명할 때 근거를 구분할 수 없다.

**출력은 JSON Schema로 강제한다.** `scent_preference`의 값은 허용 accord/note enum으로 제한한다.
노트북 26에서 92개 목록을 프롬프트에 명시했는데도 `sharp`·`dry`·`rain`을 만들어냈다.

#### ②-b. 정규화 (LLM 없음)

```
NFC 정규화 → Kiwi 형태소 분석 → 표제어 추출 → 공백 제거 키
```

토큰 단위는 **명사 + 형용사 어간 + 구**다 (`NNG` + `VA` + `XR`).
명사만 뽑으면 향 관련 표현 140개 중 **46%(형용사·이미지 표현)를 잃는다.**

**Kiwi 사용자 사전은 Domain Lexicon에서 자동 생성한다.** 분석기가 `파우더리한`을 모르면
`파우더/리/한`으로 쪼개서 사전 조회가 실패한다. 두 파일을 따로 관리하면 반드시 어긋난다.

#### ②-c. 사전 조회 (LLM 없음)

```
빨래  →  soapy    core      (조건: 없음)    근거 등급 TEAM
         fresh    core      (조건: 없음)    근거 등급 TEAM

이불  →  powdery  core      (조건: 없음)    근거 등급 TEAM
         soapy    core      (조건: 없음)    근거 등급 TEAM
         musky    optional  (조건: 없음)    근거 등급 LLM
```

**`core`는 AND 필터이고 `optional`은 점수에만 기여한다.** 한 표현의 `core`는 최소 2개다
(§4.3 매핑 규칙 ①). 두 표현의 `soapy`는 같은 accord이므로 하나로 합친다.

**조건 판정도 사전이 한다.** `match_condition` 칸에 검사 규칙을 적고 코드가 평가한다.
이 쿼리의 두 표현에는 조건이 없지만, 뜻이 갈리는 표현은 사전이 갈래를 나눠 갖는다.

```
깨끗한  →  soapy + fresh   (조건: 비누·세탁·빨래·샤워·침구·이불·스킨·뽀송)
           aquatic + fresh (조건: 물·바다·여름·공기·수영·워터·시원)
```

이렇게 하면 "왜 비누가 아니라 물로 갔는가"에 답할 수 있다.

이 예시에서는

- `빨래`·`이불` 모두 조건이 없으므로 갈래 판정 없이 `soapy`, `fresh`, `powdery`
- `avoid`에 `머스크`가 있으므로 `이불`의 `musky` 후보 제외 → 남은 `core` 3개

**회피 조건이 선호 조건의 후보를 이긴다.** 이 규칙도 사전이 아니라 코드에 둔다 (모든 항목 공통).

> **이 예시가 전제하는 것 — 아직 정하지 않았다.**
> `머스크`는 사전에서 `musky`뿐 아니라 `soapy` 후보도 갖는다(한국어 드리프트, 2.15배).
> 회피가 사전 항목 전체를 쓰면 `빨래`의 `soapy`까지 지워져 선호가 통째로 사라진다.
> 위 예시는 **회피가 이름 동일성(`머스크` → `musky`)만 쓴다**고 가정했다. §8 11번.

#### ②-d. 미매칭 처리

사전에 없는 표현은 LLM이 추정하되 **등급을 `LLM`으로 기록**하고 미매칭 로그에 쌓는다.
로그에 3회 이상 쌓이면 사람이 검토해 사전으로 승격한다.

**Python 서버의 응답**

```json
{
  "conditions": { ... },
  "scent_targets": [
    { "type": "ACCORD", "name": "soapy", "weight": 1.0, "required": true,
      "from": "빨래 냄새", "tier": "TEAM", "entry_id": "kr.scene.laundry",
      "rationale": "팀 문서의 생활 비유에 '햇빛에 바싹 말린 빨래'가 있다. 비누 계열이 이 인상의 중심이다." },
    { "type": "ACCORD", "name": "fresh", "weight": 1.0, "required": true,
      "from": "빨래 냄새", "tier": "TEAM", "entry_id": "kr.scene.laundry",
      "rationale": "같은 축이 '뽀송한'을 함께 두고 있다. 마른 빨래의 가볍고 개운한 쪽이다." },
    { "type": "ACCORD", "name": "powdery", "weight": 1.0, "required": true,
      "from": "이불 같은 느낌", "tier": "TEAM", "entry_id": "kr.scene.bedding",
      "rationale": "팀 문서의 생활 비유에 '코튼 이불'이 있다. 보드라운 천의 인상이 파우더리한 질감으로 나타난다." }
  ],
  "excluded_by_avoid": [
    { "name": "musky", "from": "이불 같은 느낌", "reason": "avoid:머스크" }
  ],
  "unmatched": []
}
```

### ③ 검색 · 점수 · 조건 완화 (Spring + PostgreSQL)

**회피 조건은 하드 필터다.** `avoid`에 걸린 accord/note를 가진 향수는 `NOT EXISTS`로 제외한다.
`required: true`는 모두 만족해야 하고 `required: false`는 점수에만 기여한다.

점수는 `perfume_accords.weight`(0~100)와 target weight를 곱해 합산하고 note 매칭을 IDF 가중으로 더한다.

> **주의 — 이 점수 식은 검증되지 않았다.**
> EDA 04~09에서 검증한 Accord 0.5 / Note 0.5 결합과 Note IDF는 **향수↔향수 유사도** 실험의
> 결과다. 지금은 **쿼리→향수** 검색이므로 다른 문제다. 11번의 category score를 출발점으로 삼되
> §7에서 별도로 측정한다.

#### 정렬 — 향 조건이 정하고 인기도는 동점만 푼다

```
1순위  strength 합 내림차순      향 조건이 순위를 정한다
2순위  평가자 수 내림차순        동점일 때만 개입한다
3순위  향수 id 오름차순          완전 동점일 때의 재현성
그리고 브랜드당 최대 1개
필터   평가자 10명 미만 제외
```

**2순위를 넣기 전에는 평가자 0명짜리 향수가 1위였다.** `strength` 합만으로 정렬하니
`이불 같은 포근한 향` 의 1위가 평가자 0명 · 평점 0.0 이었다. 상위 5개에 든 평가자 0명
향수가 합성 600건에서 **249개 → 165개**, 평가자 중앙값이 **9명 → 15명** 이 됐다.

**인기도를 점수에 곱하거나 평점을 더하면 안 된다.**

| 방식 | 왜 안 되나 |
|---|---|
| `strength` 합 + 평점 가중 | 평점 5.00 인 향수 8,410개 중 **99.8%가 평가자 10명 이하**다. 평가자 1명짜리가 1위가 된다 |
| `strength` 합 × log(평가자 수) | **인기가 향 조건을 이긴다.** `이불` 검색에 `soapy=13` 인 향수가 4위로 온다 |

근거와 대안 비교는 `DECISIONS.md` N9. 브랜드 상한과 문턱 값은 **제안**이며 조정 가능하다.

**조건 완화** — 결과가 3개 미만이면 순서대로 뗀다.

| 순서 | 완화 대상 | 근거 |
|---|---|---|
| 1 | `required: false` accord 제거 | 사전이 보조 후보로 표시한 것 |
| 2 | context (계절·시간대) 제거 | 향 자체가 아닌 상황 조건 |
| 3 | performance (강도·지속력) 제거 | 명시 빈도가 낮고 데이터 신뢰도가 낮음 |
| 4 | `required: true` accord를 AND에서 OR로 | 향 조건의 강도만 낮춤 |
| 5 | 사전 추정(`LLM` 등급) accord 제거 | 근거가 약한 것부터 |
| **—** | **`avoid`는 어떤 단계에서도 완화하지 않는다** | **사용자가 명시적으로 거부한 것** |

완화가 일어나면 **어느 조건을 뗐는지 기록**하고 추천 이유에 반영한다.

> **구현 상태 (2026-09-13)** — 4·5단계만 구현돼 있다. 1~3단계는 그 조건들을 아직 검색에
> 쓰지 않아 해당 사항이 없다. 완화를 켜면 합성 600건 커버리지가 **58.3% → 77.7%** 로 오르고,
> 조건을 하나라도 뽑으면 결과가 0개인 경우가 **0건**이 된다.
>
> **대가** — 완화로 넘어간 116건(19.3%)은 5위 동점이 **중앙값 3,204개**다. 향 조건이 순위를
> 거의 정하지 못하고 평가자 수가 정한다. 응답의 `diagnostics.stage` 로 `AND` 와 `RELAXED_OR` 를
> 구분하므로 **화면에서 "조건을 넓혀 찾았다"를 반드시 알려야 한다.** 안 하면 사용자가 정밀한
> 추천으로 오해한다.

### ④ 추천 근거 계산 (Spring, 규칙)

선정된 3~5개 각각에 대해 **사실만** 계산한다. LLM은 이 단계에 없다.

```
White Cotton Hair & Body Mist (Aqua Savon)
  ├ 충족: soapy(strength 100)   ← "빨래 냄새"     [TEAM] 근거: 햇빛에 말린 빨래의 비누 계열…
  ├ 충족: powdery(strength 100) ← "이불 같은 느낌" [TEAM] 근거: 코튼 이불의 보드라운 질감…
  ├ 충족: fresh(strength 12)    ← "빨래 냄새"     [TEAM]
  ├ 회피 확인: musky 없음        ← "머스크는 빼줘"
  └ 완화된 조건: 없음
```

**이 예시의 숫자는 실측이다.** `soapy`+`fresh`+`powdery`를 모두 가진 향수가 271개,
`musky` 보유분을 뺀 뒤 **86개**가 남고 위 향수가 strength 합 212로 1위다.
**5위 동점은 2개**라 상위 5개가 제비뽑기가 되지 않는다(§4.3 매핑 규칙 ①).

### ⑤ 문장화 (Python, LLM 1회)

④의 근거를 자연스러운 한국어로 바꾼다. 3~5개를 **한 번의 호출로** 처리한다.

> 비누 향이 또렷하게 깔리고 파우더리한 질감이 갓 갠 이불 같은 인상을 만듭니다.
> 프레시 노트는 약하게 받쳐주는 정도입니다. 요청하신 머스크는 들어있지 않습니다.

**LLM에게 주는 것은 ④의 근거뿐이다.** 향수의 전체 정보를 주지 않는다.
근거에 없는 내용을 쓸 재료 자체를 주지 않는 것이 지어내기를 막는 방법이다.

**근거 등급은 문장에 노출하지 않는다.** 사용자에게 필요한 건 "왜 이 향수인가"이고,
팀에게 필요한 건 "이 매핑을 믿어도 되나"다. 두 질문이 다르므로 답도 나뉜다.

### ⑥ 결과 조립 (Spring)

향수 정보 + 추천 이유 + 완화 안내를 합쳐 응답한다. MAP-09 연동을 위해
각 향수의 `perfume_map_points` 좌표를 함께 내려준다(없으면 `null`).

### 4.3 Domain Lexicon

**현재 버전 — `EDA/data/scent_knowledge/domain_lexicon_v1_2.csv`**

| 버전 | 만든 것 | 무엇이 바뀌었나 |
|---|---|---|
| `v1` | 노트북 28 | 최초 작성. 표현 26개 / 44행 |
| `v1_1` | 노트북 31 | N4 측정 반영 — `core` → `optional` 강등 6행, `NO_MAPPING` 3표현 |
| **`v1_2`** | **노트북 39** | **§8 6번·2번 판정 — `LLM` → `TEAM` 승격 4행, 판정 근거 기록** |

**이전 버전을 덮어쓰지 않는다.** 되돌리려면 앞 버전 파일을 그대로 쓰면 된다.

CSV 파일로 관리하고 Python 서버 기동 시 메모리에 적재한다.

**파일로 두는 이유** — git에 이력이 남는다. "왜 머스크를 `musky` 단독으로 매핑하지 않기로
했는가" 같은 판단이 커밋 메시지에 기록되고 PR로 검수된다.

**DB 대신 파일이어도 안전한 이유** — 기동 시 모든 accord/note 이름이 `accords`/`notes`
테이블에 존재하는지 검사하고, 하나라도 없으면 에러를 내고 기동을 중단한다. FK와 같은 효과다.

#### 파일 스키마

| 컬럼 | 설명 |
|---|---|
| `entry_id` | 안정적인 ASCII 식별자 (`kr.pogeunhan`) |
| `expression` | 대표 한국어 표현 |
| `aliases` | 표기 변형을 `\|`로 구분 |
| `expression_type` | 24번의 10종 재사용 |
| `target_field` | `STAGE1_DIRECT` / `STAGE2_BRIDGE` / `NO_MAPPING` |
| `candidate_type` | `ACCORD` / `NOTE` / **`FIELD`** (Fragrantica 스키마 필드) |
| `candidate_name` | accord/note 이름. 마스터 테이블에 존재해야 함. `FIELD`면 스키마 필드 경로 |
| `rank` | 후보 순서 |
| `required` | `core` / `optional` |
| **`match_condition`** | **코드가 검사하는 조건.** 예: `query_contains:비누,세탁,빨래,샤워` |
| **`rationale`** | **판단 근거를 문장으로.** 사용자 설명에 그대로 쓸 수 있게 |
| **`evidence_tier`** | `VERIFIED` (외부 자료) / `TEAM` (팀 판단) / `LLM` (추정) |
| `corpus_support` | 이 accord를 가진 향수 수 (스크립트로 자동 갱신) |
| `standardness` | `standard` / `dialect` / `loanword` / `non_dictionary` |
| `status` | `candidate` / `active` / `retired` |
| `source_query_ids` | 어느 쿼리에서 나왔는지 — **평가 시 leakage 판별용** |

한 표현이 후보를 여러 개 가지면 **여러 줄**이 된다. 후보마다 조건과 근거와 코퍼스 지지도가 다르다.

#### `candidate_type = FIELD` — 우선순위 1번을 담기 위한 값

우선순위 1번(향수 전문 용어, 실사용 **18.1%**)은 accord나 note가 아니라
**Fragrantica 스키마 필드**를 가리킨다. `ACCORD` / `NOTE`만으로는 담을 칸이 없어 값을 추가했다.

```
탑노트   → FIELD  notes.tiered.top
지속력   → FIELD  longevity
발향     → FIELD  sillage
```

허용 필드는 `SCHEMA.md`에 **실제로 있는 것만** 쓴다. 기동 시 검사는 accord/note와 같은 방식이다.

**두 가지 주의**

- `부향률`은 매핑하지 않는다. dump에 `concentration` 필드가 없다(§6 미확인 항목과 같은 내용)
- `지속력`·`발향`은 dump 필드에 대응하지만 **현재 ERD에 담을 컬럼이 확인되지 않았다.**
  §6의 제약으로 함께 봐야 한다

#### 매핑 규칙 — 측정으로 정한 두 가지

**① 한 표현은 accord 2개 이상으로 매핑한다. 단독 매핑을 금지한다.**

accord 하나로는 상위 5개를 뽑지 못한다. 노트북 27에서 v2가 제안한 accord 7종을 단독으로
검색해 strength 합으로 정렬했을 때, 5위 진입 동점 규모가 다음과 같았다.

| 단독 | 후보 | 5위 동점 | | 조합 | 후보 | 5위 동점 |
|---|---:|---:|---|---|---:|---:|
| `citrus` | 59,969 | **17,736** | | `fresh`+`citrus` | 18,826 | **25** |
| `warm spicy` | 45,319 | **6,281** | | `soapy`+`warm spicy` | 114 | **5** |
| `fresh` | 33,478 | **830** | | `fresh`+`soapy` | 1,049 | **6** |
| `musky` | 41,154 | **4,010** | | `musky`+`powdery`+`vanilla` | 8,007 | **9** |

`citrus` 단독은 17,736개가 똑같이 강도 100이라 상위 5개가 제비뽑기가 된다.
같은 accord인데 **단독이냐 조합이냐로 기능이 되고 안 된다.**

`required` 칸의 `core` / `optional` 구분이 이 규칙을 표현한다. `core`가 최소 2개다.

**② `corpus_support`가 검색 가능 범위인지 확인한다. 아니면 항목을 넣지 않는다.**

`foresty`는 보유 향수가 **1개**라 다른 accord와 AND로 묶으면 0이 된다. 노트북 27에서
검색 불가로 판정된 3건의 원인이 전부 이것이었다(`비 온 뒤의 숲`, `숲 속에 온 듯한 향`,
`편백나무·산내음`).

목록에서 지우지는 않는다. **값을 기록하고 검색 단계에서 판단한다.**

두 규칙 모두 새 컬럼을 요구하지 않는다. `required`와 `corpus_support`가 이미 있다.
근거와 한계는 `DECISIONS.md` N2, 측정은 `nlr_engineering_notes.md` 8번.

#### 이 사전의 방법론 위치 — 표준 대비 어디에 있는가

*"정답이 없는 자연어 표현으로 어떻게 향수를 추천했는가"* 에 대한 답이다.
근거 조사 기록은 `nlr_engineering_notes.md` 9번, 결정은 `DECISIONS.md` N3.

**ISO 13299:2016**(감각 프로파일 확립 절차)의 §6.2.3 Table 1은 attribute 목록을 정하는
**허용된 세 절차**를 적는다. 그중 Row 1이 *"기존 용어와 기준 물질을 재사용한다"* 이고,
우리가 IFRA glossary와 Michael Edwards 계열 용어를 빌려 쓰는 것이 **이 절차에 해당한다.**
표준 밖의 임의 관행이 아니다.

같은 §6.2.3이 attribute 집합의 목적을 이렇게 적는다.

> *"The purpose is to identify and select a set of **non-overlapping, singular, objective,
> unambiguous, and referenced** attributes…"*

**우리가 충족하지 못하는 것은 `referenced`다.** ISO에서 이 말은 평가자에게 각 descriptor를
가르치는 **물리적 기준 물질**을 뜻한다. 훈련된 패널도 기준 물질도 없으므로 사전은 이 조건을
갖출 수 없다. 따라서 이 조항은 *"우리가 기준을 통과했다"* 가 아니라 **"기준이 무엇인지"** 에만 쓴다.

**같은 표준이 이 경로의 단점도 적어뒀다.** 인용할 때 함께 말해야 한다.

> Row 1 단점 — *"기존 용어나 기준 물질이 **특정 샘플 집합에 부정확하거나 부적절한 선택**을
> 포함할 수 있다."*
> Row 2·3 단점 — *"기준 물질이 주어지지 않으면 **다른 그룹이 해석할 수 없다.**"*

**인용 위생 3가지.** 원문은 `shall`이 아니라 `The purpose is to…`이고 문서 제목이
*General guidance*이므로 **요구사항이 아니라 목적 진술**로 인용한다. `may include`는 가능성
서술이므로 단정으로 바꾸지 않는다. ISO의 `a particular set of samples`는 **물리적 자극**이며
이를 텍스트 코퍼스로 옮기는 것은 표준이 아니라 우리 쪽 유추다.

#### 이 설계에 대한 반박 근거 — 함께 보고한다

조사에서 우리 매핑을 **반박하는** 근거가 나왔다. 지지 근거만 모으면 조사가 아니다.

| # | 반박 | 걸리는 곳 |
|---|---|---|
| 1 | 교차언어 감각 어휘 연구에서 **한쪽 언어에만 있는 용어는 정의로 풀지 않고 배제**됐다 | SCENE 6항목 (`빨래`·`이불`·`호텔`·`휴양지`·`비 오는 숲`) |
| 2 | Dravnieks Atlas는 powderiness를 **dryness와 한 concept으로 묶는다** (prefLabel `Dry`, altLabel `Powdery`) | `포근한 → powdery` — 포근함과 건조함은 같은 방향이 아니다 |
| 3 | ISO 의미의 `referenced`를 충족할 수 없다 | 사전 전체 |

그리고 **`aquatic`·`musky`·`tropical`·`white floral`의 공식 정의를 찾지 못했다.**
IFRA glossary에 미매칭이고 Dravnieks 146개 descriptor(라벨 181개)에도 0건이다.
`musky`는 맨명사 `Musk`만 있어 **white musk와 animalic musk를 구분하는 근거가 되지 못한다.**
`nlr_engineering_notes.md` 2번의 한국어 드리프트 주장이 코퍼스 관찰에만 의존하는 상태로 남는다.

#### 근거 등급

| 등급 | 뜻 | 예 |
|---|---|---|
| `VERIFIED` | 외부 자료·스키마로 검증 | `탑노트 → notes_top` (Fragrantica 스키마), `바닐라 → Vanilla` (note 목록) |
| `TEAM` | 팀이 정함, 근거 문장 기록 | `빨래 → soapy + fresh` |
| `LLM` | 사전에 없어 추정 | `달큰한 → sweet` |

`LLM` 등급은 자동으로 미매칭 로그에 쌓이고, 사람 검토를 거쳐 `TEAM`으로 승격한다.
**시간이 지날수록 설명 가능한 비율이 올라간다.** 처음부터 완벽한 사전이 필요 없다.

#### 무엇을 담는가 — 측정으로 정한 우선순위

| 순위 | 담을 것 | 근거 |
|---|---|---|
| 1 | **향수 전문 용어** (노트·탑·베이스·잔향·지속력) | 실사용 **18.1%**. Fragrantica 스키마와 직접 대응 → `VERIFIED` |
| 2 | **코퍼스 지지도** (foresty는 향수 1개) | LLM이 구조적으로 알 수 없는 우리 데이터 사실 |
| 3 | **한국어 드리프트** (머스크 ≠ musky 단독) | 코퍼스 31% 중 의도한 의미는 1.0% |
| 4 | **문맥 분기** (깨끗한 = 비누냐 물이냐) | 설명 가능성 |
| 5 | **매핑 금지** (향긋한에는 accord 없음) | 근거 없는 추론 방지 |
| 6 | 방언 `달달` 1항목 | 방언 등장의 94.7% |
| 7 | 은어·비유 | 실사용 1.3%. 로그 기반 승격 |

**표현을 나열하지 않는다.** 사전 커버리지를 재보니 새 쿼리의 8.2%(어간으로 묶어도 15.8%)였다.
나열로는 덮을 수 없고, 덮을 필요도 없다. LLM이 못 하는 지점만 담으면 된다.

방언·은어를 후순위로 둔 근거는 `DECISIONS.md` N1에 측정과 한계까지 기록했다.

#### 초기 규모

**30~50개 항목**을 목표로 한다. 10번 노트북이 `evidence_level=D`로 남긴 13개
(고급스러운·깨끗한·도시적인·비 오는 숲·빨래·섹시한·이불·자연스러운·차가운·촉촉한·포근한·호텔·휴양지)와

## 5. 정책

### 5.1 실패 처리 — 모든 LLM 호출에 비-LLM 대안이 있다

| 실패 지점 | 대체 동작 | 품질 손실 |
|---|---|---|
| LLM 1 (구조화) | 11번 `rule_lexicon.csv` 기반 규칙 파서 | 조건 인식률 41.5% → 15.5% |
| LLM 2 (문장화) | 템플릿 문장 | 문장이 딱딱해짐 |
| 미매칭 추정 실패 | 그 표현을 조건에서 제외하고 로그에 기록 | 조건 하나를 못 씀 |

**사전 조회는 LLM이 아니므로 실패 지점이 아니다.** Python 서버 자체가 죽으면
규칙 파서 + 사전 조회 + 템플릿으로 동작한다.

타임아웃은 각 호출마다 8초를 제안한다. 재시도는 스키마 검증 실패와 네트워크 오류에만 적용하고,
결과가 마음에 안 든다는 이유로 재호출하지 않는다.

### 5.2 출력 검증

LLM이 돌려준 accord/note 이름은 **반드시 허용 목록과 대조**한다. 목록에 없으면 버리고
버린 개수를 로그에 남긴다. 노트북 26에서 목록을 명시했는데도 목록 밖 이름이 3종 나왔다.

JSON Schema의 enum으로 제약하되, **목록 밖이라 버려진 값의 개수를 지표로 관리**한다.

### 5.3 부적절 입력과 프롬프트 스타일 입력

설문 실측에서 이런 입력이 나왔다.

```
[277자] "너는 최고급 니치 향수 전문 컨설턴트야. ... 각 향수마다 왜 골랐는지 설명해 줬으면"
[600자] "이 편지는 영국에서 최초로 시작되어..."   ← 행운의 편지
```

첫 번째는 **악의적 공격이 아니라 평범한 사용자의 자연스러운 입력**이다. 그래서 정책이 필요하다.

- 사용자 입력은 시스템 프롬프트와 명확히 분리된 위치에 넣는다
- 입력 안의 지시문("너는 ~야", "앞의 지시를 무시하고")은 데이터로 취급한다
- 출력이 고정 스키마이고 accord 이름이 enum이므로 인젝션이 성공해도 스키마 검증에서 걸린다
- **향과 무관한 입력**은 조건이 하나도 안 잡히므로 감지된다. 이 경우 추천 대신 안내를 보낸다

### 5.4 비회원

비회원도 추천을 받을 수 있고 결과는 저장하지 않는다. 회원과의 차이는 호출량 제한뿐이다.
이번 범위에서는 로그인 여부가 추천 결과에 영향을 주지 않는다.

## 6. 데이터 — 현재 ERD로 가능한 것과 아닌 것

### 사용하는 테이블

| 테이블 | 용도 |
|---|---|
| `perfumes` | 기본 정보. `is_active=true`만 검색 |
| `perfume_accords` | **핵심.** `weight`가 accord strength |
| `perfume_notes` | note 매칭. `note_type`으로 tier 구분 |
| `accords`, `notes` | 허용 목록 검증 |
| `perfume_map_points` | MAP-09 연동용 좌표 |
| `perfume_prices` | 가격 조건 |

### 제약 4건 — 현재 ERD를 바꾸지 않는 대신 기록한다

#### 제약 1. 계절·시간대 커뮤니티 투표가 없다

EDA 07~09번은 Fragrantica의 계절·시간대 **투표수**로 재정렬해 NDCG@10을 0.271 → 0.322로 올렸다.
그런데 ERD의 계절 데이터는 `perfume_review_seasons`, 즉 **우리 서비스 사용자가 후기에 남긴 계절**이다.
서비스 초기에는 0건이다.

**결과** — "여름에 쓸 향수" 같은 계절 조건을 데이터로 걸 수 없다.
**대응** — 계절 조건을 accord 상관으로 간접 반영하는 것을 검토한다(`10_accord_season_bridge.csv`).
검증되지 않은 우회이므로 §7에서 측정한다.

#### 제약 2. 추천 이력을 저장할 테이블이 없다

**결과** — 같은 질문을 다시 하면 처음부터 계산한다. 사후 분석 데이터가 남지 않는다.
**대응** — 이번 범위에서는 저장하지 않는다. REC-13이 자연어 입력 결과를 쓰려면 필요해지므로
부록 A에 제안을 남긴다.

#### 제약 3. `perfume_notes` PK가 `(perfume_id, note_id)`다

같은 note가 top과 base에 동시에 들어갈 수 없다.
**실측: tiered note 보유 향수 93,166개 중 4,935개(5.3%)가 이 경우다.**

**대응** — 적재 시 `top > middle > base` 우선순위로 하나만 남긴다. EDA 06번에서 tier가
유효한 추가 정보가 아니라고 판정됐으므로(개선 fold 0/5) 영향은 작을 것으로 본다.
다만 이는 향수↔향수 실험의 결론이다.

#### 제약 4. `perfumes.description`이 `VARCHAR(500)`이다

**실측: Fragrantica description 평균 505자, 500자 초과가 50,575개(38.3%)다.**

**대응** — 이번 범위에서 description을 쓰지 않으므로 기능에는 영향이 없다.
다만 **적재 시 잘림을 DB 담당자와 공유해야 한다.** 부록 A에 변경을 제안한다.

### 미확인 항목

- **`perfumes.name_ko`** — Fragrantica에 한국어 이름이 없다. 어디서 채울지 미정
- **`perfumes.concentration`** — dump에 해당 필드가 없다. 출처 확인 필요
- **적재 규모** — 131,930개 전량 적재 여부를 DB 담당자와 확인 필요

## 7. 성능 측정 · 평가 계획

### 7.1 응답 시간

| 구간 | 상태 |
|---|---|
| LLM 1 (구조화) | **실측** — golden 200: mean 1.96초 / p95 3.19초 · **합성 600: mean 1.52 / p95 2.01** · **설문 155: mean 1.60 / p95 2.13** (GMS `gpt-5.4-nano`) |
| 정규화 + 사전 조회 | **미측정.** LLM이 아니므로 수 ms 예상 |
| SQL 검색 (13만 개) | **미측정** |
| LLM 2 (문장화) | **미측정** |

> 세 수치는 **같은 조건 비교가 아니다.** 측정 시점과 입력이 다르다.
> **길이로는 설명되지 않는다** — golden 이 가장 짧은데(30자) 가장 느리다.
> 측정 시점(2026-09-01 vs 09-12), 서버 부하, 모델 버전 중 무엇이 원인인지
> **분리해 재지 않았다.** 구간 목표를 정할 때 이 값을 그대로 쓰면 안 된다.

LLM 2회 기준 예상은 4초 내외다. **호출 3회 설계에서 2회로 줄면서 2초가량 줄어든다.**

**먼저 할 일** — 미측정 세 구간을 20~30개 쿼리로 개별 계측하고 p50/p95를 낸다.
그 결과를 보고 목표를 확정한다.

### 7.2 추천 품질 — 평가셋의 역할을 나눈다

평가셋이 **세 개**다. 서로 다른 질문에 답하므로 역할을 나눈다.

| | golden 200 (팀원) | **합성 600 (AI 역생성)** | survey 155 (실사용자) |
|---|---:|---:|---:|
| 평균 길이 | 30자 | **57자** | **71자** |
| 길이 중앙값 | 29자 | **57자** | **57자** |
| 조건 수 | 1.3개 | 2.0개 | **2.7개** |
| 향수 전문 용어 | 5.5% | **0.0%** | **18.1%** |
| **정답 향수** | 없음 | **있다** | 없음 |
| **현실 노이즈** | 적음 | **없음** | **있음** |

```
golden 200   조건 추출 회귀 테스트
             라벨이 있고 재현 가능하다. 코드 변경이 깨뜨리는지 보는 용도.
             여기서 나온 숫자를 "실사용 성능"이라고 부르지 않는다

합성 600     검색 회귀 테스트 · 설계 비교용 상대 지표 · 하한선
             향수에서 문장을 역생성해 정답이 공짜로 붙는다.
             대신 현실의 노이즈가 없다. DECISIONS.md N8

survey 155   외부 holdout — 실사용 성능
             아직 라벨링 안 됨. 노트북 22가 12건 사용 → 남은 143건.
             라벨링하면 처음으로 실사용 성능을 잴 수 있다
```

**세 개가 합쳐져야 한 바퀴가 돈다.** 합성 600은 정답이 있지만 노이즈가 없고,
설문 155는 노이즈가 있지만 정답이 없다. **서로를 대체하지 않는다.**

#### 합성 600이 못 채우는 칸

| | 합성 600 | 설문 155 |
|---|---:|---:|
| 전문 용어 | **0건** | 28건 (18.1%) |
| 가격 조건 | 2건 (0.3%) | 25건 (**16.1%**) |
| 개인화 (*"나에게 어울리는"*) | **0건** | 10건 (6.5%) |

전문 용어 0%는 생성 규칙의 결과다(영어 향 용어 금지 + note 미제공). 그래서
**사전의 우선순위 1번인 전문 용어 10행은 이 평가셋으로 검증되지 않는다.**

#### holdout 취급 — 이미 한 번 건드렸다

`DECISIONS.md` N7 이 **설문 155건의 조건 개수 분포와 검색 동작을 측정했다.**
라벨 대조가 아니라 입력 분포와 시스템 동작이므로 성능을 잰 것은 아니지만,
**이후 이 155건으로 실사용 성능을 잴 때 "입력 분포는 이미 본 상태였다"를 함께 보고해야 한다.**

**그리고 설문에서 본 표현을 사전에 넣으면 holdout 이 아니게 된다.**
사전 확장의 출처는 팀 문서·미매칭 로그(§4.4)·`ai_summary` 로 제한된다.

#### 라벨링 전에 `avoid` 기준을 확정해야 한다

`16_golden_set_errata_report.md`의 가이드 개정안을 적용하지 않으면 같은 오분류가 반복된다.
실사용 문장이 더 자연스러우므로 문제가 **더 자주** 나올 것으로 예상해야 한다.

### 7.3 사전의 기여를 어떻게 재는가

**baseline은 사전 없이 LLM만 쓴 결과다.** 규칙 baseline과 비교하면 오해를 만든다.

| # | 조건 | 무엇을 분리하는가 |
|---|---|---|
| 0 | 현재 프롬프트 그대로 | baseline |
| 1 | + accord enum 제약 | 값 공간 제약의 효과 |
| 2 | + 사전 조회 | 사전 자체의 효과 |
| 3 | + 후처리 정규화 | 정규화의 효과 |
| 4 | 사전 전체를 프롬프트에 덤프 | 조회 방식 vs 덤프 |
| **5** | **크기는 같고 내용을 무작위로 섞은 사전** | **통제군** |

조건 5가 결과를 정직하게 만든다. 틀린 사전으로도 같은 이득이 나오면
측정된 건 도메인 지식이 아니라 "토큰이 늘고 구조가 생긴 효과"다.

**leakage 주의** — `korean_scent_lexicon_v0_1.csv`는 golden set 200개에서 추출됐고
`query_ids`에 출처가 기록돼 있다. 같은 200개로 평가하면 암기를 측정한다.
→ `source_query_ids`로 seen/unseen을 나눠 따로 보고하고, 최종 판단은 설문 holdout으로 한다.

**지표** — 필드별 F1(paired, n=200)을 주 지표로, Overall Exact Match는 보조로만 쓴다.

`foresty` 하나이며 92개 안에 대안이 있다), 노트북 28이 그 규칙을 적용해 사전을 만들었다.

**의미 판정은 부분적으로 생겼다.** N4가 `ai_summary` 배수로 28행을 대조했고, 노트북 39가
그 판정을 적용해 `LLM` 등급 7행 중 **4행을 `TEAM`으로 올렸다**(2번 처리됨).

**그래도 `status`는 여전히 전부 `candidate`다.** 등급(`evidence_tier`)은 *"이 매핑의 출처가
무엇인가"* 를 말하고, `status`는 *"서비스에 써도 되는가"* 를 말한다. 후자는 사전 전체를
놓고 한 번 판정해야 하므로 아직 열려 있다.

`mossy+earthy`가 `비 온 뒤의 숲`의 옳은 번역인지는 배수가 답하지 못한다. 배수는
*"그 표현으로 불린 향수에 이 accord가 흔한가"* 만 답한다(N4 한계 1).

**1번(22번 판정표 재정의)은 성격이 달라졌다.** 2번을 N4 배수로 처리했으므로 합칠 대상이
없어졌고, 노트북 32~38이 별도 평가 경로(합성 평가셋 600건)를 만들었다. 70건을 되살릴지
폐기할지는 그 경로의 결과를 보고 정하는 것이 낫다.

근거와 한계는 `DECISIONS.md` N2, 측정은 `nlr_engineering_notes.md` 8번,
사전 빌드 기록은 `analysis_outputs/28_domain_lexicon_build_report.md`.

```sql
CREATE TABLE nlr_requests (
```

### 2026-09-10 (2차) — accord 검색 성립성 측정 반영

노트북 27의 측정으로 §8 남은 작업 1번의 검색 성립성 축이 계산됐다. 사전 **스키마는 바뀌지 않고**
기존 컬럼(`required`, `corpus_support`)에 규칙이 붙었다.

| 변경 | 이전 | 이후 | 근거 |
|---|---|---|---|
| **매핑 단위** | 미정 (후보 여러 줄 허용) | **accord 2개 이상. 단독 금지** | `citrus` 단독 5위 동점 17,736개 vs `fresh+citrus` 25개 |

| `corpus_support` | 필수 컬럼 (값만 기록) | **검색 가능 범위 확인이 항목 추가 조건** | `foresty` 1개 → AND로 묶으면 0 |
| §8 작업 순서 | 1번(사람 평가)이 2번(사전)을 막고 있었음 | **2번을 먼저 시작할 수 있음** | 1번의 target space 질문에 답이 나옴 |

**되돌리는 법** — 단독 매핑을 허용하려면 §4.3 `매핑 규칙` ①을 지우고 `required`의 `core`
최소 개수 제약을 없애면 된다. canonical note를 target에 다시 넣으려면 §0의 `target 범위`
행을 지우고 노트북 23의 accord-only 축소를 되돌린다 — 그 경우 `candidate_type`이 이미

- **조건을 못 뽑는 22.3%가 그냥 사라진다.** 미매칭 로그가 미구현이다(§8 18번)
- **향수 데이터가 DB와 CSV 두 곳에 있다**(§8 19번). 협의 안건이다
- **점수 식은 이번에도 검증하지 않았다.** `strength` 단순 합 그대로다
- **LLM 구조화가 연결되지 않았다.** 붙이면 커버리지가 35.7% → 77.7% 가 되는데
  지금은 사전 문자열 매칭만 쓴다
- **추천 이유 문장화가 없다.** 근거 데이터까지만 만들어 NLR-07이 완전히 충족되지 않았다
